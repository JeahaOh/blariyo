# 금지 규칙 중심의 AI harness 설계

- 상태: 설계. 실행 코드·hook·CI·원격 보호 규칙 연결은 미구현·미검증이다.
- 규칙 정본: [AGENTS.md](../../AGENTS.md)의 G01~G10. 이 문서는 검사 방법과 한계를 소유한다.
- 대상: Claude·Codex·Gemini의 공통 작업. 특정 AI 전용 승인 절차를 추가하지 않는다.

## 목적과 책임

harness는 작업 범위·변경·검증 결과를 확인하는 공통 실행 도구다. 작업자가 선택할 수 있는
방법을 매번 지정하지 않고, 금지 경계를 넘었거나 필요한 근거가 빠진 경우를 드러낸다.

- `AGENTS.md`: 해서는 안 되는 행동과 작업 권한의 기준.
- `CLAUDE.md`·`GEMINI.md`: `@AGENTS.md`로 공통 지침을 불러오는 진입점.
- 로컬 harness: 시작 기준선과 작업 결과를 비교하는 보조 검사.
- CI·원격 보호: 해당 후보의 필수 검사 결과와 병합 조건 확인.

문서 import는 행동 준수의 보장이 아니다. 로컬 검사는 관측하지 않은 행동을 증명할 수 없고,
원격 CI는 로컬 세션의 동시 편집이나 모든 외부 행동을 관측할 수 없다. 각 계층의 한계를 보고한다.

## 검사 대응표

아래는 구현할 검사 계약이다. 현재 동작하는 검사 목록이 아니다.

| 규칙 | 기계적으로 확인할 대상 | 검토가 필요한 판단 |
| --- | --- | --- |
| G01 | 요청 범위와 실제 변경 경로의 차이 | 변경이 요구사항에 필요한지, 정본 변경이 필요한지 |
| G02 | 시작 시 기존 변경·staged 상태와 종료 diff, commit 직전 staged 경로 | 기존 변경의 소유권과 덮어쓰기 여부; 사후 diff만으로 모든 중간 행동을 증명하지 않음 |
| G03 | 작업 기록의 담당·폴더·브랜치·변경 경로·상태·갱신 시각, 쓰기·Git 작업 전 예상 밖 HEAD·파일 hash 변경 | 다른 세션의 작업 여부·담당 인계; 기록과 한 번의 점검만으로 동시성 방지를 보장하지 않음 |
| G04 | 신규 worktree 경로·격리 사유, Git 제외 규칙과 사용할 검색·검사 명령의 제외 설정 | 공통 영역·아키텍처 변경의 복잡성과 격리 필요성 |
| G05 | 현재 작업 기록의 경로·날짜·필수 항목 존재 | 기록의 정확성, 정본 갱신 필요성, 명시적 전체 쓰기 금지 요청 |
| G06 | 필수 검사 실행 여부·종료 코드·생략 수·검사 대상 SHA 또는 입력 hash 일치 | 테스트 기대값 변경의 정당성, 실행 환경 차단 원인 |
| G07 | 검사 정책·workflow·예외 목록 변경 감지 | 규칙 변경의 요청 근거와 완화 영향; AI 자체 예외 승인을 근거로 삼지 않음 |
| G08 | feature→release→main 방향, main 대상 PR의 소스, hotfix 기준 main과 main→release→진행 중 feature 전달 기록, 실제 push 대상 ref·후보 식별자 | 웹 GUI 병합 준수와 사용자 예외; PR 존재·Git 그래프·로컬 hook만으로 실행 도구나 전달의 의미적 정확성을 증명하지 않음 |
| G09 | 변경 내용의 비밀 후보와 대상 자원의 식별 정보 | 비밀 탐지의 오탐·누락, 자원 소유권·운영 영향 |
| G10 | 과거 날짜 기록 수정 감지 | 링크 보정인지 과거 사실의 소급 변경인지 |

단순 문자열 검사만으로 파괴적 명령·비밀·업무 영향 전체를 판정하지 않는다.
관측 가능한 부분만 검사하고, 근거가 부족한 부분은 검토 필요 또는 미검증으로 남긴다.
작업자 기록만으로 '승인됨'이나 '통과'를 자체 발급하지 않는다.

## 판정과 중단 범위

| 판정 | 의미와 다음 행동 |
| --- | --- |
| 통과 | 해당 검사와 입력 범위에서 위반이 발견되지 않음. 전체 작업·배포 완료와 구분 |
| 위반 | 확인된 금지 규칙 위반. 해당 쓰기·Git 반영·병합 단계 진행을 멈추고 원인·경로·복구 방법 표시 |
| 검토 필요 | 소유권·아키텍처 영향·규칙 변경 근거 등 판단이 필요함. 확보된 요청·근거를 먼저 확인하고 부족한 결정만 질문 |
| 환경 차단 | 도구·권한·의존 환경이 없어 필수 검사를 실행하지 못함. 제품 실패나 통과로 바꾸지 않음 |
| 미실행 | 아직 실행하지 않은 검사. 필수 검사이면 완료·병합 가능으로 집계하지 않음 |

위반과 무관한 읽기 전용 조사·문제 해결은 계속할 수 있다. 실패를 해결한다며 자동 stash·reset·clean,
브랜치 이동·worktree 생성·정책 예외 추가를 수행하지 않는다. 이미 허용된 수정·검증은 매번 재승인받지 않는다.

## 최소 실행 설계

1. 시작: 요청 범위·브랜치·HEAD·기존 변경과 작성 담당을 확인한다. 기존 변경 내용을 외부 로그로 복사하지 않는다.
2. 수정과 Git 반영 전: 영향을 받는 파일·기준선·동시 작업 여부를 재확인한다.
3. 검증: 실제 변경으로 필요한 검사 범위를 결정한다. 작업자가 선택한 일부 검사만으로 전체 통과를 만들지 않는다.
4. 종료: 작업 기록·최종 diff·검사 결과·미검증·권한별 Git 상태를 대조한다.

기존 [검증 안내](../testing/README.md)와 source의 검사 명령을 재사용한다.
과거 전환 전용 `verify:migration`은 일반 검사로 연결하지 않는다([코드 구조의 검증 경계](../system-design/08-code-structure.md#5-검증과-운영-경계)).
검사 뒤 대상 코드가 바뀌면 영향을 받는 결과를 무효화한다. 기록 파일 갱신과 제품 입력 변경은 구분한다.
기록은 작업 브랜치의 `worklog/YYYY-MM-DD/<주제영역>/` 한곳에 남기고 별도 task·session 기록 체계를 만들지 않는다.

검토·설계 결과만 요청됐으면 작업 기록 외 파일을 변경하지 않는다. 특정 파일의 수정·재작성 요청은
해당 범위의 변경으로 처리한다. 모든 파일 쓰기를 금지한 명시적 요청은 작업 기록 생성보다 우선한다.

## 담당 확인과 인계

같은 작업 폴더의 사용자 지정 순서와 최신 작업 기록을 대조한다. 기록에 담당·작업 폴더·브랜치·
변경 경로·진행/인계/종료 상태·갱신 시각을 남기고, 인계에는 다음 담당과 잔여 작업을 포함한다.
진행 중 담당이 겹치거나 불명확하면 쓰기·Git 작업을 시작하지 않는다. 종료 시 담당 상태를 갱신한다.
읽기 전용 조사는 가능하지만 작업 기록 쓰기도 기존 작성 담당과 충돌시키지 않는다.
이 절차는 담당을 확인하는 약속이며 원자적 잠금·다중 PC 조정 기능은 아니다.

## Worktree 검사 경계

- 신규 worktree는 기본 프로젝트 루트의 `.worktree/<주제영역>/`만 허용 대상으로 삼는다.
- 기존 외부 경로 worktree는 도입 전 자산으로 식별한다. 신규 생성 규칙을 소급 적용해 이동·삭제하지 않는다.
- [`.gitignore`](../../.gitignore)의 `/.worktree/`로 기본 프로젝트의 Git 추적과 ignore를 존중하는 검색에서 제외한다.
  Git 제외 규칙만으로 모든 검색·빌드 도구에 적용됐다고 판단하지 않는다. 생성 전에 사용할 검색·검사 명령의
  대상 경로를 확인하고, ignore를 무시하는 재귀 탐색에는 명시적인 제외를 적용한다. 확인 전에는 생성하지 않는다.
  worktree 자체를 작업 루트로 선택하면 그 안의 source는 정상 검사한다.
- 기록은 해당 worktree의 worklog에 작성해 코드와 같은 브랜치에서 관리한다.
- 일반 작업에 worktree가 없다는 이유로 검사 실패나 생성 요구를 만들지 않는다.

## Git·배포 전환 경계

최신 사용자 결정에 따른 [Git workflow](git-workflow.md)는 `feature/* → release → main`이다.
feature→release는 로컬 CLI merge를 허용하고, main 대상 release·hotfix PR은 GitHub 웹 GUI로만 병합한다.
긴급 수정은 main에서 `hotfix-*`를 만들고 main→release→진행 중 feature 순서로 전달한다.
일반 작업의 출발점·후보 확인·병합 방식과 적용 제안은 Git workflow에서 관리한다.
문서·긴급 수정도 main 보호의 자동 예외가 아니다. 대상·범위를 명시한 사용자 요청만 예외로 처리한다.
지침 도입 당시 main·release의 기존 미커밋 변경은 요청 범위에서 보완·기록할 수 있으나 직접 commit·push를
허용하지 않는다. Git 반영 전 기존 변경 보존과 작업 브랜치 이관 또는 명시적 예외를 확인한다.
이를 자동 stash·브랜치 이동으로 해결하지 않는다.

현재 [배포 정책](../operations/deployment-policy.md)과 [CI source](../../.github/workflows/ci.yml)는
main 검증·이미지 게시와 별도 수동 배포를 다룬다. release push 검사와 main 대상 PR의 소스 제한은 별도 전환 작업이다.
문서만 바꾸고 기존 branch 이력·CI·원격 보호가 전환됐다고 보고하지 않는다.

GitHub PR 필수 설정은 CLI·API의 PR 병합과 웹 병합을 구별하는 GUI 전용 설정이 아니다.
로컬 pre-push는 git push를 검사하며 GitHub CLI·API 병합은 가로채지 못한다. 원격 권한과 AI 작업 규칙을 함께 관리한다.
PR 검사만으로 금지한 직접 push가 차단됐다고 보고하지 않는다. 원격 보호 설정과 실제 거부·통과 동작이 필요하다.
release의 로컬 병합·push를 허용하는 설계에 PR 전용 제한을 일괄 적용하지 않는다. push 권한은 요청 범위로 확인한다.
로컬 hook은 보조 검사이며 유일한 강제 수단으로 사용하지 않는다. CI는 필수 하위 검사가 실제로
실행·성공했는지 최종 판정해야 하며 skipped·누락을 통과에 포함하지 않는다.

## 수용 조건

- 세 도구의 새 세션에서 공통 지침이 읽히고 같은 금지 경계를 설명할 수 있어야 한다.
- 일반 작업의 worktree 미생성, 신규 경로 위반·제외 설정 미확인, 작업 기록 누락을 구분해야 한다.
- 검토 요청의 기록 예외와 명시적 전체 쓰기 금지, 담당 충돌·인계와 브랜치 직접 반영 예외를 구분해야 한다.
- 정상 feature→release 로컬 병합과 main 대상 금지 push를 구분하고, hotfix의 main→release→진행 중 feature 전달을 확인해야 한다.
- GUI 전용은 작업 규칙이며 GitHub 기본 설정·로컬 hook으로 완전히 강제했다는 잘못된 판정을 하지 않아야 한다.
- 기존 변경·예상 밖 HEAD 변경을 감지하되 검사기가 기존 변경을 수정하지 않아야 한다.
- 필수 검사 실패·생략·결과 누락·검증 후 코드 변경을 통과로 처리하지 않아야 한다.
- 작업 규칙 변경은 자체 완화로 통과하지 않고 기존 기준과 변경 근거를 검토해야 한다.
- 원격 강제 적용은 실제 PR·직접 push의 거부와 정상 변경 통과를 별도로 확인해야 한다.
