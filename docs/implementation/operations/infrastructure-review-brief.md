# Blariyo 인프라 독립 검토 요청서

작성일: 2026-09-10. **이 문서는 배포 전 독립 검토 요청의 시점 사본이다.**
2026-09-20 Lightsail 배포와 구현 보완 이후 상태는 [현재 운영 상태](current-status.md)를 따른다.
아래 OCI 후보·공용 R2 키·미배포 설명을 현재 구현으로 사용하지 않는다. 당시 검토 입력은 보존한다.
프로젝트 배경, 현재 설계, 확인된 구현 차이, 검토 지시를 모두 포함한다. 저장소 접근이나 다른 프로젝트 문서 열람은 필수가 아니다.
이 문서는 검토용 기준 시점 사본이며 제품·기술 정본을 대체하지 않는다. 아래 수치는 별도 표시가 없으면 **설계값이며 실측 결과가 아니다.**

## 1. 검토 에이전트에게 요청하는 작업

당신은 소규모 웹서비스 운영을 검토하는 독립 리뷰어다. 아래 설계를 비판적으로 검토하고, 초기 운영에 적합한지 한국어로 판단해줘.

- 이 파일을 프로젝트 입력 자료로 사용해줘. 다른 프로젝트 문서를 요구하는 대신, 부족한 정보는 가정을 명시하거나 미확인으로 남겨줘.
- 최신 가격·무료 한도·가입 조건·서비스 제약은 Oracle, Cloudflare, AWS 등 **공식 문서**로 확인하고 조회 날짜와 링크를 제시해줘. 웹 접근이 안 되면 최신성 미확인으로 표시해줘.
- 설계의 타당성을 검토하는 작업이다. 아래 코드 관찰 요약만으로 전체 코드의 보안·동작·배포 성공을 보증하지 마.
- 파일 변경, 계정 생성, 유료 자원 생성, 서버 작업, 배포는 하지 마. 검토 결과와 권장 조치만 작성해줘.
- 기존 사업자 선택에 맞춰 결론을 내리지 마. 문제가 있다면 근거와 함께 수정안을 제안해줘.
- 운영자 1명이 유지할 수 있는 단순한 구성을 우선해줘. Kubernetes·다중 리전·복잡한 분산 구성은 구체적인 필요 조건 없이는 제안하지 마.

## 2. 서비스와 운영 목표

Blariyo는 한국 이용자를 대상으로 하는 이미지 중심 게시판 서비스다.

| 항목 | 현재 전제 |
| --- | --- |
| 초기 기능 M0 | 운영자가 짤 게시글을 작성·예약 발행·숨김 처리하고, 이용자는 로그인 없이 목록·상세를 조회 |
| 후속 M1 / M1.5 | 회원 기능 / 익명 게시판·댓글·신고. 사용자 쓰기와 악용 방어 부하는 그때 재산정 |
| 운영 인원 | 초기 1명 |
| 예상 부하 | 저트래픽으로 시작한다는 가정. 방문자·동시 요청·응답시간·DB 크기의 운영 실측은 없음 |
| 비용 목표 | 초기 공개 검증 월 USD 0~12, 유료 대안 12~24. 기존 목표이며 현재 요금 확인 필요 |
| 별도 비용 | 도메인·메일·세금·환율을 위 목표에서 제외했음. 총비용 평가에서는 함께 구분할 것 |
| 장애 수용 | 무중단보다 장애 감지·외부 백업·복원을 우선하는 단일 서버 운영 |
| 복구 목표 | RPO: 최대 24시간 데이터 손실 허용 목표. RTO: 장애 확인 후 4시간 이내 공개 읽기 복구 목표 |
| 기능 선택 | GA4는 기본 비활성. 활성 승인과 동의 처리 전에는 켜지 않음. 초기 공개의 필수 기능은 아님 |

RPO와 RTO는 보장된 서비스 수준이 아니다. 실제 복구 시험과 운영 대응 시간을 포함해 달성 가능한지 검토해야 한다.
다른 작은 개인 앱을 같은 서버에 추가할 가능성이 있지만 앱 종류·수·부하는 미정이다. 이를 필수 배치 조건으로 간주하지 말고, 추가 허용 조건을 제안해줘.

## 3. 검토 대상 배치안

```text
이용자 / 운영자
    │ HTTPS
Cloudflare: DNS · CDN · TLS · 관리자 Access
    │ Tunnel 연결
공개 VM 1대: Docker Compose
    cloudflared → nginx → Nuxt Web/BFF → NestJS Core API → PostgreSQL
                               │                │
                        관리자 인증 검증    R2 이미지 / 캐시 삭제 API
    예약·정리 작업: 단발성 애플리케이션 명령
    백업 작업: PostgreSQL → 암호화 → R2 비공개 백업

운영자 로컬 PC: 별도 Spring collector + 로컬 PostgreSQL
    외부 출처·Discord와 통신 → 공개 Web의 수집 전용 API → Core
    공개 VM에는 collector를 올리지 않음
```

- Web은 Nuxt SSR, API는 NestJS·TypeORM·TypeScript strict, DB는 PostgreSQL 18이다. Node 설계 고정값은 24.18.0이다.
- BFF는 브라우저 요청을 받아 내부 API로 중계하는 웹 서버 역할이다. nginx는 Web만 호출하고, Core는 Web을 통해서만 접근한다. DB는 Core와 백업 작업만 접근한다.
- Redis, 별도 관리형 DB, 다중 API 서버, 상시 staging 서버는 현재 범위에 없다.
- collector를 끄거나 운영자 PC가 꺼져도 공개 조회·수동 작성·예약 발행·백업은 동작해야 한다.

### 서버 후보와 전환 조건

| 후보 | 현재 설계 | 비용 전제와 확인할 점 |
| --- | --- | --- |
| 우선 후보 | OCI 서울 A1, ARM64, 2 OCPU·12GB, Ubuntu 24.04, 부팅 볼륨 100GB 이하 | Always Free 범위. 전체 부팅·추가 볼륨 200GB 한도 전제. 계정 전체 무료량과 실제 생성 가능 여부 확인 필요 |
| 대안 | AWS Lightsail 서울, x86_64, 2 vCPU·2GB·60GB, swap 2GB | 기존 가격 기준 2026-08-14의 월 USD 12. 최신 요금·트래픽·IP 조건 재확인 필요 |
| 대안 증설 | Lightsail 서울 4GB·80GB | 기존 월 USD 24. 메모리 부족 시 전환하는 안 |

사용자가 가입 과정에서 **서울을 선택할 수 없다고 보고했다.** 실제 가입 화면과 계정별 자원은 검증하지 않았다.
리전의 존재, 신규 가입 시 홈 리전 선택 가능 여부, 해당 계정의 무료 A1 생성 가능 여부를 각각 구분해줘.
다른 리전을 선택한 뒤 서울로 옮길 수 있다고 가정하지 마. 무료 계정·체험 크레딧·유료 전환 계정의 조건도 구분해줘.

현재 문서에는 A1을 3일 이내 확보하지 못하면 Lightsail로 전환하는 기준이 있다.
또한 A1 장애 2회 또는 복구 4시간 초과 시 영구 전환한다는 조항과, 복구 4시간 초과 2회 시 대안을 검토한다는 조항이 함께 있다. 이 기준은 아직 일관되게 정리되지 않았다.
월 인프라 예상 비용 USD 15 초과 시 원인 검토와 신규 유료 자원 승인을 요구하는 기준도 있어, USD 24 증설안과의 승인 관계를 검토해야 한다.

### 자원 배분안

| 컨테이너 | OCI CPU 상한 | OCI 메모리 상한 | Lightsail 2GB 메모리 상한 |
| --- | ---: | ---: | ---: |
| cloudflared | 0.25 | 128MB | nginx와 합계 192MB |
| nginx | 0.25 | 128MB | 위 합계에 포함 |
| Web | 1.00 | 768MB | 384MB |
| API | 0.75 | 512MB | 256MB |
| PostgreSQL | 1.25 | 2GB | 768MB |
| 백업 단발 작업 | 0.50 | 512MB | 별도 상한 미기재 |

OCI CPU 상한 합계는 물리 CPU보다 크며 자원 예약은 하지 않는 설계다. 모든 앱이 동시에 최대 부하를 쓰지 않는다는 가정이다.
Lightsail은 PostgreSQL shared_buffers 192MB, work_mem 4MB, maintenance_work_mem 64MB, max_connections 30, API 연결 풀 10으로 시작하는 안이다.
서버에서 소스나 Docker 이미지를 빌드하지 않는다. swap은 지속 사용을 전제로 하지 않는다.
메모리 p95 80% 초과, 메모리 부족 종료(OOM), swap 15분 지속을 증설 판단에 사용하되 기존 문서의 OOM 즉시 증설·원인 확인 후 증설 표현은 통일이 필요하다.
OS·Docker·페이지 캐시·이미지 재인코딩·백업·배포 중 구버전/신버전 동시 실행까지 포함해 자원안의 현실성을 평가해줘.

## 4. 네트워크·인증·데이터 설계

- 평상시 VM 인바운드는 차단하고 Tunnel의 아웃바운드 연결을 사용한다. 긴급 SSH만 운영자 고정 IP에 임시 허용한다.
- DB·Core·Web 포트를 인터넷에 직접 공개하지 않는다. Docker 네트워크는 edge, app, data로 분리한다.
- `/admin*`와 `/api/v1/admin/*`는 Access로 보호한다. 공개 게시판과 수집 전용 API에는 같은 관리자 정책을 일괄 적용하지 않는다.
- Web은 Access 토큰의 서명·발급자·대상·만료를 검증하고, 외부 식별자를 내부 operator ID로 대응한다. Core에는 서비스 토큰과 서명한 운영자 정보만 전달한다.
- 관리자 응답·비공개 정보는 공개 캐시 대상이 아니다. 게시글 숨김 시 목록·상세·이미지 캐시 삭제를 재시도 가능한 작업 기록(outbox)으로 처리한다. 숨긴 글 응답은 404·no-store다.
- 공개 서비스 주소 설계값은 `https://blariyo.com/`이다. 실제 DNS·소유권·연결은 이 문서로 확인되지 않았다. 이미지 도메인은 미정이다.

### R2와 이미지 보관

| 버킷 | 용도 | 공개·권한 설계 |
| --- | --- | --- |
| blariyo-media-private | 초안·재인코딩한 원본·임시 업로드 | 비공개, 전용 자격증명 |
| blariyo-media-public | 발행된 이미지 | 이 버킷에만 이미지 도메인 연결, 전용 자격증명 |
| blariyo-backup | 암호화 DB 백업·manifest | 비공개, 전용 자격증명 |

발행 시 private 원본을 public에 복사하고, 원본은 복구·재공개를 위해 유지한다. 검증 전 업로드 raw bytes는 영구 보관하지 않는다.
이미지는 개당 최대 10MiB, 게시글당 최대 20개다. 영구 이미지 증가 가정은 하루 30개 글 × 이미지 1.5개 × 평균 350KB로, public 월 약 0.47GB, private 포함 약 0.94GB다. 실제 원본 크기와 차이가 날 수 있다.
수집 preview는 별도 24시간 임시 보관하며 위 계산에 포함되지 않는다. DB 백업 저장 예산은 총 4GB다.
기존 무료량 전제는 R2 Standard 저장 10GB-month, 월 Class A 요청 100만·Class B 요청 1,000만이다. 최신 요금과 세 버킷·임시 이미지·백업 합산을 다시 계산해줘.
R2 사용량 7GB 경고, 9GB에서 업로드 제한 또는 유료 전환 결정이 기존 기준이다. 무료 유지 때문에 정상 데이터 삭제나 보안 완화를 선택하지 않는다는 원칙과 일치하는 운영 절차가 필요하다.

## 5. 백업·배포·장애 대응 설계

- PostgreSQL을 매일 03:30·15:30 KST에 logical dump하고, age 암호화·SHA-256 manifest를 거쳐 R2에 업로드한다. 원격 검증까지 성공해야 백업 성공이다.
- 최근 28개(14일)와 주간 8개를 보관한다. 매월 새 DB로 복원 시험을 한다. 복호화 키는 서버 밖에 보관한다.
- DB의 앱·migration·백업 역할과 비밀번호를 분리한다. 비밀값은 각 컨테이너에 필요한 파일로 주입하며 저장소·이미지·로그에 넣지 않는다.
- CI에서 테스트 후 ARM64/AMD64 이미지를 빌드하고 commit SHA와 digest로 고정한다. 서버는 pull → 백업 → 호환 migration → API/Web 교체 → smoke 순서다.
- 실패 시 이전 이미지로 되돌리되 비호환 DB 변경은 자동 rollback하지 않는다.
- 별도 상시 staging 대신 운영 VM의 임시 preview Compose 검증 후 전환하는 설계다. preview DB·비밀정보·작업 실행의 격리와 자원 예산은 이 요약에서 확인되지 않았다.
- VM 소실 시 새 서버 준비 → 이미지·설정 배치 → DB 복원 → R2 재연결 → Tunnel 전환 → 공개 조회 검증을 수행한다.
- 공급자 이전 시 기존 서버의 모든 DB 쓰기와 scheduler/outbox를 중단한 뒤 최종 dump를 복원한다. 새 서버 검증 후 전환하고 기존 서버는 읽기 전용으로 24시간 관찰한다.
- 외부 감시는 5분마다 공개 health와 목록을 확인한다. 사업자·알림 수신 경로는 미정이다. 내부 감시는 디스크·메모리·swap·재시작·5xx·응답시간·백업 나이·outbox 실패·R2 사용량을 확인하는 설계다.
- Cloudflare 장애에 따른 서비스 중단과 R2 장애 시 캐시가 없는 이미지의 표시 실패를 수용한다. R2 장애 시 업로드·발행을 제한하되 텍스트 공개 조회와 관리자 숨김은 유지하려는 설계다.

무료 VM 회수·계정 접근 상실·운영자 부재 때 위 복구 시간이 가능한지, R2 한 계정에 이미지와 백업을 모은 위험이 허용 가능한지 검토해줘.

## 6. 현재 확인된 구현 차이와 검증 한계

다음은 작성일에 저장소 파일을 읽어 확인한 내용이다. 실행 시험 결과가 아니다.

| 항목 | 관찰 내용 | 검토 관점 |
| --- | --- | --- |
| 루트 Compose | 이름이 local이며 DB trust 인증, localhost 주소, Web/API의 test 환경, 로컬 관리자 인증을 사용. DB/API/Web만 정의 | 이 파일을 그대로 운영 배포할 수 없음. production 네트워크·인증·작업·비밀값 설정이 필요 |
| R2 어댑터 | private/public 두 버킷에 한 S3Client와 한 키 쌍을 사용. 발행은 CopyObject로 private에서 public으로 복사 | 버킷별 별도 키 설계와 차이. 키 분리 시 교차 버킷 복사에 필요한 읽기/쓰기 권한과 구현 방법까지 검토 |
| R2 환경변수 | 실제 코드는 R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY, R2_PRIVATE_BUCKET, R2_PUBLIC_BUCKET 사용 | 설계의 R2_PRIVATE/PUBLIC별 키 이름과 불일치 |
| Web 설정 | 실제 runtimeConfig는 actorSecret, accessIssuer, accessAudience, adminOperatorsFile 등 사용 | 설계에 적힌 ADMIN_ACTOR_HMAC_SECRET·CLOUDFLARE_ACCESS 계열 이름과 배포 대응 필요 |
| 캐시 설정 | 실제 Core는 CACHE_ZONE_ID, CACHE_PURGE_TOKEN 사용 | 설계의 CF_ZONE_ID, CF_CACHE_PURGE_TOKEN과 불일치 |
| 내부 API 포트 | 로컬 Compose의 API는 3100, 설계는 4000 | 포트 자체보다 배포 설정과 호출 주소의 일치 여부 확인 필요 |
| GA4 | 활성·승인 flag 기본 false, ID 빈 값 | 기본 비활성 유지 가능. 실제 외부 수집 검증과는 별개 |

실제 계정 가입, 서울 A1 생성, 운영 VM 부하, ARM64 운영 이미지 기동, Access/R2/CDN 실연동, 원격 백업 복원, 실서비스 장애 대응은 이 전달 문서에서 검증 완료로 제시하지 않는다.
로컬 테스트의 존재나 통과 이력을 외부 운영 검증으로 대신하지 마. 이 파일만으로 확인할 수 없는 구현은 “코드 또는 운영환경 추가 확인 필요”로 분류해줘.

## 7. 반드시 답할 질문과 결과 형식

다음 순서로 검토 결과를 작성해줘.

1. **종합 판정:** 현 설계 유지 가능 / 조건부 유지 / 주요 변경 필요 중 하나와 핵심 이유 3개 이내.
2. **주요 발견 사항 표:** 운영 전 필수 / 초기 운영 중 보완 / 추후 검토로 우선순위를 나누고, 근거(이 문서 절 또는 공식 링크), 실제 영향, 권장 조치를 적어줘. 확정 문제와 추가 검증이 필요한 위험을 구분해줘.
3. **현실적인 선택:** OCI에서 Blariyo만 운영 / OCI에 다른 앱도 함께 운영 / Lightsail로 시작을 비교하고 추천해줘. 앱 수·동시 접속자를 측정 없이 단정하지 마.
4. **자원·비용 검토:** 백업·preview·OS까지 포함한 메모리 여유, CPU 경합, R2 전체 저장량, 무료 한도 초과 조건을 계산해줘. 무료 계정과 유료 계정에서 예산 알림이 실제 과금 차단인지도 구분해줘.
5. **실행 순서:** 사용자가 콘솔에서 확인할 일, 개발자가 수정할 일, 배포 후 시험할 일을 각각 제시해줘. 가장 먼저 해야 할 일은 5개 이내로 추려줘.
6. **남은 불확실성:** 검토에 사용한 가정, 웹에서 확인하지 못한 조건, 실제 계정·부하·복구 시험이 필요한 항목을 남겨줘.
