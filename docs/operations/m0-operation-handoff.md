# M0 운영 인수 체크리스트

상태: **실제 운영 인수 미실행**.

이 문서는 개발자가 통과시킨 로컬 테스트를 운영자가 실제 운영 준비 상태로 받아도 되는지 확인하는 절차다.
운영자는 사용자 본인(OWNER)이다. 공동 운영자가 있으면 게시물 작업만 담당하는 EDITOR로 본다.

## 먼저 할 일

오늘 바로 이어서 한다면 아래 순서대로 진행한다.

| 순서 | 해야 할 일 | 통과하면 남길 증거 |
| --- | --- | --- |
| 1 | 운영자 계정으로 관리자에 실제 로그인한다. | OWNER/EDITOR 로그인 허용·거부 결과, MFA 확인 시각 |
| 2 | 관리자 화면에서 글 10~20건을 직접 처리한다. | 작성·이미지·발행·예약·취소·숨김 결과와 불편사항 |
| 3 | 현재 운영 서버 상태를 읽기 전용으로 확인한다. | 현재 배포 SHA, image digest, API/Collector DB 버전, timer 상태 |
| 4 | 최근 백업과 복원 가능성을 확인한다. | 18시간 이내 백업, 격리 DB 복원, 실패 시 되돌릴 방법 |
| 5 | Discord·수집 장비·Drive 전환은 별도 준비가 끝난 뒤 확인한다. | 실제 수신, DB/R2 readback, Drive 독립 복원 |

이 다섯 가지가 끝나기 전에는 “운영 인수 완료”로 표시하지 않는다.

## 용어

| 문서 안 표현 | 쉬운 뜻 |
| --- | --- |
| Access/MFA | Cloudflare Access 로그인과 2단계 인증 |
| OWNER | 서버·DB·백업·운영 설정을 관리하는 사용자 본인 |
| EDITOR | 게시물 작성·편집만 하는 공동 운영자 |
| SHA | 어떤 소스 코드 버전을 배포했는지 나타내는 Git 식별자 |
| image digest | 서버에서 실제 실행 중인 Docker 이미지 식별자 |
| ledger | DB에 적용된 API/Collector 버전 기록 |
| readback | 저장됐다고 믿지 않고, 다시 읽어서 값이 맞는지 확인하는 것 |
| R2 | 이미지·첨부 파일을 보관하는 Cloudflare R2 저장소 |
| Drive | 운영 DB 백업을 옮길 Google Drive 저장소 |
| age 복구키 | 백업 파일 암호를 풀 때 쓰는 복구 키 |
| S1~S5 | 수집 출처를 운영에 넣기 전 확인해야 하는 5단계 |

## 하면 안 되는 일

- 토큰, 쿠키, JWT, DB 비밀번호, 계정 식별값을 문서나 채팅에 쓰지 않는다.
- 과거 로컬 테스트 PASS를 실제 운영 인수 완료로 쓰지 않는다.
- 기존 R2 백업이 정상이라고 해서 Drive 전환까지 끝난 것으로 보지 않는다.
- 검증되지 않은 출처를 한꺼번에 수집 대상으로 켜지 않는다.
- 장애가 났을 때 원문 전체가 들어 있는 과거 full dump로 무작정 되돌리지 않는다.
- legacy 수집 기능은 별도 재활성화 결정 전까지 켜지 않는다.

## 1. 관리자 실제 로그인 확인

목적: 운영자가 실제로 들어갈 수 있고, 권한 없는 사람은 막히는지 확인한다.

### 실행

1. OWNER 계정으로 관리자에 로그인한다.
2. MFA를 완료한다.
3. 관리자 목록 화면이 열리는지 확인한다.
4. EDITOR 계정으로 로그인한다.
5. EDITOR가 게시물 작업 화면에 접근할 수 있는지 확인한다.
6. EDITOR가 서버 설정, DB, R2, Drive, legacy 설정 변경에 접근하려고 할 때 거부되는지 확인한다.
7. 한 계정을 비활성화한 뒤, 이미 열려 있던 브라우저에서 다음 요청이 거부되는지 확인한다.

### 통과 기준

- OWNER는 관리자 작업을 할 수 있다.
- EDITOR는 게시물 작업만 할 수 있다.
- EDITOR는 설정·서버·DB·저장소·백업 작업을 할 수 없다.
- 비활성화된 계정은 기존 세션에서도 다음 요청이 거부된다.
- 브라우저 HTML/API 응답에 storage credential이나 계정 원문이 노출되지 않는다.

### 기록

| 역할 | 로그인 | 허용된 작업 | 거부된 작업 | 세션 회수 | MFA 시각 | 결과 |
| --- | --- | --- | --- | --- | --- | --- |
| OWNER | 사용자 보고 성공, 2026-10-03 11:38 KST | 미실행 | 해당 없음 | 미실행 | 2026-10-03 11:38 KST | 부분 확인 |
| EDITOR | 미실행 | 미실행 | 미실행 | 미실행 | 미정 | 미검증 |

2026-10-03 사용자 결정·관측:

- 운영자가 직접 쓰는 글, 익명 게시판 성격의 글은 출처 없음 허용.
- 게시글 작성은 완료.
- `/admin` 초안 작성 화면에서 이미지 업로드 버튼은 보이나 업로드가 실패하고 화면 문구는 없었다.
- 브라우저 콘솔에서 `/api/v1/admin/images` 413 응답을 확인했다. 일반 관리자 업로드는 파일당 10MiB,
  한 번에 최대 10개·전체 100MiB, 40MP와 애니메이션 자원 제한을 넘으면 실패할 수 있다.
- 최신 소스에는 업로드 실패 문구가 있으므로, 운영 배포 버전 차이 또는 화면 표시 위치/상태 문제를 후속 확인한다.
- 후속 파일 대조: `reward.png`는 PNG 370x165·12K로 업로드 성공. `maly_mint.jpg`는 JPEG 22677x14173·4.0M로
  파일 크기는 작지만 약 321MP라 40MP 해상도 제한 초과로 실패한 것으로 판단한다.

## 2. 관리자 화면 수동 인수

목적: 자동 테스트가 아니라 사람이 실제로 글을 처리할 때 헷갈리지 않는지 확인한다.

자세한 12건 기록 양식은 [Core 관리자 수동 인수 기록](../testing/operator-acceptance.md)을 사용한다.

### 실행

1. 글 10~20건을 직접 만든다.
2. 각 글에 제목, 본문, 출처, 이미지 2개, 이미지 대체 텍스트를 넣는다.
3. 저장 후 제목으로 다시 검색해 내용이 유지되는지 확인한다.
4. 일부 글은 즉시 발행하고 공개 화면에서 확인한다.
5. 일부 글은 예약 발행한다.
6. 일부 예약 글은 취소한다.
7. 발행 글을 숨김 처리하고 이미지 회수 상태를 확인한다.
8. 숨긴 글을 다시 공개한다.
9. 작은 화면에서 목록으로 돌아가기와 편집으로 돌아가기를 확인한다.
10. 혼동, 반복 클릭, 느린 구간, 내용 유실, 중복 발행을 기록한다.

### 통과 기준

- 내용 유실 0건
- 잘못 공개된 글 0건
- 중복 발행 0건
- 출처 없는 운영자 직접 작성 글을 허용함
- 이미지 없는 글과 이미지 있는 글을 각각 확인함
- 고해상도 이미지 실패 시 화면에 이해 가능한 오류 문구가 보이는지 확인함
- 예약 취소한 글은 예약 시각 이후에도 공개되지 않음
- 숨김 글은 공개 목록과 공유 화면에서 보이지 않음
- 운영자가 남은 불편사항을 수용하거나 수정 후 재확인함

## 3. 운영 서버 상태 재조회

목적: 지금 운영 중인 것이 어떤 버전인지 확인한다. 과거 배포 기록을 현재 상태로 재사용하지 않는다.

### 실행

1. 현재 실행 중인 Web/API image digest를 확인한다.
2. 현재 Git SHA를 확인한다.
3. DB ledger에서 API와 Collector 버전을 확인한다.
4. feature flag 상태를 확인한다.
5. 예약 발행 timer와 알림 timer 상태를 확인한다.
6. 현재 공개 글·이미지 수량을 읽기 전용으로 다시 확인한다.

### 통과 기준

- 현재 실행 중인 SHA와 image digest가 기록된다.
- API/Collector 버전이 기록된다.
- timer 상태가 기록된다.
- 9월 23일 또는 9월 25일의 과거 수치를 현재 수치로 복사하지 않는다.

## 4. 백업과 복원 확인

목적: 배포나 운영 전환 전에 실제로 되돌릴 수 있는지 확인한다.

### 실행

1. 최근 18시간 안에 생성된 정상 백업이 있는지 확인한다.
2. 백업을 운영 DB가 아닌 격리 DB에 복원한다.
3. 복원된 DB에서 주요 테이블과 수량을 확인한다.
4. 백업 파일 hash가 변하지 않았는지 확인한다.
5. Drive 전환 전에는 기존 정상 R2 백업 경로를 유지한다.
6. Drive 전송을 시험할 때는 업로드, 다운로드, 독립 복원을 각각 확인한다.
7. Drive 장애가 나면 같은 선택 profile로 R2에 되돌릴 수 있는지 확인한다.

### 통과 기준

- 최근 18시간 이내 백업이 있다.
- 격리 DB 복원이 성공한다.
- 복원 결과를 다시 읽어 확인한다.
- Drive 전환은 정기 백업 2회 성공과 독립 복원 후에만 판단한다.
- 실패한 새 백업 때문에 이전 정상 백업의 만료 시간을 임의로 늘리지 않는다.

## 5. 수집 출처 운영 편입

목적: 어떤 사이트를 실제 수집 대상으로 켜도 되는지 출처별로 판단한다.

현재 원칙은 **검증된 출처만 M0에 포함**이다. 21개 adapter가 있다는 사실이나 과거 개발 저장 결과는 운영 편입 증거가 아니다.
에펨코리아, 뽐뿌, 유튜브 커뮤니티, PGR21은 사용자 재개 지시 전까지 보류한다.

### 출처별 확인 5단계

| 단계 | 사람이 확인할 질문 | 통과 기준 |
| --- | --- | --- |
| S1 허용 | 이 출처를 요청해도 되는가? | robots, User-Agent, 간격, 일일 한도, redirect 제한을 지킴 |
| S2 발견 | 목록이나 지정 URL에서 실제 원문을 찾는가? | 같은 실행에서 목록과 상세 또는 승인된 상세 URL 확인 |
| S3 보존 | 본문·이미지·첨부·외부 링크가 빠지지 않는가? | 순서와 수량이 맞고, 한도 초과로 잘리지 않음 |
| S4 저장 | DB와 R2에 저장된 값을 다시 읽어 확인했는가? | DB/object bytes/hash/size 일치, 미승인 공개 0건 |
| S5 운영 | 운영자가 이 출처를 받아들였는가? | 검수, 알림, 보존, 고지까지 확인 |

`--dry-run`도 외부 사이트 요청과 quota 기록을 남긴다. 단순 조회가 아니다. 실제 요청은 승인된 표본만 사용한다.

| 미정 | 미정 | 미정 | 미실행 | 미실행 | 미실행 | 미실행 | 미실행 | 후보 |

## 6. Discord와 수집 장비 확인

목적: 실제 장비에서 요청을 받고, 취소·중복·권한 오류까지 처리되는지 확인한다.

### 실행

1. 실제 사용할 장비와 OS를 정한다.
2. 장비 재시작 후에도 queue가 중복 처리되지 않는지 확인한다.
3. 허용된 Discord 사용자와 채널에서만 요청이 접수되는지 확인한다.
4. 같은 Discord interaction이 다시 들어와도 1건만 접수되는지 확인한다.
5. 확인 전 취소와 10분 만료가 정상 처리되는지 확인한다.
6. 비허용 사용자·채널 요청이 거부되는지 확인한다.
7. 내부 성공 기록과 실제 사용자 수신 메시지를 따로 기록한다.

### 통과 기준

- 장비 재시작 후 중복 queue 0건
- 비허용 사용자·채널 접수 0건
- 취소·만료 후 URL/actor/channel 정보 제거
- 실제 Discord 수신 확인

### 기록

| 시험 | 시작/종료 시각 | 대상 안전 ID | 기대 결과 | 실제 결과 | 담당 |
| --- | --- | --- | --- | --- | --- |

## 중단 기준

아래 중 하나라도 발생하면 새 수집·회수·Drive 전환을 멈추고 Core 수동 운영만 유지한다.

- 권한 없는 계정이 관리자·서버·DB·저장소에 접근한다.
- 원문이나 이미지가 유실된다.
- 잘못된 글이 공개된다.
- 예약 취소한 글이 공개된다.
- robots 또는 quota 판단이 불확실하다.
- DB와 R2 readback 값이 다르다.
- 백업 복원이 실패한다.
- Discord에서 비허용 사용자나 채널 요청이 접수된다.

만료·회수 대기·삭제 실패만으로 신규 수집을 중단하지 않는다. 회수는 독립적으로 재시도하고 지연·실패를 경보 및 관찰표에 기록한다. 위 권한·데이터 유실·복원 실패 등의 중단 기준은 유지한다. [현행 수집 정책](../planning/content-collection/README.md#13-m0-마무리-결정--2026-09-26)을 따른다.
