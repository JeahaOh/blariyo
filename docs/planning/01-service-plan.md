## 1. 결론

`blariyo`의 방향을 범용 커뮤니티 CMS에서 운영자 큐레이션형 유머 피드로 좁힌다. 서비스 공개 명칭은 `블라리요`로 확정한다. 이미 확보한 도메인을 기준으로 브랜드, SEO, 공유 문구, 운영자 표기를 통일한다.

첫 출시에서는 커뮤니티 전반을 만들지 않는다. 먼저 아래 가설 하나만 검증한다.

> 운영자가 고른 유머 콘텐츠를 사용자가 한 번에 여러 개 보고, 7일 안에 다시 방문하는가?

이 가설을 확인하기 전에는 회원 커뮤니티, 자동 추천, 네이티브 앱으로 확장하지 않는다. 다만 광고는 수익 기능이 아니라 화면 구조와 동의 UX에 영향을 주는 제품 요소이므로 기획 단계에서 위치, 금지 영역, 빈도 제한, 중단 조건을 먼저 정의한다.

개발과 운영은 검증 결과에 따라 다음 단계로 분리한다.

| 단계               | 목적                    | 핵심 범위                                     |
| ------------------ | ----------------------- | --------------------------------------------- |
| M0 피드 검증판     | 반복 소비 검증          | 공개 피드, 상세, 조회 기록, 관리자 게시글 API |
| M1 커뮤니티판      | 참여와 운영 가능성 검증 | 회원, 좋아요, 댓글, 신고, 최소 관리자 화면    |
| M1.5 승인형 제보판 | 사용자 콘텐츠 수요 검증 | 제보 작성, 내 제보, 관리자 검수와 승인 발행   |

## 2. 서비스 이름과 기획 선행 원칙

### 확정안

- Repository 및 내부 코드명: `blariyo`
- 서비스 공개명: `블라리요`
- 도메인: 확보된 `blariyo` 도메인을 사용한다.
- 슬로건: 결정 보류. 후보는 [06-copy-candidates.md](./06-copy-candidates.md)에서 관리한다.

문서, 화면, SEO, 관리자 기본 작성자명, 푸터 브랜드는 `블라리요`로 통일한다.

### 기획 선행 원칙

AA, IA, 화면 설계, 기술 설계는 기획 확정 이후에 다시 정리한다. 기존 화면 설계와 와이어프레임은 현재 기준으로 구현 확정 산출물이 아니라 참고안이다.

기획 확정 전 완료해야 할 항목은 아래와 같다.

| 항목      | 결정해야 할 내용                                      |
| --------- | ----------------------------------------------------- |
| 브랜드    | 서비스명, 슬로건, 편집자 표기, 공유 제목              |
| 콘텐츠    | 선별 기준, 출처·권리 기준, 게시 빈도                  |
| 홈 구조   | 최신 피드 밀도, 게시판 2개 노출, 페이지네이션 방식      |
| 상세 구조 | 본문 소비 흐름, 하단 목록, 출처와 권리자 요청          |
| 광고 UX   | 광고 위치, 표시 방식, 금지 위치, 빈도 제한, 중단 조건 |
| 운영      | 주간 운영 시간, 콘텐츠 후보 수집, 삭제 요청 처리      |

### 게시판 구성

게시판은 2개만 사용한다.

| 게시판 | 용도 | M0 작성 권한 |
| --- | --- | --- |
| 유머 | 이미지와 짧은 텍스트 중심의 웃긴 자료 | 운영자 |
| 이야기 | 생활 공감, 짧은 썰, 가벼운 읽을거리 | 운영자 |

게시글은 반드시 두 게시판 중 하나에만 속한다. 홈과 상세 하단 목록은 이 두 게시판 기준으로만 이동한다.

## 3. 문제와 대상

### 해결할 문제

유머 콘텐츠는 여러 플랫폼에 흩어져 있고 품질 편차가 크다. 사용자는 게시판을 탐색하기보다 짧은 시간에 선별된 콘텐츠를 연속해서 보고 싶어 한다.

### 1차 사용자

- 출퇴근, 점심시간, 자기 전에 5분 정도 가볍게 보는 사람
- 글을 직접 쓰기보다 보고 반응하는 사람
- 자극적인 이슈보다 무난한 유머와 댓글 반응을 선호하는 사람

### 이번에 해결하지 않는 문제

- 누구나 글을 올리는 대형 커뮤니티
- 실시간 이슈 전달

## 4. 고급유머 벤치마킹 기준

2026-08-11 기준 `goodgag.net` 검색 노출 정보와 공식 소개 페이지를 확인했다. 원문 웹 페이지는 직접 접속 시 차단될 수 있으므로, 현재 문서는 검색 캐시와 공개 마켓에 노출된 구조를 근거로 삼는다.

고급유머에서 확인되는 핵심은 기능 수가 아니라 운영 방식이다. “운영자가 계속 수동 업데이트한다”, “첫 화면이 바로 최신 콘텐츠 목록이다”, “광고 기반 무료 소비와 광고 제거 수익화가 공존한다”는 점을 블라리요 기획의 기준점으로 둔다.

### 가져올 것

- 운영자가 콘텐츠를 선별하는 방식
- 첫 화면에서 바로 보이는 최신 피드
- 짧은 제목과 이미지 중심의 빠른 소비
- 게시글 단위의 독립 URL
- 페이지 번호 기반의 오래된 글 탐색
- 게시글 목록 사이에 광고 행을 끼워 넣는 수익화 패턴
- 상세 화면의 광고 영역, 본문 하단 흐름, 하단 목록 배치
- 광고 차단 사용자에게 해제 요청을 보여주는 안내 패턴
- 제휴 상품 모음과 일반 게시글 안의 상품 링크 연결 패턴
- 꾸준한 게시 주기가 만드는 재방문 습관
- 공식 소개에서 강조하는 수동 업데이트 운영 메시지
- 광고 제거 구독까지 이어지는 장기 수익화 힌트

### 가져오지 않을 것

- 익명 게시판과 다수 게시판
- 많은 랭킹 종류
- 앱 푸시와 네이티브 앱
- 대규모 사용자 차단 및 제재 기능
- 댓글과 커뮤니티 경쟁을 초기 핵심으로 삼는 구조
- 원본 저작권과 출처 확인 없는 단순 재게시 운영

장기적으로 참고할 항목은 광고 제거 구독과 커뮤니티 정화 구조다. 단, 블라리요의 초기 기획은 데스크톱·모바일 웹 피드와 운영자 큐레이션의 반복 소비 검증에 집중한다.

- [고급유머 상품형 게시물 모음](https://www.goodgag.net/pr)
- [고급유머 App Store](https://apps.apple.com/kr/app/%EA%B3%A0%EA%B8%89%EC%9C%A0%EB%A8%B8/id495871144)
- [고급유머 Google Play](https://play.google.com/store/apps/details?id=net.appeat.dogdrip)

## 5. 핵심 원칙

1. M0와 M1의 공개 게시글은 운영자만 등록한다.
2. 사용자는 로그인하지 않아도 모든 콘텐츠를 볼 수 있다.
3. 첫 화면은 최신 피드 하나로 시작한다.
4. 기능 추가보다 콘텐츠 품질과 재방문을 먼저 본다.
5. MySQL 하나만 사용한다.
6. 자동 수집은 허용하되, 수집 결과를 즉시 공개 발행하지 않는다.
7. 출처 표시와 사용 권리 확인을 분리해서 관리한다.
8. 운영이 주 4시간을 넘으면 기능이나 게시량을 줄인다.

## 6. 단계별 범위

### M0: 피드 검증판

M0는 외부 사용자 100명 내외에게 보여줄 수 있는 최소 웹 서비스다.

#### 사용자 기능

- 로그인 없는 최신 게시글 피드
- 페이지네이션
- 게시글 상세
- 이미지와 텍스트 표시
- 원본 유형과 조건부 출처 링크 표시
- 게시글 조회 기록
- 모바일 우선 반응형 웹 화면
- 게시글 URL 공유 시 제목과 대표 이미지 노출
- 상세 화면 공유하기
- 카카오톡, X/Twitter 등 SNS 공유용 Open Graph와 Twitter Card meta tag
- 서비스 하단의 권리자 요청 연락처
- 분석 동의 후 GA4 유입·화면 흐름 측정

#### 운영 기능

- 관리자 로그인
- Swagger 또는 보호된 API를 통한 게시글 등록, 수정, 숨김
- 게시판 코드 선택
- 발행 전 출처와 권리 상태 입력
- 조회 수와 일별 방문 수 확인

#### M0에서 만들지 않는 것

- 일반 사용자 회원가입과 로그인
- 좋아요와 싫어요
- 댓글과 신고
- 인기글
- 검색
- 마이페이지
- 게시글 업로드 관리자 화면
- 이미지 업로드 UI
- 실제 광고 노출과 광고 스크립트 연동
- MongoDB 로그 적재

관리자 전용 웹 화면을 먼저 만들지 않는다. 기존 Swagger 또는 API 클라이언트로 운영해보고 반복 작업이 불편할 때 M1에서 화면을 만든다.

### M1: 커뮤니티판

M0 성공 조건을 충족했을 때만 시작한다.

#### 추가할 기능

- 이메일 회원가입, 로그인, 로그아웃
- 게시글 좋아요 1종
- 댓글 목록, 작성, 본인 삭제
- 게시글과 댓글 신고
- 관리자 게시글 관리 화면
- 관리자 신고 목록과 수동 처리
- 관리자 댓글 숨김과 사용자 비활성화
- 좋아요 수 기준의 단일 인기 목록

#### M1에서도 제외할 것

- 유저 게시글 직접 공개
- 싫어요
- 대댓글과 댓글 좋아요
- 자동 숨김과 자동 제재
- 주간, 댓글순 등 다중 인기글
- 포인트, 뱃지, 쪽지, 채팅
- 실시간 알림과 푸시
- OAuth 로그인
- 앱과 PWA
- 영상 업로드
- 자동 크롤링
- 광고 슬롯 DB 관리

### M1.5: 승인형 제보판

M1의 댓글과 신고 운영이 안정된 경우에만 사용자 제보를 연다. 제보는 사용자가 작성하지만 즉시 공개하지 않는다.

#### 추가할 기능

- 로그인 사용자의 제보 작성
- 제목, 본문, 대표 이미지 1개, 원본 유형과 출처 입력
- 직접 제작 또는 사용 권한 보유 확인
- 내 제보 목록과 처리 상태 확인
- 검수 대기 중인 제보 철회
- 관리자 제보 검수 목록
- 승인, 반려, 반려 사유 기록
- 승인된 제보를 기존 게시글로 발행

#### 운영 규칙

- 사용자당 하루 3건까지만 제출할 수 있다.
- 대표 이미지는 `jpg`, `png`, `webp`, 최대 5MB로 제한한다.
- 직접 제작이면 원본 유형을 `ORIGINAL`로 기록하고 외부 출처 URL을 받지 않는다.
- 외부 콘텐츠면 원본 유형을 `EXTERNAL`로 기록하고 출처 이름과 URL을 필수로 받는다.
- 출처 URL만으로 권리가 확보됐다고 판단하지 않는다.
- 운영자가 내용, 출처, 권리를 확인한 뒤에만 공개한다.
- 승인 시 기존 `TB_POST`로 전환하고 제보자 번호를 연결한다.
- 반려 사유는 `RIGHTS`, `DUPLICATE`, `POLICY`, `QUALITY`, `OTHER` 중 하나로 기록한다.
- 제보 검수 목표 시간은 접수 후 48시간 이내다.
- 제보자가 철회하거나 반려된 이미지는 운영 저장소에서 7일 안에 삭제한다. 암호화 백업의 잔여 사본은 최대 28일 후 만료한다.

#### M1.5에서도 제외할 것

- 검수 없는 즉시 공개
- 제보 수정과 버전 이력
- 이미지 여러 장과 영상 업로드
- 공동 작성과 임시 저장
- 포인트, 보상금, 등급 상승
- 제보 승인 수 기반 자동 권한 부여

제보 대기 건이 20건을 넘거나 가장 오래된 건을 48시간 안에 처리하지 못하면 신규 제보를 일시 중단한다.

## 7. 핵심 사용자 흐름

### M0 사용자

```text
링크 진입 -> 최신 피드 -> 게시글 상세 -> 다음 게시글 -> 재방문
```

### M0 운영자

```text
후보 수집 -> 권리 확인 -> 이미지 준비 -> API 등록 -> 발행 확인 -> 지표 확인
```

### M1 사용자

```text
피드 조회 -> 상세 조회 -> 로그인 -> 좋아요 또는 댓글 -> 문제 콘텐츠 신고
```

### M1 운영자

```text
게시글 관리 -> 신고 확인 -> 댓글 또는 게시글 숨김 -> 처리 사유 기록
```

### M1.5 사용자

```text
로그인 -> 제보 작성 -> 검수 대기 -> 승인 또는 반려 확인
```

### M1.5 운영자

```text
제보 목록 -> 내용·출처·권리 확인 -> 승인 또는 반려 -> 승인 게시글 발행
```

## 8. 화면 설계

### M0 화면

| 화면 | 필수 요소                                                                             | 제외 요소          |
| ---- | ------------------------------------------------------------------------------------- | ------------------ |
| 홈   | 게시판형 최신 목록, 번호, 게시판, 제목, 게시 시각, 조회 수, 페이지네이션, 하단 연락처, 광고 배치 후보의 여백 정책, 기본 OG tag | 블로그형 카드 피드, 인기 탭, 회원 메뉴 |
| 상세 | 게시판형 제목·메타 영역, 본문, 이미지, 하단 출처, 공유하기, 하단 목록, 하단 연락처, 게시글별 OG tag                         | 블로그형 히어로 상세, 댓글, 반응, 추천, 개별 이동 버튼 |

홈과 상세는 블로그 레이아웃이 아니라 커뮤니티 게시판 레이아웃을 기본으로 한다. 고급유머처럼 목록에서 게시판, 제목, 번호, 조회 수, 게시 시각을 빠르게 훑고, 상세를 읽은 뒤 하단 목록에서 바로 다른 글로 이동하는 흐름을 우선한다.

홈 목록과 상세 하단 목록은 페이지당 20개를 기본으로 한다. 상세 하단에는 현재 페이지의 최신 목록 또는 현재 글 주변 목록을 다시 보여준다. 사용자는 브라우저 뒤로 가기를 누르지 않아도 다음 콘텐츠를 고를 수 있어야 한다.

광고는 M0 수익 기능으로 바로 켜지지 않는다. 그러나 화면 설계 전에 광고 위치와 금지 영역을 확정해야 한다. 광고를 나중에 붙이기 위해 본문 흐름을 깨는 방식은 피한다.

기획 기준은 아래와 같다.

| 광고 후보         | 화면                    | 기획 판단                                         |
| ----------------- | ----------------------- | ------------------------------------------------- |
| 상세 본문 하단 광고 | 본문과 출처 다음        | 본문 소비가 끝난 뒤 노출하는 기본 후보            |
| 상세 하단 목록 중간 광고 | 상세 하단 목록 안       | 하단 목록 안에 1개만 넣는 광고 행 후보           |
| 상세 하단 목록 아래 광고 | 상세 하단 목록 아래     | 목록 탐색 이후 노출하는 하단 광고 후보            |
| 홈 목록 중간 광고 행 | 게시글 행 사이          | 5~6번째 게시글 이후 1개만 후보로 둠. 목록 첫 화면 진입을 막지 않아야 함 |
| 광고 차단 해제 요청 | 광고 영역 또는 상세 하단 | 광고가 차단된 경우에만 안내. 콘텐츠 열람을 막지 않음 |
| 제휴 상품 링크    | 상품형 게시글 본문 상단 | 명확한 제휴 고지와 외부 이동 확인을 전제로 후보 |
| 제휴 상품 목록    | 별도 제휴 목록 화면     | 일반 최신 피드와 분리. 트래픽 게이트 이후 후보 |
| 대형 광고         | 상세 연속 탐색 중간     | 첫 방문 금지, 닫기 필수, 일 최대 3회 후보         |

광고 영역은 게시글 행처럼 보이면 안 된다. `광고` 표기를 명확히 두고, 로딩 실패 시 빈 박스가 콘텐츠 사이에 남지 않게 한다. 홈 목록 광고는 연속 게시글 사이에 하나만 끼워 넣는 형태로 설계하고, 번호·작성자·조회 수를 가진 게시글처럼 렌더링하지 않는다.

광고 차단 해제 요청은 광고 로드 실패 또는 광고 차단 감지 시에만 표시한다. 본문, 목록, 공유, 출처 이동을 막지 않는다. 문구는 짧게 유지하고, `계속 보기`, `해제 방법 보기`, `다시 확인` 세 가지 명령만 둔다. 같은 세션에서 사용자가 닫으면 재노출하지 않는다.

쿠팡 파트너스 같은 제휴 수익화는 가능하다. 단, 일반 유머 게시글과 제휴 상품형 게시글을 데이터와 화면에서 분리한다. 상품형 게시글에는 `제휴 링크`, `수수료 고지`, `원문 자료 보기`, `외부 쇼핑몰 이동`을 명확히 표시한다. 별도 제휴 목록은 `/partners` 같은 독립 경로 후보로 두고, 일반 최신 피드에는 기본 노출하지 않는다.

### 공유와 SNS 미리보기

공유 기능은 M0 상세 화면에 포함한다. 목적은 사용자가 본 유머를 카카오톡, X/Twitter, 브라우저 기본 공유, 링크 복사로 쉽게 전달하게 하는 것이다.

#### 공유 버튼

| 공유 방식 | 우선순위 | 동작 |
| --- | ---: | --- |
| 브라우저 기본 공유 | 1 | 모바일에서 `navigator.share`가 가능하면 제목, 설명, canonical URL을 전달 |
| 링크 복사 | 2 | 모든 환경에서 canonical URL을 clipboard에 복사하고 성공/실패 상태를 표시 |
| 카카오톡 공유 | 3 | Kakao JavaScript SDK를 사용해 스크랩 공유 또는 피드 템플릿 공유 제공 |
| X/Twitter 공유 | 4 | `https://twitter.com/intent/tweet`에 제목과 canonical URL을 전달 |

공유 버튼은 상세 헤더 우측에 기본 배치한다. 데스크톱에서는 공유 버튼 클릭 시 작은 메뉴를 열고, 모바일에서는 기본 공유를 먼저 시도한 뒤 실패하면 공유 메뉴를 보여준다.

#### URL 기준

- 공유 URL은 항상 `https://{service-domain}/posts/{postNo}` 형식의 canonical URL이다.
- 페이지 번호, 유입 캠페인, 임시 preview token은 `og:url`에 넣지 않는다.
- 숨김 또는 없는 게시글은 `404`와 `noindex`로 처리하고 공유 meta를 생성하지 않는다.
- 관리자 preview URL은 SNS crawler에 노출하지 않는다.

<link rel="canonical" href="https://blariyo.example.com/">

#### 이미지와 캐시 규칙

- 공유 이미지는 absolute HTTPS URL이어야 한다.
- 기본 공유 이미지는 `1200 x 630`을 기준으로 만든다.
- 게시글 대표 이미지가 공유용 비율에 맞지 않으면 서버 또는 운영 도구에서 중앙 crop된 OG 이미지를 별도로 만든다.
- 카카오톡 스크랩과 SNS crawler가 접근할 수 있도록 인증이 필요한 URL, 내부망 URL, 만료 URL을 사용하지 않는다.
- 공유 이미지는 5MB 이하로 유지한다.
- 게시글 제목, 설명, 이미지가 바뀌면 카카오 OG 캐시 초기화가 필요할 수 있다.
- GA4에는 공유 대상 채널과 게시글 번호만 보내고, 사용자 개인 식별값이나 공유 대상 정보를 보내지 않는다.

## 9. 콘텐츠 정책

### 등록 가능한 콘텐츠

- 직접 제작한 콘텐츠
- 제작자에게 사용 허가를 받은 콘텐츠
- 상업적 재사용이 허용된 라이선스 콘텐츠
- 인용 범위와 출처가 명확한 텍스트 콘텐츠

### 등록하지 않는 콘텐츠

- 출처가 불분명한 재게시 이미지
- 불법 촬영물과 성인물
- 개인 신상과 연락처가 노출된 자료
- 특정 집단에 대한 혐오와 차별
- 악성 정치 분쟁을 목적으로 한 자료
- 타 서비스의 유료 콘텐츠를 복제한 자료

출처 URL이 있다는 사실만으로 사용 권리가 확보되지는 않는다. 게시글에는 `source_name`, `source_url`, `rights_status`, `rights_note`를 함께 기록한다.

### 출처 후보 수집

고급유머처럼 외부 출처를 표시하는 운영 방식은 벤치마킹한다. 블라리요도 자동 수집을 할 수 있다. 다만 수집 결과를 공개 게시글로 즉시 전환하지 않는다.

허용하는 방식은 아래와 같다.

| 방식 | 설명 | 단계 |
| --- | --- | --- |
| 수동 후보 등록 | 운영자가 URL, 제목, 출처명, 메모를 직접 입력 | M0 |
| 후보 수집 도구 | 운영자가 지정한 URL의 제목, 대표 이미지 후보, 원문 링크만 임시 큐에 저장 | M1 후보 |
| 출처별 자동 수집 | 허용 목록에 등록한 출처에서 목록과 상세 후보를 주기적으로 수집 | M1 후보 |
| 중복 확인 | 같은 원문 URL 또는 유사 제목이 이미 있는지 확인 | M1 후보 |
| 발행 전 검수 | 본문, 이미지, 출처, 권리 상태를 운영자가 직접 확인한 뒤 발행 | M0 |

금지하는 방식은 아래와 같다.

- 외부 사이트의 목록을 주기적으로 수집한 뒤 자동 발행한다.
- 원문 이미지 파일을 권리 확인 없이 저장하거나 재배포한다.
- 출처 표기만으로 사용 권리가 확보됐다고 처리한다.
- 원문 사이트의 차단, robots 정책, 이용 조건을 우회한다.
- 본문 전문을 기계적으로 복제해 블라리요 본문으로 사용한다.

후보 수집 도구를 만들더라도 공개 게시글 테이블에 바로 쓰지 않는다. `TB_SOURCE_CANDIDATE` 같은 임시 큐에 저장하고, 운영자가 검수 완료한 건만 `TB_POST`로 발행한다.

#### 출처별 수집 계획

초기 수집 대상은 운영자가 명시적으로 허용 목록에 넣은 사이트만 사용한다. 출처별 adapter를 분리해 URL 구조, 목록 selector, 상세 selector, 속도 제한, 차단 대응을 독립 관리한다.

| 출처 | 수집 대상 | 수집 필드 | 우선순위 |
| --- | --- | --- | --- |
| 이토랜드 | 유머, 인기, 생활관, 핫딜 목록 후보 | 원문 URL, 제목, 작성자명, 작성 시각, 추천 수, 조회 수, 게시판명, 썸네일 후보 | 1 |
| 펨코 | 포텐·유머성 상세 후보 | 원문 URL, 제목, 작성자명, 작성 시각, 조회 수, 추천 수, 댓글 수, 첨부 이미지 후보 | 2 |
| 개드립넷 | 개드립, 유저 개드립, 읽을거리 후보 | 원문 URL, 제목, 댓글 수, 게시판명, 목록 위치, 상세 출처 표시 후보 | 2 |
| 고급유머 | 벤치마킹 구조 확인용 | 메뉴, 목록 밀도, 광고 위치, 하단 목록 구조 | 수집 발행 대상 아님 |

수집 주기는 처음에는 6시간 1회 이하로 제한한다. 같은 출처에 연속 요청하지 않고, 출처별 실패율이 높으면 자동으로 해당 출처를 일시 중지한다. HTTP 403, 429, 로그인 요구, CAPTCHA, 차단 페이지가 나오면 우회하지 않고 해당 후보를 `BLOCKED` 상태로 기록한다.

수집 상태는 `PENDING`, `DUPLICATE`, `NEEDS_REVIEW`, `APPROVED`, `REJECTED`, `BLOCKED`로 관리한다. `APPROVED`가 되어도 바로 공개하지 않고 운영자의 최종 발행 명령을 별도로 둔다.

### 권리자 요청

- 연락 창구를 서비스 하단에 표시한다.
- 권리 확인이 필요한 요청은 접수 즉시 비노출한다.
- 게시글, 저장 이미지, 캐시를 함께 제거한다.
- 요청과 처리 결과를 운영 기록에 남긴다.

## 10. 댓글과 신고 운영

이 절은 M1부터 적용한다.

### 댓글

- 로그인 사용자만 작성한다.
- 작성자는 본인 댓글을 삭제할 수 있다.
- 외부 링크, 연락처, 동일 내용 반복 등록을 제한한다.
- 계정별 작성 속도를 제한한다.
- 관리자가 숨긴 댓글은 원문과 처리 사유를 보존한다.

### 신고

- 동일 사용자는 같은 대상에 한 번만 신고할 수 있다.
- 신고 수는 검토 우선순위로만 사용한다.
- 신고 횟수에 따른 자동 숨김은 하지 않는다.
- 불법 촬영물, 개인정보, 성인물 의심은 신고 수와 관계없이 즉시 비노출한다.
- 일반 신고는 24시간 이내 확인한다.

### 운영 한계

아래 중 하나가 3일 이상 이어지면 신규 가입 또는 댓글 작성을 잠시 닫는다.

- 댓글 하루 50개 초과
- 신고 하루 5건 초과
- 일반 신고를 24시간 안에 처리하지 못함
- 운영 시간이 주 4시간 초과

## 11. 가벼운 운영 계획

### 게시량

- 시작 재고: 30개
- 신규 게시: 평일 하루 2~3개
- 주간 목표: 10~15개
- 콘텐츠 준비: 주 1회 2시간 30분 배치 작업
- 일일 확인: 게시 상태와 긴급 문의를 10~15분 확인

고급유머와 같은 대량 게시 빈도를 초기 목표로 잡지 않는다. 재방문에 필요한 최소 게시량부터 찾는다.

### M0 주간 운영 시간 목표

| 작업                    |       목표 시간 |
| ----------------------- | --------------: |
| 콘텐츠 수집과 권리 확인 |           150분 |
| 등록과 예약 발행        |            30분 |
| 지표 확인               |            20분 |
| 문의와 삭제 요청        |            20분 |
| 합계                    | 3시간 40분 이하 |

M1에서 댓글과 신고를 열면 주간 운영 상한은 그대로 4시간이다. 초과분은 기능 축소 신호로 본다.

M1.5 제보 검수도 같은 주간 운영 상한 안에 포함한다. 제보 처리를 위해 주 4시간을 넘기면 신규 제보를 닫고 기존 콘텐츠 운영을 우선한다.

단계가 늘어도 운영 시간을 더하지 않고 콘텐츠 준비 시간을 줄여 커뮤니티 운영 시간을 확보한다.

| 단계 | 콘텐츠 준비·등록 | 댓글·신고 | 제보 검수 | 지표·문의 |  합계 |
| ---- | ---------------: | --------: | --------: | --------: | ----: |
| M1   |            140분 |      70분 |         - |      30분 | 240분 |
| M1.5 |            105분 |      55분 |      50분 |      30분 | 240분 |

콘텐츠 준비 시간을 줄인 단계에서는 신규 게시 목표를 주 10~15개에서 주 7~10개로 낮출 수 있다. 게시량보다 운영 안정성을 우선한다.

## 12. 검증 지표와 중단 기준

M0 공개 후 4주 동안 최소 순사용자 100명, 세션 200건을 확보한 뒤 판단한다. 소규모 표본이므로 절대값보다 방향과 사용자 인터뷰를 함께 본다.

- 방문·조회·재방문 지표의 정본은 MySQL 내부 이벤트다.
- GA4는 유입 채널, 기기, 화면 흐름과 광고 전후 행동 비교에 사용한다.
- 분석 동의를 거부한 사용자도 핵심 기능을 그대로 사용할 수 있어야 한다.
- GA4에는 이메일, 닉네임, 제목, 본문, 댓글, 제보 원문을 보내지 않는다.
- 세부 이벤트와 동의 기준은 [04-analytics-ad-plan.md](./04-analytics-ad-plan.md)를 따른다.

### 계속할 조건

| 지표                        |                    기준 |
| --------------------------- | ----------------------: |
| 세션당 상세 조회 수 중앙값  |                3개 이상 |
| 7일 재방문율                |                20% 이상 |
| 피드에서 상세로 이동한 세션 |                50% 이상 |
| 다시 사용할 의향            | 인터뷰 10명 중 6명 이상 |
| 운영 시간                   |           주 4시간 이하 |

위 다섯 조건 중 네 개 이상을 충족하면 M1을 진행한다.

### 보류 또는 중단 조건

- 세션당 상세 조회 수 중앙값이 2개 미만
- 7일 재방문율이 10% 미만
- 인터뷰에서 기존 플랫폼 대신 사용할 이유가 없다는 응답이 과반
- 권리 확인 때문에 주간 게시 목표를 2주 연속 달성하지 못함
- 운영 시간이 2주 연속 주 6시간을 넘음

중단 조건에 걸리면 회원, 댓글, 사용자 제보를 추가하지 않는다. 콘텐츠 주제, 선별 기준, 게시 주기를 먼저 수정하고 한 번만 재검증한다.

## 13. 기술 결정

### 확정

| 항목        | 결정                                                                                                     | 이유                                                                    |

| 광고        | 기획 단계에서 UI/UX 위치를 확정하고, 트래픽 게이트 이후 목록 중간 광고 행, 상세 상·하단 배너와 일 3회 제한 대형 광고를 실험 | 나중에 억지로 붙이면 소비 흐름과 레이아웃이 깨지므로 사전 설계가 필요함 |

### 이미지

M0에서는 운영자가 권리를 확인한 `jpg`, `png`, `webp`만 사용한다.

- 게시글당 대표 이미지 1개
- 파일당 최대 5MB
- 영상과 GIF 업로드 제외
- 외부 이미지 핫링크 금지
- 배포 서버의 영속 볼륨에 저장하고 매일 백업
- M1 이후 운영이 계속되면 S3 호환 스토리지로 이전

M0에는 업로드 UI를 만들지 않는다. 운영자가 파일을 정해진 경로에 배치하고 게시글에 경로를 입력한다.

## 14. 데이터 설계

기존 테이블을 관리자 인증에 사용한다. 권한과 상태 코드는 SQL 기준인 `ADM`, `SAD`, `ACT`로 통일한다.

- `content`

- `image_path`
- `image_alt`

- `source_type`: `ORIGINAL`, `EXTERNAL`
- `source_name`

- `rights_status`
- `rights_note`
- `board_code`
- `author_no`
- `visible_yn`
- `published_at`
- `reg_dttm`
- `upd_dttm`

- `event_no`
- `anonymous_id`
- `session_id`
- `event_type`: `FEED_VIEW`, `POST_VIEW`
- `post_no`: nullable

원문 IP와 User-Agent 원문은 장기 보관하지 않는다. M0 검증에 필요한 방문, 세션, 게시글 조회만 기록한다.

### M1 추가

- `TB_COMMENT`: 게시글 댓글과 숨김 상태
- `TB_POST_LIKE`: 사용자별 게시글 좋아요, `(post_no, user_no)` unique
- `TB_POST_REPORT`: 게시글 신고와 처리 상태
- `TB_COMMENT_REPORT`: 댓글 신고와 처리 상태

신고를 하나의 다형성 테이블로 만들지 않는다. 게시글과 댓글 신고를 분리해 외래키와 데이터 정합성을 유지한다.

### M1.5 추가

#### `TB_POST_SUBMISSION`

- `submission_no`
- `submitter_no`
- `title`
- `content`
- `image_path`
- `source_type`: `ORIGINAL`, `EXTERNAL`
- `source_name`
- `source_url`: `ORIGINAL`이면 nullable
- `rights_confirmed_yn`
- `status`: `PENDING`, `APPROVED`, `REJECTED`, `WITHDRAWN`

승인 처리는 하나의 트랜잭션에서 제보의 원본 유형과 출처 정보를 복사해 `TB_POST`를 생성하고 `published_post_no`와 상태를 갱신한다. 승인된 게시글에는 nullable `submission_no`, `submitter_no`를 연결한다. 반려·철회 건은 운영 이력을 위해 텍스트와 상태를 보존하되 업로드 이미지는 운영 저장소에서 7일 후 삭제한다.

## 17. 현재 저장소 상태와 선행 문제

현재 저장소에서 재사용 가능한 것은 Express, MySQL 연결, 사용자 테이블, Swagger, Jest 설정이다. 프론트엔드와 게시글 도메인은 미구현 상태다.

구현 시작 전에 다음을 해결해야 한다.

1. JWT 생성과 검증 코드를 정상화한다.
2. 비밀번호 비교 로직을 수정한다.
3. `ApiError` 내보내기와 에러 처리 순서를 수정한다.
4. SQL, 서비스, 테스트의 권한/상태 코드를 통일한다.
5. 기획과 실제 API를 `/api/v1`으로 통일한다.

README는 이 문서를 기준으로 M0 큐레이션 피드, MySQL 단일 사용, 단계별 확장 방향으로 정리한다.

| 회원/좋아요/댓글         | M0 계속 조건 5개 중 4개 충족                                                  |
| 승인형 사용자 제보       | M1 댓글·신고 운영이 8주 연속 주 4시간 이내                                    |
| 유저 게시글 직접 공개    | 승인형 제보를 8주 운영한 뒤 별도 검토                                         |
| 광고 실행                | 월간 활성 사용자 1만 이상, 최근 30일 5만 PV 이상, 직접 광고 제안 중 하나 충족 |
| 제휴 상품 목록           | 광고 실행 조건 충족 후, 제휴 고지·외부 이동·수익 정산 정책 문서화 완료        |
| 이미지 오브젝트 스토리지 | 영속 볼륨 5GB 초과 또는 다중 서버 필요                                        |
| PWA/앱                   | 이번 기획서의 검토 대상에서 제외. 별도 사용자 요구가 확인되면 새 기획으로 분리 |
| 추천 알고리즘            | 게시글과 행동 데이터가 수동 큐레이션 비교에 충분히 쌓임                       |

조건을 충족하지 않으면 해당 기능은 백로그에만 둔다.

광고 UX 기획은 개발 전 확정한다. 실제 광고 실행은 목록 중간 광고 행과 상세 상·하단 배너부터 시작한다. 광고 차단 해제 요청은 광고 실행과 동시에 열 수 있지만 열람 차단 방식으로 만들지 않는다. 2주간 소비 지표 하락이 없을 때만 대형 광고를 일 1회로 열고, 주 단위로 일 2회, 최대 일 3회까지 올린다. 제휴 상품 목록은 광고 실행 조건을 충족한 뒤 별도 게이트로 연다. 안정적인 운영비 회수 목표는 월 10만 PV이며 세부 손익·중단 기준은 분석 및 광고 운영 설계서를 따른다.

## 22. 최종 판정

이 프로젝트는 구현 가능하다. 다만 첫 버전을 댓글 커뮤니티로 잡으면 가볍지 않다.

적당한 시작점은 다음과 같다.

> 운영자가 권리를 확인한 유머 콘텐츠를 주 10~15개 올리고, 사용자는 로그인 없이 피드와 상세를 본다. 4주 동안 반복 소비와 주 4시간 이하의 운영 가능성을 확인한 뒤에만 회원과 댓글을 연다. 사용자 콘텐츠는 댓글 운영이 안정된 뒤 승인형 제보로 추가하며 즉시 공개 게시판은 만들지 않는다.

이 범위라면 현재 `blariyo` 기반을 살리면서도 중간에 버려지는 기능을 줄일 수 있다.
