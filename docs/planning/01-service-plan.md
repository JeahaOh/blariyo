## 1. 서비스 정의

블라리요는 관리자가 보기에 웃긴 짤을 골라 하루 두 차례 묶어서 올리는 반응형 웹 서비스다.

- 데스크톱 웹과 모바일 웹을 하나의 반응형 화면으로 운영한다.
- 초기에는 운영자만 게시한다.
- M0의 짤 콘텐츠는 로그인 없이 열람한다. 네이버, 카카오, Google, Apple 소셜 회원가입·로그인은 M1에서 제공한다.
- 목록과 상세는 블로그보다 커뮤니티 게시판 형태로 구성한다.
- 고급유머의 빠른 목록 탐색, 상세 하단 목록, 목록 중간 광고 배치를 참고한다.
- 콘텐츠 후보는 운영자가 Discord `/collect url` 또는 관리자 화면으로 원문 URL을 지정해 모으는 흐름을 제공하며, 별도 batch는 source policy의 `HOT_LIST`·`GENERAL_LIST` 목록을 발견한다. 현재 연결 범위와 미완료 항목은 §8을 따른다. 공개 여부는 항상 운영자가 결정한다.
- 네이티브 앱은 현재 범위에 포함하지 않는다.

### 출시 단계

| 단계 | 포함 범위 | 제외·후속 범위 |
| --- | --- | --- |
| M0 Core | 운영자 수동 짤 발행·예약·숨김, 공개 목록·상세, 정책 화면, 게시글 조회 수, GA4 연동 준비(기본 비활성) | 수집 보조·자동 수집, 회원, 사용자 작성, 광고 |
| M0 수집 보조 | Discord `/collect url` 또는 관리자 URL 입력, 단일 상세 페이지 후보 생성, 검수·반려·초안 승격 | 목록·feed·pagination 자동 수집 |
| M0 자동 수집 | 후속 단계. 사용 결정된 출처 목록·feed의 후보 자동 적재와 실패 시 출처 비활성 | 자동 발행, 차단 우회 |
| M1 | 네이버·카카오·Google·Apple 가입·로그인·탈퇴 | 사용자 게시글·댓글·신고 |
| M1.5 | 익게 작성·댓글·신고·moderation | 뉴스와 추가 게시판 세부 기능 |

`M0`라고만 쓰면 위 세 단계를 묶은 전체 범위를 뜻한다. 첫 production 공개는 `M0 Core`를
완료 조건으로 하고 수집 보조와 자동 수집은 각각의 gate를 통과한 뒤 별도로 활성화한다. 이
문서에서 단계 표시가 없는 공개 짤 요구사항은 `M0 Core`에 속한다. M1·M1.5 제품 정책은
[회원·익게 제품 계약](08-member-community-plan.md), 상세 기술 계약은
[회원·익게 기술 설계](../system-design/06-member-community-design.md)를 따른다. 설계 기준선·구현 수용·
production 공개 승인은 [현행 설계 준비 상태](../system-design/design-readiness.md)에서 별도로 판정한다.

이 문서는 제품 요구사항이다. 구현 진척은 [요구사항 현황](../development-specs/requirements-status.md),
마지막 운영 관측은 [운영 현재 상태](../operations/current-status.md)를 따른다. 아래 개발 우선순위와
활성화 조건을 모두 미착수 또는 모두 충족한 상태로 해석하지 않는다.

## 2. 게시판과 URL

게시판 `slug`는 URL 첫 번째 경로로 사용한다.

| 공개 순서 | 표시명 | URL slug    | URL          | 작성 주체             |
| --------- | ------ | ----------- | ------------ | --------------------- |
| 초기      | 짤     | `meme`      | `/meme`      | 운영자                |
| 추후      | 익게   | `community` | `/community` | 사용자                |
| 추후      | 뉴스   | `news`      | `/news`      | 운영자 또는 추후 결정 |

- 초기 공개 게시판은 `짤` 하나다.
- `/` 요청은 `/meme`으로 리다이렉트한다.
- 초기 헤더에는 `짤`만 표시하거나 게시판 메뉴 자체를 생략할 수 있다.
- `익게`와 `뉴스`는 처음부터 빈 메뉴로 노출하지 않는다.
- 게시판은 앞으로 더 추가될 수 있다. 코드에 세 slug를 고정하지 않는다.
- 게시글은 한 게시판에 속하며 상세 URL은 `/:boardSlug/posts/:postId`를 사용한다. 요청 게시판과 게시글 소속이 다르면 공개하지 않는다.
- 게시판 문맥이 없는 `/posts/:postId` 별칭과 자동 redirect는 제공하지 않는다.

게시판은 데이터로 관리한다.

| 항목 | 설명 |
| --- | --- |
| URL slug | URL에 사용하는 고유 영문 값 |
| 표시명 | 화면 표시명 |
| 활성 여부 | 공개 메뉴와 작성 대상 활성화 여부 |
| 작성 정책 | `ADMIN`, `USER` 등 작성 주체 |
| 표시 순서 | 메뉴 표시 순서 |

### M1 회원과 소셜 로그인

- 가입·로그인 제공자는 네이버, 카카오, Google, Apple이다.
- 가입 완료 전에 소셜 제공자 동의와 별도로 블라리요 이용약관 동의와 회원가입 개인정보 수집·이용 동의를 받는다. 개인정보처리방침 전문도 확인할 수 있게 한다.
- 제공자별 고유 식별자를 연동 키로 사용하고 이메일을 회원 고유 키로 사용하지 않는다.
- 소셜 제공자에는 고유 식별자와 인증에 필요한 최소 권한만 요청한다. 이메일·이름·닉네임·사진·성별·생년월일·연령대·전화번호는 추가 요청하지 않는다.
- 서비스 표시명과 생년월일은 가입 화면에서 직접 입력받는다. 생년월일은 만 14세 이상 판정에만 사용하고 원문을 보관하지 않는다.
- 소셜 비밀번호는 받거나 저장하지 않는다.
- 로그인 access token은 처리 뒤 폐기한다. Apple refresh credential의 암호화 보관·철회 예외와 다른 제공자 재인증은 [회원 생명주기](08-member-community-plan.md#3-m1-계정-연결세션탈퇴)를 따른다.
- 계정 연결·해제, 로그아웃, 탈퇴를 제공한다. 탈퇴 시 회원·연동 정보를 삭제하고 제공자가 지원하는 범위에서 unlink/revoke를 호출한다.
- 초기 `짤/meme`의 작성 권한은 로그인 회원이 아니라 운영자에게만 있다. 소셜 계정 기반의 사용자 작성 기능은 `익게/community` 단계에서 추가한다.

## 3. 콘텐츠 운영

### 선별 기준

콘텐츠 선별 기준은 하나다.

> 관리자가 보기에 웃긴 것

별도의 점수표, 품질 등급, 반응 수 기준을 두지 않는다. 운영자가 직접 보고 게시 여부를 결정한다.

### 게시 빈도

- 하루 2회 게시한다.
- 1회당 10~20개를 게시한다.
- 하루 게시량은 20~40개다.
- 기본 예약 발행 운영 시각은 `07:30`, `17:30` KST(`Asia/Seoul`)로 둔다. 출근·등교 전후와
  퇴근·하교 전후에 게시 묶음을 제공하려는 기본값이며, 운영자는 게시글별로 다른 미래 시각을
  예약할 수 있다.
- 예약 발행은 운영자가 각 게시 묶음을 준비하는 용도로 사용할 수 있다.

### 출처

- 외부 콘텐츠는 출처명 전체를 원문 URL 링크로 표시하고 별도 `원문 보기` 버튼은 두지 않는다.
- 출처는 상세 본문이 끝난 뒤 한 번만 표시한다.
- 출처 표시는 콘텐츠 권리를 보유하거나 사용 허가를 받았다는 뜻이 아니다.
- 출처를 모르면 임의로 만들지 않고 `출처 확인 필요` 상태로 운영자에게 표시한다. 공개 여부는 관리자가 판단한다.

### 권리

- 블라리요는 게시 시점에 외부 콘텐츠의 권리 보유 여부를 확정하거나 보증하지 않는다.
- `권리 확인 완료`를 게시 조건으로 강제하지 않는다.
- 1차에서는 푸터의 이메일로 권리자 요청을 받고, 운영자가 메일을 확인하면 대상 게시글을 우선 숨긴다.
- 숨김 이후 관리자가 요청 내용과 출처를 다시 확인해 `재공개`, `수정`, `삭제` 중 하나를 결정한다.
- 내부 검토 내용은 공개 화면에 표시하지 않는다.

권리자 요청 상태 흐름은 다음과 같다.

```text
PUBLISHED
  -> HIDDEN_REVIEW
  -> PUBLISHED | REMOVED
```

## 4. 이미지 저장

- 외부 이미지는 블라리요가 사용하는 서버 측 저장소에 저장한다.
- 외부 원본 URL을 화면에서 직접 핫링크하지 않는다.
- DB에는 공개 URL 전체가 아니라 저장소 key 또는 상대 경로를 저장한다.
- M0 운영 저장소는 Cloudflare R2 Standard를 사용한다.

저장소 구현과 대체 후보는 다음과 같다.

- 기본: Cloudflare R2 Standard
- 장애·정책 변경 시 대안: Backblaze B2 또는 다른 S3 호환 오브젝트 스토리지
- 로컬 개발: 단일 서버 파일시스템 또는 테스트 bucket

애플리케이션은 저장소 구현에 직접 의존하지 않고 업로드, 조회 URL 생성, 삭제를 담당하는 저장소 인터페이스를 사용한다. R2를 M0 기본값으로 사용하되 사업자 교체가 데이터 모델과 게시글 API 변경으로 이어지지 않게 한다.

## 5. 공개 화면

### 짤 목록 `/meme`

- 최신순 게시판형 목록을 표시한다.
- 일반 목록 위에 고정 공지 0~3건을 표시할 수 있다.
- 고정 공지는 `공지` 배지로 구분하고 일반 게시글 20개와 광고 위치 산정에서 제외한다.
- 한 페이지에 게시글 20개를 표시한다.
- 후속 광고 기능을 활성화하면 광고 행은 게시글 20개에 포함하지 않는다. M0에는 광고 행을 렌더링하지 않는다.
- 행에는 번호, 제목, 조회 수, 작성자, 게시 시각을 표시한다.
- 초기에는 게시판이 하나이므로 각 행의 게시판명은 생략할 수 있다.
- 페이지 번호 방식으로 이동한다.

### 게시글 상세 `/:boardSlug/posts/:postId`

후속 광고 기능까지 활성화했을 때의 표시 순서는 다음과 같다. M0에서는 아래 광고 항목 5, 8, 9를 렌더링하지 않는다.

1. `← / 한 줄 제목 / 공유 아이콘` 상세 고정 헤더 (`←`, 공유 아이콘의 접근성 이름은 각각 `목록으로`, `공유하기`). M1부터 로그인·계정 진입을 추가한다.
2. 전체 제목과 게시 정보
3. 본문과 이미지
4. 출처명 원문 링크
5. 본문 하단 광고
6. 현재 글과 같은 게시판의 글 목록 20개
7. 상세 하단 목록 페이지네이션
8. 목록 중간 광고 1개
9. 목록 아래 광고 1개

- 출처는 하단에 한 번만 표시한다.
- 이전 글·다음 글 버튼은 두지 않는다.
- 하단 목록에는 현재 글을 포함하고 현재 행은 선택할 수 없게 표시한다.
- 상세 최초 진입 시 현재 글이 포함된 게시판 페이지를 선택 상태로 표시하고, 페이지 이동 시 본문은 유지한 채 하단 목록만 20개 단위로 교체한다.
- 숨김 또는 삭제된 게시글은 내용과 숨김 사유를 공개하지 않는다.
- M0는 게시글 API·HTML을 캐시하지 않는다. 숨김 commit 이후 시작된 조회에서 목록 제외·상세 404를 보장한다.
  이미 내려받은 콘텐츠는 회수할 수 없으며 공개 이미지 삭제·CDN 캐시 제거는 별도 비동기 완료로 추적한다.

### 운영자 화면 `/admin`

- `/admin` 계열은 M0의 비공개 운영자 화면이며 외부 관리자 인증을 통과한 운영자만 접근한다.
- 게시글 검색·작성·상태 관리는 `/admin`, 직접 수집 결과 검수·승인·초안 승격은 `/admin/batch`에서
  처리한다. `/admin/collect`와 `/admin/collect/sources`는 legacy 후보·출처 관리 경로이며 direct 설정을 변경하지 않는다.
- 화면 구성과 상태별 동작은 [03-screen-design.md](./03-screen-design.md), 접근 경계는 [02-infra-plan.md](./02-infra-plan.md)를 따른다.
- 관리자 화면은 검색 엔진과 공개 목록에 노출하지 않는다.

## 6. 후속 광고와 제휴

광고와 제휴는 M0 배포 범위가 아니다. 아래 계약은 기능을 활성화할 때 적용한다.

### 목록 광고

- 게시글 목록 중간에 광고 행 1개를 넣을 수 있다.
- 광고임을 명확하게 표시한다.
- 게시글 번호와 동일한 모양을 사용하지 않는다.

### 상세 광고

상세에서는 다음 세 위치만 사용한다.

| 슬롯                    | 위치                |
| ----------------------- | ------------------- |
| `AD-POST-BODY-BOTTOM`   | 본문과 출처 다음    |
| `AD-DETAIL-LIST-INLINE` | 상세 하단 목록 중간 |
| `AD-DETAIL-LIST-AFTER`  | 상세 하단 목록 아래 |

- 상세 상단, 우측, 전면형 광고는 두지 않는다. 광고 차단 해제 요청 modal은 광고 슬롯이 아니다.
- 광고 차단이 확인되면 화면 전체를 dim 처리하는 해제 요청 modal을 표시할 수 있다.
- modal이 열린 동안 배경 조작과 스크롤은 막지만 사용자가 닫으면 즉시 콘텐츠 열람을 계속할 수 있다.
- 사용자가 닫으면 같은 세션에서는 다시 자동 표시하지 않는다.
- 광고 로드 실패만으로 광고 차단 안내를 띄우지 않는다.

### 제휴

- 쿠팡 파트너스 같은 제휴 링크를 사용할 수 있다.
- 제휴 콘텐츠와 일반 게시글을 구분한다.
- 링크 가까이에 광고·제휴 사실과 수수료 수취 가능성을 표시한다.

## 8. 콘텐츠 수집

콘텐츠 수집은 `M0 Core` 이후 별도 활성화하는 `M0 수집 보조`와 `M0 자동 수집`이다. 수집이 중단돼도
운영자 수동 작성과 공개 목록·상세는 계속 동작해야 한다. 현행 경로는 별도 컴퓨터의 batch가 원문과
이미지를 수집 저장하고, API에서 검수→초안 승격→별도 발행하는 방식이다.
제품 정본은 [콘텐츠 수집 기획](./content-collection/README.md)이며 구현·로컬 검증·운영 활성화를 구분한다.

### 두 수집 경로

| 경로 | 시작과 저장 | 활성화 단계·기본값 |
| --- | --- | --- |
| Discord·운영자 URL 지정 | 상세 URL 한 건을 확인한 batch가 공통 상세 parser로 처리하고 수집 DB/object에 직접 저장한다. Web URL 입력의 direct 전달 계약은 `(미정)`이며 기존 URL 화면은 legacy 후보 방식이다 | `M0 수집 보조`, 단계 전 비활성 |
| 사용 결정 출처 목록 수집 | 허용된 HOT/GENERAL 목록에서 새 URL을 발견하고 같은 상세 처리·검수 경로로 연결한다. DETAIL_ONLY·차단 출처는 목록을 호출하지 않는다 | `M0 자동 수집`, 전역·출처별 기본 비활성 |

API·Web은 외부 원문을 fetch하지 않는다. batch는 글마다 API에 결과를 제출하지 않으며 content 게시글을
직접 발행하지 않는다. legacy candidate/preview 중계는 기존 호환 계약으로만 유지한다.

### 수집 출처 관리

출처별 parser 코드와 운영 설정은 분리한다. 현행 direct 실행기는 검토된 source 설정 파일을 읽고,
legacy 출처 수정 화면은 기존 후보 테이블을 변경한다. 그 화면의 변경이 direct batch에도 반영된다고
표시하지 않는다. Web 입력 전달·source 변경 권한·설정 버전 관리 방식은 P1-01의 별도 결정 사항이다.

| 항목 | 설명 |
| --- | --- |
| 출처 식별자·표시명·기준 URL | source별 parser와 운영 설정을 연결하는 정보 |
| 수집 방식 | `HOT_LIST`, `GENERAL_LIST`, `DETAIL_ONLY`, `BLOCKED`, `UNVERIFIED` |
| 목록 주소 | 목록 허용 source의 검증된 chart/list URL·탐색 범위 |
| 활성 여부·요청 간격·일일 상한 | 검증과 운영 사용 결정을 거친 출처별 제한 |
| robots 확인·이용약관 위험 판단 | 기술 gate와 운영 위험 근거, 확인일 |
| parser·설정 식별자·최근 결과 | 실제 적용 설정과 수집/실패 이력을 추적하는 근거 |

### 수집 규칙

- 원문 본문·이미지·첨부·SNS/외부 링크를 순서대로 보존한다. 제목·OG 이미지·요약만으로 수집 성공을 선언하지 않는다.
- 직접 수집 원본은 비공개 collect 저장소에, 검수 상태와 초안은 API 소유 영역에 둔다. API는 collect 원본을 다시 fetch하지 않는다.
- parser 결과에서 댓글·프로필·광고·스크립트를 제외한다. 수집 진단용 raw HTML 저장본과 파싱된 본문은
  다른 자료다. raw에 불필요한 정보가 들어가지 않았다고 가정하지 않으며 접근·보존·고지 정합성을 별도로 확인한다.
- 운영자는 수집 완료 건을 검수 시작→승인 또는 반려한다. 승인한 결과만 비공개 초안으로 만들고 발행은 별도 명령으로 수행한다.
- 이미지 검증·복사 중 누락이 생기면 일부 성공으로 승격하지 않는다. 첨부는 원문 링크로 표시하고 collect 파일 익명 다운로드는 열지 않는다.
- 동일 원문과 기존 게시글 중복·내용/검수 버전 충돌을 확인한다. 완료 건의 기본 재수집 정책은 skip이며 자동 승격하지 않는다.
- 로그인·CAPTCHA·유료 장벽·접근 차단을 우회하지 않는다. 허용 host·공인 주소·robots·요청 간격·상한·연락 수단을 확인한다.
- 위 통제는 요구사항이다. 현재 direct 경로에는 robots/Crawl-delay·영속 일일 총량 연결과 redirect 상한 차이가 남아 있다.
  [수집 기술 설계](../system-design/07-spring-collector-design.md)와 [P1-06](../roadmap.md)에서 추적하며, 목록·단건·queue 활성화 전에 검증한다.
- direct raw/media/report/queue의 보존 기간과 승격 후 원본 유지 여부는 `(미정)`이다. legacy metadata의 30일·preview 24시간을 자동 적용하지 않는다.
  현재 개인정보처리방침의 수집 설명과 실제 저장 범위·자동 파기를 맞추는 작업도 해당 수집 기능 활성화 전에 완료한다.
- 출처 표시는 권리 확보를 뜻하지 않으며 권리자 요청 처리 절차는 §3을 따른다.

### 수집 흐름

```text
확인된 상세 URL 또는 허용 목록에서 발견한 URL
  -> 별도 PC의 batch가 공통 상세 parser로 원문 수집
  -> 비공개 수집 DB/object에 본문·raw·이미지·첨부·보고서 저장
  -> 관리자 direct 검수 화면에서 원문·실패 이유·중복 확인
  -> 검수 시작 -> 승인 또는 반려
  -> 승인한 원문의 검증된 이미지 private 사본과 순서대로 된 본문을 초안으로 승격
  -> 게시글 편집 화면에서 확인 후 별도 즉시 또는 예약 발행
```

관리자 Web URL의 입력 전달 단계는 아직 연결 완료가 아니다. CLI/Discord 구현, 실제 Discord Gateway,
다른 PC·원격 DB/object 검증과 production 활성화는 각각 별도 증거로 확인한다.

## 9. 제품 데이터 요구사항

planning은 저장해야 할 정보와 제품 규칙만 정의한다. 테이블명·열·자료형·인덱스·migration은 [M0 데이터 모델](../system-design/02-data-model.md)의 책임이다.

| 제품 개념 | 필요한 정보와 규칙 |
| --- | --- |
| 게시판 | URL slug, 표시명, 활성 여부, 작성 주체, 표시 순서 |
| 게시글 | 게시판, 제목, 순서가 있는 텍스트·복수 이미지, 출처, 공지 순서, 발행 상태·시각 |
| 상태 이력 | 초안·예약·공개·숨김·삭제 전이와 행위자·사유 |
| 정책 | 유형별 전문, 버전, 시행·종료 시각과 개정 이력 |
| 게시글 조회 수 | 공개 상세 화면 표시 후 증가하는 참고용 누적값. 개인·세션 식별자와 원시 이용 이벤트는 저장하지 않음 |
| 수집 출처 | 표시명, 기준 URL, 수집 방식, 목록 주소, 활성 여부, 요청 간격·일일 상한, robots 확인 결과·확인일, 최근 수집 시각·오류 |
| 수집 결과·검수 | 출처·원문 URL·제목, 순서가 있는 본문·이미지·첨부/SNS 참조, 수집 상태·실패 이유·시각, 별도 검수 상태·버전·승격 게시글. raw·미디어·보고서의 비공개 보존 계약은 수집 기획을 따름 |

- 공개 게시글 상태는 `DRAFT`, `SCHEDULED`, `PUBLISHED`, `HIDDEN_REVIEW`, `REMOVED` 흐름으로 관리한다.
- 고정 공지는 게시판별 0~3건이고 일반 게시글 페이지 수에 포함하지 않는다.
- 공개 이미지에는 대체 텍스트가 필요하며 외부 원본 URL 대신 블라리요 저장소의 object를 사용한다.
- M1 회원·소셜 연동 데이터는 M0 schema에 미리 포함하지 않는다. [회원·익게 데이터 확장](../system-design/06-member-community-design.md#data)을 해당 단계 migration으로 적용한다.

## 10. 제품 API 요구사항

planning은 화면과 운영 흐름이 필요로 하는 동작만 정의한다. HTTP method, endpoint, request·response schema, 오류 코드는 [M0 API 설계](../system-design/03-api-design.md)의 책임이다.
아래 수집 요구사항은 `M0 Core`에 미리 노출하지 않고 수집 보조·자동 수집 단계에 맞춰 추가한다.

- 활성 게시판과 공개 게시글 목록을 조회할 수 있어야 한다.
- 목록은 고정 공지 0~3건과 일반 게시글 20건을 분리한다.
- 상세는 본문과 같은 게시판의 현재 목록 페이지·20개 목록을 함께 제공한다.
- 숨김·삭제·예약·초안 게시글은 공개 API에서 미존재와 구분하지 않는다.
- 운영자는 이미지를 staging하고 초안을 생성·수정하며 즉시 발행 또는 예약할 수 있어야 한다.
- 운영자는 게시글을 우선 숨긴 뒤 재공개 또는 최종 삭제할 수 있어야 한다.
- 운영자는 원문 URL을 지정해 후보를 만들고, 후보 목록을 검색·검수하며, 후보를 반려하거나 초안으로 승격할 수 있어야 한다.
- 수집 출처 목록을 조회하고 활성 여부·요청 간격을 조정할 수 있어야 한다.
- 수집 관련 동작은 모두 운영자 인증이 필요한 관리자 API이며 공개 API에 노출하지 않는다.
- M1 소셜 인증·회원 API는 M0 API에 포함하지 않는다.

## 11. 정책 화면

푸터에서 다음 정책을 modal로 열 수 있어야 한다. 직접 URL로 접근하면 같은 내용을 독립 화면으로 제공한다.

- 이용약관 `/terms`
- 개인정보처리방침 `/privacy`
- 쿠키 설정 `/cookie-settings`

- modal이 열린 동안 화면 전체를 dim 처리하고 배경 클릭과 스크롤을 막는다.
- 닫기, `Escape`, dialog 바깥 dim 영역 클릭으로 원래 화면에 돌아갈 수 있다.
- 이용약관과 개인정보처리방침은 현재 적용 버전의 전체 본문을 먼저 표시하고, 하단에 `버전, 적용 기간`만 가진 개정 이력을 둔다.
- 적용 기간은 현재 버전은 `yyyy.mm.dd ~ 시행 중`, 이전 버전은 `yyyy.mm.dd ~ yyyy.mm.dd`로 표시한다.
- 개정 이력 행 전체를 선택하면 같은 modal의 전체 본문을 해당 버전으로 교체한다.
- 시행 중인 버전과 과거 버전의 본문을 덮어쓰지 않고 각각 보관한다.
- 권리 침해·게시 중단 문의는 푸터의 `권리 문의`로 현재 화면 URL을 본문에 미리 넣은 이메일 작성
  화면을 연다. 별도 복사 버튼은 두지 않으며 전환 신호가 없으면 이메일 주소·제목·문의 양식을
  복사하고 alert로 알린다. 실행 성공·실패를 확정 판정하지 않으며 clipboard 거부 시 직접 복사를 지원한다.
  동작과 한계는 [화면 설계](./03-screen-design.md#권리-침해게시-중단-이메일)를 따른다.
- 요청 form, `/rights` 화면과 권리자 요청 API는 초기 범위에서 제외하고 필요성이 확인되면 후속 단계에서 검토한다.
- M0 Core에는 GA4 연동과 동의 제어를 구현하되 운영 기본값은 비활성으로 둔다. 운영 활성화 조건과
  비활성 기본값은 [분석·광고 계획 §2·§11](./04-analytics-ad-plan.md)을 따른다.
- GA4 또는 광고처럼 동의가 필요한 선택 기능을 실제 활성화한 환경에서만, 저장된 선택이 없는
  최초 접속에 화면 하단 비차단형 쿠키 배너를 표시한다.
- 하단 배너는 `필수만 사용`, `설정`, `모두 허용`을 제공하고 `설정`은 쿠키 설정 modal을 연다.
- 선택을 저장한 뒤에는 modal과 배너를 닫고 푸터의 쿠키 설정에서 언제든 다시 변경할 수 있다.
- 분석에 동의하기 전에는 Google tag를 로드하거나 GA4 요청을 보내지 않으며, 거부해도 콘텐츠를 계속 이용할 수 있다.
- 비활성 기능의 선택 항목은 노출하지 않고 사전 동의를 받지 않는다.

권리자 요청 메일을 확인한 운영자는 대상 게시글을 우선 숨긴 뒤 재공개·수정·삭제를 판단하고 처리 결과를 회신한다.

## 12. 추후 확장

### 익게 `/community`

- 표시명은 `익게`, URL slug는 `community`다.
- 사용자가 글을 작성하는 게시판이다.
- 소셜 계정 기반으로 작성자를 식별한다.
- 작성·댓글·신고·글별 익명성과 탈퇴 콘텐츠 처리는 [회원·익게 제품 계약](08-member-community-plan.md)을 따른다.

### 뉴스 `/news`

- 표시명은 `뉴스`, URL slug는 `news`다.
- 게시 주체, 출처 수집 방식, 노출 형식은 뉴스 게시판 개발 전에 별도 기획한다.

### 추가 게시판

- 게시판 데이터 추가로 확장한다.
- 새 게시판을 추가할 때 표시명, slug, 작성 주체만 우선 확정한다.
- 목록·상세·관리 기능은 게시판 slug를 기준으로 공통 처리한다.

## 13. 아직 미정인 항목

- 익게·뉴스의 공개 시점과 뉴스의 세부 기능. 익게 세부 기능은 [회원·익게 제품 계약](08-member-community-plan.md)을 따름
- 직접 입력 생년월일로 만 14세 이상을 판정하는 방식의 법무 적정성 검토 결과
- 소셜 제공자별 production application, callback URL과 동의 항목 검수 결과
- GA4 운영 활성화에 필요한 실값과 법무·CSP 조건은 [분석·광고 계획](./04-analytics-ad-plan.md)에서 추적
- 향후 추가 게시판의 이름과 운영 방식
- 수집 출처별 `robots.txt` 확인 결과, 이용약관 위험 판단과 `HOT_LIST`/`GENERAL_LIST`/`DETAIL_ONLY`/`BLOCKED`/`UNVERIFIED` 운영 정책. 출처별 명세의 개발 분류·예제 승인은 운영 승인과 구분한다.
- 수집 요청 User-Agent 문자열과 연락 수단
- 출처별 요청 간격과 일일 수집 상한 실제 값
- source별 batch 목록 수집 주기·페이지/글 상한·실패 중단 기준

미정 항목은 확정된 것처럼 문서나 코드에 넣지 않는다.

## 14. 단계별 개발 우선순위

### M0 Core

1. `/`에서 `/meme` 리다이렉트
2. 확장 가능한 게시판 구조와 `meme` 초기 데이터
3. 짤 목록 20개와 페이지네이션
4. 게시글 상세와 하단 목록 20개·페이지네이션
5. 관리자 초안·예약 발행 API
6. 외부 이미지 서버 저장 인터페이스
7. 출처 링크와 푸터 권리자 이메일, 운영자 수동 숨김 처리
8. 공유·OG와 정책 화면
9. 게시글 참고용 조회 수와 기본 비활성 GA4 연동·동의 차단 검수

### M0 수집 보조

1. 수집 출처 데이터와 Discord·운영자 URL 지정 단일 페이지 후보 생성
2. 후보 검수·반려·초안 승격과 중복 표시

### M0 자동 수집

1. 후속 단계로 분리. 출처별 명세의 사용 결정 뒤 출처 목록 수집 주기 실행과 차단·오류 대응

### M1

1. 네이버·카카오·Google·Apple 가입·로그인, 필수 동의와 재동의
2. 계정 연결·해제, 세션 종료·탈퇴와 외부 철회 실패 처리
3. [회원 기능 명세](../development-specs/m1/member-identity/member-identity.dev.md)와 [계정 생명주기 명세](../development-specs/m1/account-lifecycle/account-lifecycle.dev.md) 수용 검증

### M1.5

1. 글 단위 익명성을 적용한 텍스트 익게·댓글·본인 활동
2. 신고·운영자 숨김·삭제·제재와 탈퇴 콘텐츠 처리
3. [익게 기능 명세](../development-specs/m1-5/community-participation/community-participation.dev.md)와 [운영 관리 명세](../development-specs/m1-5/community-moderation/community-moderation.dev.md) 수용 검증

광고는 별도 활성화 조건을 따르며 M1·M1.5 완료를 위한 필수 기능으로 묶지 않는다.

`M0 Core` 초기 구현 완료 기준은 `짤 게시판에 운영자가 하루 두 번, 한 번에 10~20개를 올리고
사용자가 목록과 상세를 연속해서 볼 수 있는 상태`다. 수집 기능은 이 완료 기준을 대신하지 않는다.
GA4 운영 활성화 gate는 M0 Core 구현 완료와 분리하며, gate가 늦어지면 GA4와 선택 배너를 끈 채
게시글 조회 수만 운영한다.
