# Blariyo 화면 설계서

- 문서 상태: 화면·퍼블리싱 정정 정본
- 기준일: 2026-08-12
- 관련 문서: [01-service-plan.md](./01-service-plan.md), [02-infra-plan.md](./02-infra-plan.md), [04-analytics-ad-plan.md](./04-analytics-ad-plan.md), [05-benchmark-spec.md](./05-benchmark-spec.md), [06-copy-candidates.md](./06-copy-candidates.md)
- 서비스 명칭: `블라리요`
- 구현 대상: M0 반응형 웹과 M1 운영 자동화 후보
- 참고 산출물: 반응형 웹 정본 와이어프레임, 퍼블 프로토타입

## 1. 결론

이 문서는 M0 반응형 웹의 화면 정본이다. 와이어프레임과 퍼블 프로토타입은 이 문서의 IA, 목록 개수, 상세 탐색, 광고, 상태, 접근성, 공유·SEO 계약을 따라야 한다.

기존 M0 화면 방향은 공개 홈 피드와 게시글 상세 두 화면으로 제한한다. 로딩, 빈 목록, 오류, 숨김 게시글은 별도 페이지가 아니라 두 화면의 상태로 처리한다.

```text
홈 피드 -> 게시글 상세 -> 하단 목록 -> 게시글 상세
```

관리자 전용 화면과 네이티브 앱은 M0에서 만들지 않는다. 관리자는 보호된 API와 Swagger를 사용한다. 현재 화면 검토 대상은 하나의 반응형 웹이다. 데스크톱과 모바일은 별도 제품이 아니라 같은 URL과 같은 컴포넌트가 다른 폭에서 보이는 상태다.

M1의 댓글과 M1.5의 승인형 제보 화면은 확장 기준만 미리 정의한다. M0 성공 조건과 각 단계의 운영 게이트를 통과하기 전에는 구현하지 않는다.

## 2. 벤치마킹 반영

2026-08-11 기준 고급유머의 공개 검색 노출, 상품형 게시물 페이지, 앱 마켓 설명을 기준으로 다음 구조를 확인했다.

- 첫 화면에서 최신 콘텐츠 목록을 바로 노출한다.
- 제목, 작성 주체, 번호, 게시 시각을 한 행에 밀도 있게 배치한다.
- 게시글 목록 중간에 광고 행을 삽입해도 목록 구조가 유지된다.
- 상단 메뉴를 적게 유지한다.
- 페이지 번호 방식으로 다음 목록을 탐색한다.
- 게시글 상세를 독립 URL로 제공한다.
- 상품형 게시물과 일반 유머 피드를 분리해 광고성/제휴성 콘텐츠를 구분한다.
- 상세 화면은 제목, 번호, 작성 주체, 날짜, 반응, 본문, 하단 출처, 본문 하단 광고, 하단 목록이 세로로 이어지는 게시판 구조다.
- 광고 차단 사용자를 위한 해제 요청 안내를 제공한다.
- 앱에서는 광고 포함, 앱 내 구입, 광고 제거 구독이 존재한다.

Blariyo에는 다음과 같이 변형한다.

### 가져올 것

- 최신순 피드를 첫 화면의 주 기능으로 둔다.
- 게시판형 목록에서 게시판, 제목, 번호, 조회 수, 게시 시각으로 내용을 빠르게 판단하게 한다.
- 상세 하단에 같은 게시판의 현재 글 주변 20개 목록을 제공해 뒤로 가기 없이 다른 글을 고르게 한다.
- 페이지네이션으로 현재 위치와 뒤로 가기 동작을 보존한다.
- 브랜드 헤더와 콘텐츠 영역의 구조를 단순하게 유지한다.
- 광고 또는 제휴성 콘텐츠는 일반 게시글과 혼동되지 않게 분리한다.
- 상품형 게시글에는 본문 상단에 제휴 링크 CTA를 두고, 별도 제휴 목록에서는 상품 번호, 제목, 자료보기 링크를 제공한다.

### 가져오지 않을 것

- 댓글 수와 반응 수 경쟁
- 광고를 초기 핵심 기능처럼 전면 배치하는 구조
- 글쓰기, 마이페이지, 로그인 메뉴
- 실시간 이슈와 검색
- 블로그형 카드 피드와 히어로 이미지 중심 상세

## 4. 공통 레이아웃

### 헤더

- 왼쪽에 텍스트 로고 `블라리요`를 배치한다.
- 게시판 메뉴는 `유머`, `이야기` 2개만 표시한다.
- `/`는 두 게시판의 최신 글을 섞은 루트 목록이지만 `최신` 같은 세 번째 메뉴를 만들지 않는다. 루트에서는 두 게시판 메뉴 모두 비활성 상태다.
- `/boards/humor`와 `/boards/talk`에서는 해당 게시판 메뉴 하나만 활성화하고 `aria-current="page"`를 부여한다.
- 상세에서는 뒤로 가기 버튼, 로고, 공유 버튼을 표시한다.
- 로그인, 검색, 글쓰기, 알림 버튼은 표시하지 않는다.
- 데스크톱 헤더 높이는 64px, 모바일은 56px를 기준으로 한다.
- 스크롤 시 모바일 헤더를 상단에 고정한다.

### 콘텐츠 폭

| 구간 | viewport | 콘텐츠 기준 |
| --- | --- | --- |
| Mobile | `360~767px` | 좌우 16px, 단일 열 |
| Tablet | `768~1023px` | 최대 720px, 단일 열 |
| Desktop | `1024px 이상` | 페이지 최대 1120px, 본문 760px + 보조 영역 280px |

- 상세 본문은 데스크톱에서도 최대 760px를 넘기지 않는다.
- 보조 영역은 운영 연락처와 최신 게시물 요약만 제공한다.
- 태블릿에서는 보조 영역을 본문 아래로 이동한다.
- 모바일에서는 보조 영역을 숨기고 본문, 목록, 페이지 이동만 남긴다.

### 모바일 단순화 원칙

모바일은 고급유머처럼 게시판 목록 소비에 집중한다. 작은 화면에서는 설명형 영역을 과감히 줄이고 `로고`, `게시판 2개`, `게시글 목록`, `페이지네이션`만 먼저 보이게 한다.

- 홈에서는 상단 안내 strip, 벤치마킹 설명, 보조 영역, 우측 광고 후보를 노출하지 않는다.
- 홈 목록 행은 `번호`, `제목`, `시간`만 남기고 게시판명, 작성자, 조회 수는 숨긴다.
- 게시글 사이 광고 행은 유지하되 높이를 낮추고 목록 일부처럼 흐름 안에 배치한다.
- 상세에서는 제목, 메타, 본문, 하단 출처, 하단 목록을 우선한다.
- 상세 공유 메뉴는 기본 노출하지 않고 헤더의 공유 버튼에서 열린다.
- 제휴 CTA와 광고 차단 안내는 모바일에서 본문을 밀어내지 않도록 짧은 안내 블록으로만 검토한다.

### 푸터

- 권리자 삭제 요청 연락처를 항상 확인할 수 있게 한다.
- 이용약관 `/terms`, 개인정보처리방침 `/privacy`, 권리자 요청 `/rights`, 쿠키 설정 `/cookie-settings`의 실제 route 링크를 둔다.
- M0에서 불필요한 회사 정보와 사이트맵은 추가하지 않는다.

## 5. 홈 피드

### 목적

사용자가 진입 후 3초 안에 볼 콘텐츠를 선택하고 상세로 이동하게 한다.

### 구성 순서

1. 헤더
2. 페이지 제목 `오늘 올라온 웃긴 것`
3. 최신순 표시와 현재 게시물 수
4. 게시글 목록
5. 페이지네이션
6. 권리자 요청 푸터

홈 목록은 페이지당 게시글 20개를 표시한다. 광고 행은 게시글 20개 산정에서 제외한다.

### IA와 route

| Route | 목록 범위 | 활성 메뉴 | API 필터 |
| --- | --- | --- | --- |
| `/` | `유머`와 `이야기` 혼합 최신 20개 | 없음 | `board` 생략 |
| `/boards/humor` | `유머` 최신 20개 | 유머 | `board=HUMOR` |
| `/boards/talk` | `이야기` 최신 20개 | 이야기 | `board=TALK` |

루트 혼합 목록은 별도 게시판이 아니며 게시글의 실제 게시판 값은 항상 `HUMOR` 또는 `TALK`다.

### 피드 항목

| 요소 | 규칙 |
| --- | --- |
| 번호 | 게시글 번호. 데스크톱과 모바일 모두 노출 |
| 게시판 | `유머`, `이야기` 중 하나. 추가 게시판은 만들지 않음 |
| 제목 | 한 줄 말줄임. 목록에서는 본문 요약을 노출하지 않음 |
| 게시 시각 | 오늘이면 `14:30`, 이전이면 `8월 5일` |
| 조회 수 | 목록과 상세에 모두 노출 |
| 작성자 | M0에서는 `운영자` 또는 `블라리요 편집부`로 고정 |
| 클릭 영역 | 게시글 행. 새 창을 강제하지 않음 |

홈 목록은 이미지 카드가 아니라 게시판형 행 목록을 기본으로 한다. 대표 이미지는 상세 본문과 SNS 공유 이미지에 집중한다. 외부 원본 이미지를 직접 핫링크하지 않는다.

### 홈 목록 광고 행

- 게시글 목록 중간에 광고 행을 1개 삽입할 수 있게 자리와 스타일을 미리 정의한다.
- 첫 번째 게시글 전에는 광고를 넣지 않는다.
- 기본 후보 위치는 4~6번째 게시글 이후다. 모바일은 4번째 이후, 데스크톱은 목록 밀도에 따라 4번째 또는 6번째 이후로 조정한다.
- 광고 행은 게시글 번호, 작성자, 조회 수를 갖지 않는다.
- 광고 행은 `광고` 표기, 별도 배경, 별도 높이로 게시글과 즉시 구분되게 한다.
- 광고 로드 실패 시 해당 행을 접고 목록 간격만 정상 유지한다.

### 페이지네이션

- `이전`, 현재 페이지 주변 최대 5개 번호, `다음`을 표시한다.
- 첫 페이지의 `이전`, 마지막 페이지의 `다음`은 disabled 처리한다.
- 페이지 이동 후 목록 제목으로 스크롤하고 초점을 이동한다.
- 무한 스크롤과 자동 추가 로딩은 사용하지 않는다.

### API 연결

```text
GET /api/v1/posts?page=1&size=20
```

게시판 route는 같은 endpoint에 `board=HUMOR|TALK`만 추가한다.

| UI | 응답 필드 |
| --- | --- |
| 상세 URL | `postNo` |
| 번호 | `postNo` |
| 제목 | `title` |
| 게시판 | `boardName` |
| 게시 시각 | `publishedAt` |
| 조회 수 | `viewCount` |
| 작성자 | `authorName` 또는 고정 문구 |
| 현재 페이지 | `page` |
| 페이지 수 | `totalPages` |

## 6. 게시글 상세

### 목적

본문을 방해 없이 소비하고 하단 목록에서 다음 콘텐츠를 선택하게 한다.

### 구성 순서

1. 뒤로 가기와 공유가 있는 헤더
2. 게시판
3. 제목
4. 게시 시각과 조회 수
5. 본문 텍스트와 이미지
6. 출처 정보
7. 상세 본문 하단 광고 후보
8. 같은 게시판의 현재 글 주변 20개 목록
9. 하단 목록 중간 광고 후보
10. 하단 목록 아래 광고 후보
11. 권리자 요청 푸터

### 본문 규칙

- 제목은 줄 수를 제한하지 않되 긴 단어가 화면을 넘지 않게 줄바꿈한다.
- 본문 기본 글자 크기는 모바일 17px, 데스크톱 18px를 기준으로 한다.
- 이미지 원본 비율을 유지하고 본문 폭보다 크게 표시하지 않는다.
- 이미지에 대체 텍스트를 제공한다.
- 이미지 로딩 전 비율 공간을 확보해 레이아웃 이동을 막는다.
- 외부 링크는 출처 영역에서만 새 창으로 연다.
- 영상, GIF, 임베드 콘텐츠는 M0에서 렌더링하지 않는다.

### 출처 영역

- `EXTERNAL`은 `출처`, 원본 사이트 이름, 원본 링크를 표시한다.
- `ORIGINAL`은 `블라리요 자체 제작` 또는 제작 주체만 표시하고 외부 링크를 만들지 않는다.
- 권리 상태나 내부 검수 메모는 사용자 화면에 표시하지 않는다.
- `EXTERNAL`인데 출처 링크가 없으면 게시물을 발행할 수 없다.

### 상세 하단 목록

- 상세 본문을 다 읽은 직후 현재 글과 같은 게시판의 현재 글 주변 목록을 게시판형으로 표시한다.
- 표시 항목은 번호, 게시판, 제목, 조회 수, 게시 시각이다.
- 상세 하단 목록은 데스크톱과 모바일 모두 게시글 20개를 표시하고 광고 행은 20개 산정에서 제외한다.
- 현재 보고 있는 글을 20개 안에 반드시 포함하고 시각적으로 강조한다. 현재 글 행에는 `aria-current="true"`, `aria-disabled="true"`를 부여하고 링크와 키보드 tab stop을 만들지 않는다.
- 정렬은 `publishedAt DESC, postNo DESC`다. 현재 글 앞뒤를 우선 채우고 첫·마지막 경계에서는 존재하는 방향의 글로 보충해 총 20개를 맞춘다. 같은 게시판 공개 글이 20개 미만이면 존재하는 글만 표시한다.
- 하단 목록에는 페이지네이션을 두지 않는다. 게시판 전체 목록으로 이동하는 `목록으로` 링크만 제공한다.
- 댓글이 없는 M0에서는 하단 목록이 연속 소비의 핵심 장치다.
- 별도 이전 글·다음 글 버튼은 두지 않는다.
- 하단 목록 안에는 광고 행을 1개까지 넣을 수 있다.
- 하단 목록 아래에는 광고 후보를 1개까지 둘 수 있다.

### API 연결

```text
GET /api/v1/posts/:postNo
GET /api/v1/posts/:postNo/context?size=20
```

| UI | 응답 필드 |
| --- | --- |
| 제목 | `title` |
| 게시판 | `boardName` |
| 본문 | `content` |
| 본문 이미지 | `imageUrl`, `imageAlt` |
| 게시 시각 | `publishedAt` |
| 조회 수 | `viewCount` |
| 출처 이름 | `sourceName` |
| 원본 유형 | `sourceType` |
| 출처 URL | `sourceUrl`, `ORIGINAL`이면 `null` |
| 하단 목록 | `contextPosts[]` — 같은 `boardCode`, 현재 글 포함, 최대 20개 |

## 7. 화면 상태

### 로딩

- 최초 진입 시 제목과 이미지 비율을 보존한 skeleton을 표시한다.
- 화면을 덮는 spinner 하나만 표시하지 않는다.
- 페이지 이동 중 기존 목록을 즉시 비우지 않는다.

### 빈 목록

- `아직 올라온 글이 없습니다`와 홈 새로고침 버튼을 표시한다.
- 검색 조건 안내는 검색 기능이 없으므로 표시하지 않는다.

### 오류

- 네트워크 또는 서버 오류 메시지와 `다시 시도` 버튼을 표시한다.
- 기술 오류 문자열과 stack trace를 노출하지 않는다.
- 반복 실패 시 홈 이동 링크를 함께 제공한다.

### 없음·숨김 게시글

- 존재하지 않음과 운영자 숨김을 사용자에게 같은 화면으로 처리한다.
- `볼 수 없는 게시글입니다`와 홈 이동 버튼을 표시한다.
- 삭제·제재 사유와 관리자 정보를 노출하지 않는다.

## 8. M1 댓글과 인증

### 로그인과 회원가입

- 로그인은 이메일과 비밀번호만 받는다.
- 회원가입은 이메일, 비밀번호, 닉네임, 필수 약관 동의를 받는다.
- 회원가입 완료 후 이메일 인증을 마쳐야 댓글, 좋아요, 신고 기능을 사용할 수 있다.
- 비밀번호 분실 화면은 이메일 입력만 받고, 계정 존재 여부와 무관하게 같은 완료 문구를 표시한다.
- 재설정 링크는 일회용·만료형 토큰을 사용하며 완료 후 모든 기존 Refresh Token을 폐기한다.
- 로그인 성공 후 원래 보던 게시글로 돌아간다.
- 비로그인 사용자가 댓글 입력을 누르면 로그인 화면으로 이동한다.
- 로그인 이동 전 작성 중인 댓글은 `sessionStorage`에 임시 보관하고 등록 또는 탭 종료 후 제거한다.
- OAuth, 소셜 프로필, 비밀번호 없는 로그인은 제공하지 않는다.

### 계정 관리

- `/me/account`에서 이메일 인증 상태, 닉네임 변경, 전체 로그아웃, 회원 탈퇴를 제공한다.
- 탈퇴 확인에는 비밀번호 재입력과 처리 결과 안내를 둔다.
- 탈퇴 즉시 로그인을 차단하고 댓글 작성자 표시는 비식별 처리한다. 법적 보존 대상과 삭제 일정은 M1 공개 전 정책 문서에 확정한다.

### 상세 댓글 영역

게시글 상세의 하단 목록 위 또는 아래에 댓글 영역을 추가한다.

1. 댓글 수와 정렬 기준
2. 로그인 사용자 댓글 입력
3. 최신순 댓글 목록
4. 본인 삭제 버튼
5. 다른 사용자 댓글 신고 메뉴
6. 다음 댓글 페이지

- 대댓글 들여쓰기와 댓글 좋아요는 표시하지 않는다.
- 댓글 입력은 최대 500자이며 남은 글자 수를 표시한다.
- 외부 링크와 연락처로 판단되는 입력은 제출 전에 경고한다.
- 숨김 댓글은 원문 대신 `운영 정책에 따라 숨겨진 댓글입니다`를 표시한다.
- 삭제된 댓글은 목록에서 제거하고 자리표시자를 남기지 않는다.
- 댓글 목록은 한 번에 20개씩 페이지네이션한다.
- 신고 메뉴는 사유 선택 후 확인하는 두 단계로 처리한다.

### 관리자 화면

- 게시글 관리와 신고 관리는 별도 route를 사용하되 공통 관리자 layout을 공유한다.
- 목록, 필터, 상세 drawer 또는 본문 영역으로 구성한다.
- 자동 숨김 버튼은 제공하지 않고 관리자가 처리 결과를 확정한다.
- 모바일 운영은 조회와 긴급 숨김만 지원하고 복잡한 수정은 데스크톱을 기준으로 한다.

### M1 운영 자동화 후보

- 자동 수집은 M1의 운영 자동화 후보이며 공개 화면 기능이 아니다.
- 수집 결과는 공개 게시글 테이블이 아닌 접근 제한 임시 큐에만 저장한다.
- 큐 항목은 운영자가 출처·본문·이미지·권리를 검수한 뒤 초안으로 전환할 수 있다.
- 초안 전환과 최종 발행은 분리하며, 최종 발행은 운영자의 명시적 수동 동작만 허용한다.
- 예약 작업, worker, 재시도 로직을 포함해 어떤 경로에서도 자동 최종 발행하지 않는다.

## 9. M1.5 승인형 제보

### 제보 작성

| 입력 | 규칙 |
| --- | --- |
| 제목 | 필수, 최대 100자 |
| 본문 | 필수, 최대 5,000자 |
| 대표 이미지 | 선택, 1개, `jpg/png/webp`, 최대 5MB |
| 원본 유형 | 필수, `직접 제작` 또는 `외부 콘텐츠` |
| 출처 이름 | 외부 콘텐츠일 때 필수, 최대 100자 |
| 출처 URL | 외부 콘텐츠일 때 필수, `https` URL |
| 권리 확인 | 필수 체크, 직접 제작 또는 사용 허가 보유 확인 |

- 제출 전에 입력 내용과 이미지를 미리 보여준다.
- 제출 후 접수 번호와 `검수 대기` 상태를 표시한다.
- 임시 저장과 여러 이미지 정렬은 제공하지 않는다.
- 사용자당 하루 1건 또는 전체 주 5건 제한에 도달하면 제출 버튼을 비활성화하고 재개 시점을 표시한다.
- 검수 대기가 5건 이상이거나 가장 오래된 대기 건이 36시간을 넘으면 신규 접수를 일시 중단한다.
- 검수 전 이미지는 공개 URL로 제공하지 않고 인증된 관리자 검수 화면에서만 표시한다.

### 내 제보

- 접수일, 제목, `PENDING/APPROVED/REJECTED/WITHDRAWN` 상태를 표시한다.
- 반려 건에는 사용자에게 공개 가능한 반려 사유만 표시한다.
- `PENDING` 상태에서만 철회할 수 있다.
- 승인 건은 발행된 게시글 상세로 이동한다.
- 제보 수정 대신 철회 후 새 제보 작성을 사용한다.

### 관리자 제보 검수

- 기본 목록은 오래된 `PENDING` 순서다.
- 제출자, 제목, 접수 시각, 대기 시간을 표시한다.
- 검수 상세에서 본문, 이미지, 출처 링크, 권리 확인 여부를 함께 본다.
- 승인은 발행 게시판와 발행 시각을 입력한 뒤 한 번 더 확인한다.
- 반려는 사유 코드를 선택하고 사용자용 메시지와 관리자 내부 메모를 분리해 입력한다.
- 처리 완료 버튼은 중복 클릭을 막고 처리 중 상태를 표시한다.
- 이미 처리된 제보를 다시 열면 읽기 전용 결과를 표시한다.

## 10. 분석 동의와 광고 확장

광고는 개발 후 덧붙이는 부가 요소가 아니다. 본문 폭, 상세 하단 여백, 하단 목록 위치, 동의 UI, CLS 방지까지 화면 기획에서 먼저 반영한다. 실제 광고 실행은 트래픽 게이트 이후지만, 광고가 들어갈 수 없는 화면과 들어갈 수 있는 자리는 기획 단계에서 확정한다.

### 분석 동의

- 첫 방문 시 화면 하단에 콘텐츠를 가리지 않는 동의 bar를 표시한다.
- 명령은 `필수만`, `분석 허용`, `설정`으로 제공한다.
- 동의 선택 전에도 홈과 상세를 바로 사용할 수 있어야 한다.
- 푸터의 `쿠키 설정`에서 분석·광고 선택을 다시 열 수 있게 한다.
- 동의 bar를 modal로 만들거나 동의할 때까지 스크롤을 막지 않는다.

### 상세 배너

| ID | 위치 | 화면 규칙 |
| --- | --- | --- |
| `AD-POST-BODY-BOTTOM` | 본문과 출처 다음 | 본문 소비가 끝난 뒤 노출되는 상세 본문 하단 광고 |
| `AD-DETAIL-LIST-INLINE` | 상세 하단 목록 중간 | 하단 목록 안에 끼워 넣는 광고 행. 게시글 행과 구분 |
| `AD-DETAIL-LIST-AFTER` | 상세 하단 목록 아래 | 목록 탐색 이후 노출되는 하단 광고 |
- 상세 상단에는 광고를 두지 않는다.
- 상세 광고 슬롯은 위 3개만 허용한다. 우측 광고, 이전·다음 사이 광고, 전면형 광고는 상세 route에 두지 않는다.
- 광고 크기만큼 공간을 예약해 로딩 중 본문과 하단 목록이 밀리지 않게 한다.
- 광고가 채워지지 않으면 예약 공간을 접는다.
- 광고를 게시글 카드, 출처, 하단 목록 행과 같은 모양으로 만들지 않는다.
- 로그인, 회원가입, 제보, 관리자, 오류, 404 화면에는 광고를 넣지 않는다.

### 광고 차단 해제 요청

- 광고 차단이 확정된 경우에만 표시한다. timeout, no-fill, 네트워크 오류 같은 일반 광고 로드 실패에는 안내를 표시하지 않고 슬롯만 접는다.
- 본문 열람, 목록 이동, 공유, 출처 링크를 막지 않는다.
- 기본 위치는 상세 하단 목록 위다. 상세 route에서는 별도 우측 안내나 전면 안내를 두지 않는다.
- 문구는 `블라리요 운영을 위해 광고 차단 해제를 부탁드립니다` 수준으로 짧게 유지한다.
- 버튼은 `계속 보기`, `해제 방법`, `다시 확인`만 제공한다.
- 사용자가 `계속 보기`를 누르면 같은 세션에서는 다시 표시하지 않는다.
- 해제 방법은 브라우저별 긴 설명을 본문에 넣지 않고 별도 도움말 화면 후보로 분리한다.

### 홈 광고 후보

홈 피드 중간 광고는 목록 안에 들어가는 별도 행으로 설계한다. 첫 게시글 전에는 배치하지 않고, 사용자가 몇 개의 게시글을 본 뒤 자연스럽게 지나칠 수 있는 위치에만 둔다.

| 후보 | 위치 | 판단 |
| --- | --- | --- |
| `AD-FEED-INLINE` | 네 번째~여섯 번째 게시글 다음 | 게시글 행과 구분되는 목록 중간 광고 행 |
| `AD-SIDE-RAIL` | 데스크톱 보조 영역 | 모바일에는 노출하지 않는 조건으로 검토 |

홈의 브랜드와 첫 게시글 사이에는 광고를 넣지 않는다.

### 제휴 상품형 콘텐츠

제휴 상품은 일반 유머 피드와 분리한다. Goodgag의 `/pr`처럼 상품형 게시물 모음과 원본 자료 보기를 분리하되, 블라리요에서는 다음 규칙을 둔다.

| 화면 | 경로 후보 | 구성 |
| --- | --- | --- |
| 제휴 상품 목록 | `/partners` | 상품 번호, 제목, 제휴 링크, 자료보기 링크, 수수료 고지 |
| 상품형 게시글 상세 | `/posts/:postNo` | 본문 상단 `상품링크 보기`, 제휴 고지, 원문 출처, 하단 목록 |

- 제휴 링크는 외부 쇼핑몰로 이동한다는 점을 버튼 문구에 드러낸다.
- 수수료 고지는 목록 상단과 상세 CTA 주변에 모두 표시한다.
- 제휴 상품형 게시글도 `유머` 또는 `이야기` 게시판 중 하나에 속하되, 화면에는 `제휴` 배지를 별도로 표시한다.
- 제휴 목록은 M0 기본 내비게이션에 넣지 않고, 광고 실행 게이트 이후 노출한다.
- 제휴 링크 클릭 이벤트는 `affiliate_click`으로 별도 기록한다.

| 동작 | 이벤트 |

| 피드 항목 선택 | `select_content` |
| 상세 15초 체류 또는 본문 50% 도달 | `post_engagement` |
| 하단 목록 글 선택 | `bottom_list_post_click` |

| 제휴 링크 선택 | `affiliate_click` |
| 광고 노출 후보·성공·닫기 | 내부 진단 이벤트, GA4에는 광고 원문 없이 상태만 전달 |

## 11. 상호작용과 접근성

- 모든 링크와 버튼은 키보드로 접근 가능해야 한다.
- 포커스 표시를 제거하지 않는다.
- 터치 대상은 최소 `44 x 44px`로 만든다.
- 텍스트와 배경의 명도 대비를 확보한다.
- 장식 목적이 아닌 모든 이미지에 대체 텍스트를 넣는다.
- 현재 페이지는 `aria-current="page"`로 표시한다.
- 오류 메시지는 다시 시도할 수 있는 명령과 함께 제공한다.
- 애니메이션은 200ms 이하의 상태 전환에만 사용한다.
- 게시글 행은 실제 `<a href="/posts/:postNo">`를 사용한다. `div`에 Enter 처리만 덧붙이는 방식은 사용하지 않는다.
- 공유 버튼은 `aria-expanded`와 `aria-controls`를 갱신한다. 메뉴가 열리면 첫 메뉴 항목으로 초점을 보내고 `Escape` 또는 바깥 클릭으로 닫은 뒤 공유 버튼으로 초점을 돌린다.
- 공유 메뉴 항목은 링크 복사, 카카오톡, X, 브라우저 공유 순서다. 실행 결과와 실패는 `aria-live="polite"`로 알린다.
- 검토용 화면 tab은 `role="tablist"`, `role="tab"`, `aria-selected`, roving `tabindex`를 사용하고 좌우 방향키·Home·End를 지원한다.
- 페이지 이동 후 목록 제목에 `tabindex="-1"`로 초점을 보내며, `prefers-reduced-motion`에서는 부드러운 스크롤을 사용하지 않는다.

## 12. SEO와 공유

### 홈

- Title: 카피 확정 전까지 [06-copy-candidates.md](./06-copy-candidates.md)의 후보로 관리
- Description: 최신 유머를 운영자가 골라 보여주는 피드
- Canonical: 서비스 루트 URL

### 상세

- Title: `{게시글 제목} | 블라리요`
- Description: 본문 앞부분을 100~140자로 정리
- Open Graph image: 대표 이미지
- Canonical: `/posts/:postNo`
- 공유 버튼은 상세 헤더 우측에 둔다.
- 모바일에서는 `navigator.share`를 우선 사용하고, 실패하면 링크 복사·카카오톡·X/Twitter 공유 메뉴를 표시한다.
- 데스크톱에서는 공유 버튼 클릭 시 링크 복사·카카오톡·X/Twitter 공유 메뉴를 표시한다.
- 카카오톡 공유와 SNS 미리보기는 `og:title`, `og:description`, `og:image`, `og:url`을 기준으로 생성한다.
- X/Twitter 공유는 `twitter:card=summary_large_image`와 게시글별 title, description, image를 사용한다.
- 공유 이미지는 absolute HTTPS URL, 1200 x 630, 5MB 이하를 기준으로 한다.

### 정적 퍼블 한계와 실제 SSR route 계약

- `docs/publishing/responsive/index.html`은 한 HTML 안에서 화면을 전환하는 정적 검토물이라 초기 `<head>`의 홈 metadata만 표현한다. JavaScript로 화면을 바꿔도 SNS crawler에 게시글별 OG를 보장할 수 없다.
- 실제 서비스의 `GET /posts/:postNo`는 서버가 게시글을 조회한 뒤 첫 HTML 응답에 게시글별 `<title>`, description, canonical, `og:type=article`, `og:title`, `og:description`, `og:url`, `og:image`, `og:image:alt`, Twitter card·image·alt를 렌더링한다.
- 공개 게시글은 HTTP `200`, 존재하지 않거나 숨김 처리된 게시글은 HTTP `404`와 `noindex`를 반환한다. 숨김 route의 응답에 제목, 본문, 이미지, 내부 `rightsStatus`를 넣지 않는다.
- `/`, `/boards/humor`, `/boards/talk`, `/terms`, `/privacy`, `/rights`, `/cookie-settings`도 각 canonical을 가진 서버 응답 HTML을 제공한다.
- hydration 이후 route를 이동하더라도 위 SSR 응답 계약을 대체하지 않는다. 공유 URL은 hash가 없는 absolute HTTPS `/posts/:postNo`다.

숨김 또는 없는 게시글은 `404` 상태 코드와 `noindex`를 사용한다.

## 13. 앱 보류

현재 기획과 와이어프레임 검토 대상에서 앱은 제외한다. 데스크톱 웹과 모바일 웹에서 홈 피드, 상세, 상태, 광고 후보, 동의 UX를 먼저 확정한다. 앱 설치 요구가 실제 사용자 행동으로 확인되기 전까지 앱 정보 구조, 네이티브 광고, 푸시, 오프라인 저장은 설계하지 않는다.

## 16. 구현 완료 조건

### M0

- 홈과 상세가 `360px`, `768px`, `1280px`에서 가로 스크롤 없이 보인다.
- 긴 제목과 긴 출처 URL이 컨테이너를 넘지 않는다.
- 이미지 로딩 실패 시 대체 정보가 남는다.
- 로딩, 빈 목록, 오류, 숨김 상태가 구현된다.
- 키보드만으로 피드, 페이지네이션, 상세 이동이 가능하다.
- 키보드와 터치로 공유 메뉴를 열고 실행하고 닫을 수 있다.
- 홈과 상세의 SEO metadata가 실제 SSR route별 첫 HTML 응답에 생성된다.
- 모바일에서 고정 헤더가 본문을 가리지 않는다.
- Lighthouse 접근성 검사의 주요 오류가 없다.
- route 이동마다 GA4 `page_view`가 한 번만 발생하고 분석 거부 시 Google tag를 로드하지 않는다.

### M1

- 로그인 후 원래 게시글과 작성 중이던 댓글로 복귀한다.
- 댓글 0개, 1개, 20개 초과 상태가 레이아웃을 깨지 않는다.
- 본인 삭제와 타인 신고 권한이 화면과 API에서 일치한다.
- 숨김 댓글과 삭제 댓글 표시 규칙이 운영 정책과 일치한다.

### M1.5

- 파일 형식, 5MB 제한, 사용자당 하루 1건·전체 주 5건 제한을 화면과 API가 함께 검증한다.
- 제보 상태별로 가능한 명령이 정확히 제한된다.
- 승인 중복 요청이 게시글을 두 개 만들지 않는다.
- 반려·철회 이미지는 운영 저장소에서 7일, 암호화 백업에서 최대 28일 안에 제거되고 텍스트 운영 이력과 분리된다.

### 광고 확장

- 하단 광고가 본문, 출처, 하단 목록과 시각적으로 구분된다.
- 광고 로딩 전후 CLS가 `0.1`을 넘지 않는다.
- 상세 route에는 정한 3개 외 광고 슬롯이 없다.
- 광고 차단·로드 실패 상태에서도 본문과 같은 게시판 주변 목록 이동이 유지된다.
- 광고 기능을 feature flag 하나로 즉시 끌 수 있다.
