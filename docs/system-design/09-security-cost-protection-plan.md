## 1. 적용 방향과 완료 경계

추천 순서는 **현황·정상 이용 측정 → 알림·캐시 보강 → 원본 보호와 제한 모의 계산 → 요청 제한의 단계적 활성화 → 운영 관찰**이다.
계정·원본 노출에 실제 결함이 확인되면 정상 관리 경로를 확보한 뒤 먼저 보완한다.

요청 횟수만으로 사람과 공격을 완전히 구별할 수 없다. 오탐, 즉 정상 요청을 공격으로 판단하는 일을
줄이기 위해 제한값을 먼저 확정하지 않는다. 정상 시나리오 통과와 대표 트래픽 관찰을 활성화 조건으로
삼고, 오탐이 확인되면 원인이 된 새 규칙을 즉시 되돌린다. 오탐 0건을 모든 미래 트래픽에 보장하지 않는다.

| 구분 | 이번 문서에서 정하는 것 | 후속 적용 전에 필요한 것 |
| --- | --- | --- |
| 유지할 계약 | 공개 무로그인 조회, 게시글 HTML·목록·상세 API `no-store`, Access 인증, 비공개 원본·백업, 기존 로그 보존 | 실제 동작 재확인 |
| 보강 계획 | 정적 파일 캐시 키, 관측·알림, 요청 제한, 원본·계정 보호, TLS·DNSSEC | 항목별 설정값·검증·되돌리기 준비 |
| 미정 운영값 | 요청 수·burst·동시 처리 상한, 알림 수신 경로, 비상 조치 발동값 | 실측과 운영자 결정. `(미정)` 상태로 차단 규칙을 활성화하지 않음 |
| 별도 정책 결정 | 공격 중 공개 이미지·읽기를 일시 제한하는 비상 모드 | planning·보안 운영 정본에 영향·발동/해제 조건 반영 후 적용 |
| 범위 밖 | 유료 요금제·Workers 신규 도입, 서버 증설, 기능 활성화, 개인정보 정책 발행 | 필요가 확인될 때 별도 결정 |

최초 문서 작성 단계에서는 운영 설정을 변경하지 않았다. 후속 직접 적용 요청에 따라 1차 캐시·알림을
적용했으며, 유료 가입·서비스 증설·commit·push는 수행하지 않았다. 요청 제한은 정상 이용 검증 후 진행한다.

## 2. 출발점: 확인한 사실과 미검증 항목

외부 설정은 2026-09-20 같은 대화의 선행 읽기 전용 점검에서 확인한 스냅샷이다. 콘솔 화면과 소수의
공개 HTTP 요청이 근거이며 외부 증거 파일을 이 저장소에 보관하지 않았다. 후속 적용 직전에 재조회한다.
소스 경로는 현재 작업 트리 기준이며 운영 release와 일치하는지도 따로 확인한다.
아래 표는 1차 적용 전 출발점이다. 이후 캐시·알림·AWS 조회의 변경된 상태와 HTTP 증거는 상단의 1차 실행 기록을 따른다.

| 항목 | 점검 결과 | 적용 계획에 미치는 영향 |
| --- | --- | --- |
| Cloudflare 기본 방어 | 네트워크·SSL/TLS DDoS 활성, HTTP DDoS 상시 보호, 설정 화면의 기본 관리 규칙 활성 | 기존 보호 유지. 규칙 목록의 관리 규칙 0개를 기본 WAF 전체 꺼짐으로 해석하지 않음 |
| 맞춤 규칙 | 사용자 지정 0/5, 요청 제한 0/1, Cache Rules 0 | 추가할 범위를 명시적으로 설계 |
| 공개 동적 경로 | `/meme`, `/api/v1/boards/meme/posts`가 `no-store`·`DYNAMIC` | 원본 CPU·DB 부하 제한 필요 |
| JS 캐시 | 동일 `/_nuxt/CJ-VOngK.js`가 `MISS` 후 `HIT`, `?security_review=1` 추가 시 `MISS` | 쿼리에 따른 캐시 분산 보강 후보. 모든 POP·모든 파일 검증은 아님 |
| R2 | 당시 청구 사용량 $0.00, public/private media 객체 0개, backup 공개 접근 꺼짐 | 실제 공개 이미지 HIT·숨김 후 제거·대용량 정상 이용은 미검증 |
| 이미지 도메인 | `media.blariyo.com` 연결 활성, 최소 TLS 1.0 표시 | 별도 TLS 1.2 이상 설정 후보 |
| 비용 알림 | 활성 예산 알림 2개, 사용자 알림 $10 확인 | 기존 알림 보존 후 조기 경고·수신 확인 보강 |
| 기타 Cloudflare | DNSSEC 꺼짐, Bot Fight·Hotlink 꺼짐. 알림 목록은 예산 알림 2개 | DNSSEC·DDoS 알림 검토, 봇 일괄 차단은 보류 |
| AWS | 콘솔 세션 만료 | 방화벽·MFA·예산·크레딧·전송량·다른 리전 자원은 미검증 |
| 운영 완료 경계 | 관리자 실제 작성·업로드·발행·숨김과 장기 관찰 잔여 | 이 흐름을 검증하기 전 제한 정책을 안전하다고 판정하지 않음 |

소스에서 확인한 보강 지점:

- [Nginx](../../deploy/gateway/nginx.conf): timeout·요청 크기 제한은 있으나 `limit_req`·`limit_conn` 없음.
- [공개 BFF](../../apps/web/server/api/v1/[...path].ts): 조회 수 증가에만 IP별 분당 60회 제한. 공개 목록·상세 전반의 제한은 아님.
- [운영 설정 생성](../../deploy/application/prepare-runtime-config.cjs): 초기 `NUXT_TRUSTED_CLIENT_IP_HEADER`는 빈 값이며 9월 23일 배포 기록에서도 유지했다. 이 경우 소켓 상대 IP에 의존하므로 프록시를 통한 이용자의 계수 합산을 시험해야 한다.
- [legacy 수집 BFF](../../apps/web/server/api/collector/v1/[...path].ts): 인증 토큰 기반 별도 제한. legacy 제출은 비활성이다. 별도 direct batch 저장·검수의 활성 상태와 혼동하지 않는다.
- [R2 adapter](../../apps/api/src/adapters/remote-adapters.ts): 업로드 시 Cache-Control을 명시하지 않고 공개 복사 시 원본 값을 계승. 이미지 헤더 계약과 실제 object metadata 확인 필요.
- [이미지 검증](../../apps/api/src/features/images/image-validation.ts): 파일 수·크기·픽셀·프레임 제한 존재. 동시 업로드의 메모리·CPU 상한은 별도 검증 대상.

## 3. 정상 이용 보호 원칙

1. 사이트 전체에 동일한 요청 수 제한을 적용하지 않는다. 공개 HTML/API, 정적 파일, 관리자, 수집, health를 분리한다.
2. 회사·학교 Wi-Fi와 이동통신사의 공유 공인 IP를 고려한다. 한 IP를 한 사람으로 가정하지 않는다.
3. 첫 방문의 JS·CSS 다운로드, 이미지 여러 장, 빠른 페이지 이동, 여러 탭, 모바일 재연결을 정상 부하로 시험한다.
4. 국가·ASN·VPN·User-Agent 문자열만으로 일괄 차단하거나 빈 Referer를 공격으로 단정하지 않는다.
5. 검색봇·공유 미리보기는 실제 요청으로 검증한다. User-Agent에 `Googlebot` 등이 있다고 보안 전체를 우회시키지 않는다.
6. HTML 챌린지를 JSON API·이미지·health 응답에 일괄 적용하지 않는다. 공개 이용자에게 로그인을 요구하지 않는다.
7. 인증된 관리자도 용량·동시 작업 제한은 받되 공개 조회 IP 제한과 공유하지 않는다. 권리 요청 숨김·복구 접근을 보전한다.
8. 관측·문서상의 설정 존재·로컬 시험·운영 반영·운영 관찰을 독립적으로 기록한다.

## 4. 요청 종류별 적용 범위

| 경로·대상 | 보호 방식 | 오탐 방지·제외 조건 |
| --- | --- | --- |
| `/meme`, `/meme/posts/:postId` | SSR, 즉 서버가 HTML을 만드는 요청의 속도·전체 동시 처리 제한 후보 | `no-store` 유지. 새로고침·다중 탭·공유 미리보기 포함 |
| `/api/v1/boards/:boardSlug/posts`, 상세 API | 동적 API 제한 후보 | 페이지 이동 burst 허용, JSON 오류 처리 확인 |
| `.../posts/:postId/views` | 기존 조회 수 제한의 실제 IP 판별·공유 IP 영향 보완 | 조회 수 실패가 본문·이미지 표시를 막지 않아야 함 |
| `/api/v1/boards`, `/api/v1/policies/:type` | 기존 응답 캐시 계약 유지, 필요한 원본 보호만 적용 | `version` 등 의미 있는 쿼리 보존. 공개 API 전부를 같은 캐시 정책으로 묶지 않음 |
| `/_nuxt/` 실제 해시 JS·CSS | 캐시 키 보강·기존 장기 캐시 유지 | 초기 동적 요청 제한에서 제외. 존재하지 않는 파일·HTML 오류까지 캐시하지 않음 |
| `media.blariyo.com`의 발행 이미지 | R2 캐시·TLS, 필요한 메서드·경로 검증 | 다중 이미지·GIF·직접 열기·Range·HEAD·공유 OG 이미지 검증 |
| `/admin*`, `/api/v1/admin/*` | Access와 앱 권한 유지, 작업별 상한 | 인증 전 IP 기준과 인증 후 operator 기준을 구분. 업로드·숨김은 별도 처리 |
| `/api/collector/v1/*` | 현재 비활성 유지 | 향후 활성화 시 토큰 제한·재시도·비브라우저 요청 별도 수용 시험 |
| `/api/v1/admin/collect/batch-items` 및 하위 경로, 외부 PC의 direct batch·queue | 관리자 검수 권한과 DB/R2 writer 권한·실행 예산을 각각 관리 | 9월 23일 batch review 플래그 활성 기록과 외부 PC writer 인수 미검증을 구분. 웹 요청 제한만으로 직접 DB/R2 작업을 제한할 수 없음 |
| `/health/live`, `/health/ready`, 내부 health | 가벼운 공개 liveness와 인증된 readiness 경계 유지 | 모니터링에 챌린지 금지, 사용자 헤더 하나만으로 전역 예외 부여 금지 |
| `/`, `www`, 정책·robots·favicon, `/cdn-cgi/*` | 리다이렉트·정상 플랫폼 경로 유지 | 포괄 경로 차단 규칙에 섞지 않음. 실제 배포 경로 목록으로 확인 |

현재 경로·메서드는 [M0 OpenAPI](../../packages/contracts/openapi/m0-core.yaml), [수집 OpenAPI](../../packages/contracts/openapi/m0-collection-assist.yaml)와 실제 라우터를 대조한다.
미래 게시판·회원·수집 기능을 켤 때 이 표와 규칙을 같이 갱신한다.

| 5 / H05 | 개발자·운영자: Nginx/App 원본 제한을 한 계층씩 활성화 | 정상 시험 전부 통과, 과부하 제한·오류 응답·자원 회복 확인 | 오탐 1건 재현 시 해당 제한을 모의 계산 모드로 복귀 |
| 6 / H06 | 운영자: 검증한 동적 경로에 Cloudflare 제한 1개 적용 | 실제 표현식·10초 임계값·범위·429, 공유 IP·검색/미리보기 시험 | 새 제한 규칙만 비활성화. 일괄 WAF Skip 금지 |
| 별도 / H07 | 운영자: 이미지 TLS 1.2 이상, DNSSEC를 각각 적용 | 모바일·공유 이미지 TLS, 등록기관 DS와 외부 DNS 검증 | TLS의 대상 규칙만 복귀. DNSSEC는 DS부터 정합성을 맞추는 절차 사용 |
| 별도 / H08 | 개발자: 업로드·변환·outbox/수집 재시도의 자원·작업 상한 | 정상 대용량 작업·실패 회복·숨김 처리 통과 | 새 작업 제한만 복귀. MIME·크기·권한 검증 유지 |
| 별도 / H09 | 운영자: 독립 백업·복구키·토큰 역할 분리 확인 | 별도 보호 사본의 실제 복원, 삭제·보존 정책 대조 | 복구 성공 전 기존 사본·키 제거 금지 |
| 마지막 / H10 | 운영자·개발자: 비상 대응 훈련과 7일 관찰 | 정상 이용·비용 증가율·가용성·되돌리기 기록 | §10 기준. 관찰 완료 전 전체 완료로 표시하지 않음 |

H03의 확인된 원본 노출·계정 침해 문제는 순서 2보다 앞서 처리할 수 있다. H07·H09는 요청 제한
실측을 기다리지 않고 준비할 수 있지만 서로 다른 설정 변경을 같은 시점에 묶지 않는다.

## 6. 요청 제한값을 정하는 방법

### 6.1 측정부터 수행

9월 20일의 빈 사이트 트래픽만으로 정상 상한을 계산하지 않는다. 9월 23일에는 공개 글74개·이미지308개를 승격했지만 이는 처리 용량·대표 이용량의 증거가 아니다. 격리 환경에 기획·API 계약상 최대 구성의 게시글·이미지를 준비하고 아래 시나리오를 실행하며 대표 운영 트래픽도 관찰한다. 시험 데이터·부하를 production에 투입하는 작업은 별도 실행 범위로 정한다.

수집할 값은 경로 그룹별 10초 요청 분포, 순간 최대 동시 요청, 첫 방문 자산 수, 응답 크기,
응답 시간 p95, 429·5xx, Web/API 메모리·재시작, DB 연결 대기, R2 작업 수와 송신량이다.
브라우저 방문 한 번이 SSR·BFF 내부 호출로 이어진 횟수와 외부 요청 횟수를 분리하여 중복 제한을 피한다.

| 값 | 산정 방법 | 현재 값 |
| --- | --- | --- |
| `L10` | 공유 IP를 포함한 정상 시험·관찰의 같은 IP당 동적 요청 10초 최대치 | `(미정)` |
| `R_edge` | `L10`에 여유를 둔 후보로 모의 평가. 최초 검토안은 `max(3 × L10, 100)`회/10초 | `(미정)` — 100은 운영 기본값·수용량 보장이 아님 |
| `R_origin`, `burst` | 정상 페이지 이동을 지연시키지 않는 지속 속도·순간 허용량, CPU/DB 여유와 함께 산정 | `(미정)` |
| `C_total` | 대표 혼합 부하에서 정상 응답·메모리·DB 여유를 유지한 전체 동시 처리 수 아래에서 산정 | `(미정)` |
| `C_upload`, 일일 용량 | 정상 관리자 작업과 백업·예약 실행이 겹치는 시험으로 산정 | `(미정)` |

정상 공유 IP 부하와 안전한 서버 용량을 동시에 만족하는 값이 없으면 제한을 억지로 낮추지 않는다.
캐시·조회 비용·작업 분리 개선 후 재시험하고 필요 시 용량·요금제 결정을 별도로 검토한다.
분산 공격은 IP 제한만으로 해결하지 못하며 전체 상한도 정상 급증을 거부할 수 있다.

### 6.2 실제 IP와 모의 계산

- Nginx 소켓의 상대는 방문자가 아니라 `cloudflared`일 수 있다. 그대로 `$remote_addr`를 제한 키로 쓰지 않는다.
- 실제 cloudflared 연결 경로·직접 접근 차단을 확인한 뒤 신뢰할 프록시 범위와 `CF-Connecting-IP` 처리를 정의한다.
  모든 주소를 신뢰하는 `0.0.0.0/0` 설정이나 임의 `X-Forwarded-For` 사용은 금지한다.
- Nginx→Web에 전달하는 정규화 IP, IPv4/IPv6 표현, 잘못된/누락된 헤더의 처리를 시험한다.
  모든 방문자를 `unknown` 한 키로 묶어 차단하지 않는다. 키 신뢰가 불명확하면 IP별 활성화를 보류하고 알린다.
- 기존 조회 수 제한 분당 60회도 공유 IP 시험 대상이다. 강화만 하지 말고 정상 이용 집계 손실을 확인한다.
- 계수 상태의 메모리 크기·만료·재시작 동작·키 고갈 시 동작을 정한다. 요청마다 무한한 식별 키를 저장하지 않는다.

Nginx는 `limit_req_dry_run`·`limit_conn_dry_run`으로 실제 차단 없이 제한 결과를 계산할 수 있다.
처음에는 이 모드를 사용하고, 필요 최소 상태값을 기존 안전한 로그에 추가한다.
설치 이미지의 모듈과 설정 상속을 확인한다. 원본 제한의 계수 방식은 Cloudflare 10초 계수와 같지 않으므로
Cloudflare 규칙은 별도로 재현·검증한다.
[요청 제한 공식 문서](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html),
[동시 처리 제한](https://nginx.org/en/docs/http/ngx_http_limit_conn_module.html),
[프록시 IP 신뢰](https://nginx.org/en/docs/http/ngx_http_realip_module.html).

### 6.3 Cloudflare Free 범위

2026-09-24 공식 문서 재확인 기준 Free는 요청 제한 **1개**, IP 기준 계수, 계수 기간·차단 기간 각각 10초다.
규칙 조건은 Path·Verified Bot 범위이며 Host·Method·세션/토큰별 계수를 사용할 수 있다고 가정하지 않는다.
캐시 HIT 제외와 NAT를 이해하는 계수도 Free에 있다고 가정하지 않는다.
[요금제별 제공 범위](https://developers.cloudflare.com/waf/rate-limiting-rules/).

따라서 첫 후보는 현재 동적 게시글 경로만 포함하고 `/_nuxt/`, 이미지·관리자·health·`/cdn-cgi/`는
포함하지 않는다. 같은 zone의 다른 hostname에도 같은 path가 있는지 조사하여 예상치 못한 합산을
검증한다. 검색봇 제외는 제공자의 Verified Bot 판별을 사용하고 보안 전체 우회와 구분한다.
공유 미리보기 봇이 모두 Verified Bot으로 잡힌다고 가정하지 않는다.

Free의 Log 전용 action을 전제로 계획하지 않는다. 로컬·Nginx 모의 계산, 허용된 분석 화면과 실제
테스트를 사용한다. 샘플링된 분석에서 차단이 보이지 않는 사실만으로 오탐이 없다고 판단하지 않는다.
지원 필드로 안전한 범위를 표현할 수 없으면 해당 규칙 적용을 보류한다.

Cloudflare 제한은 계수 지연과 데이터센터별 동작 때문에 정확한 요청 총량·과금 상한이 아니다.
API에 HTML 챌린지를 넣지 않으며, 제한 응답의 상태·Content-Type·앱 오류 처리를 실제 확인한다.
원본 API 제한은 기존 API 계약과 맞는 오류 본문·`Retry-After`를 설계하고 클라이언트의 무한 재시도를 막는다.

## 7. 정적 파일·이미지 캐시와 전송 보안

### 7.1 캐시 키

- `/_nuxt/`에서는 실제 배포 manifest의 해시 파일만 대상으로, 쿼리가 파일 내용·권한을 바꾸지 않는지 확인한다.
  검증 후 해당 경로의 쿼리를 캐시 키에서 제외하는 안을 적용한다. 사이트 전체 Query String Ignore는 금지한다.
  1차의 파일명 9개 열거 규칙을 대체할 후속 후보는 `blariyo.com`의 `/_nuxt/` 아래 JS·CSS다.
  운영 이미지의 정적 파일 처리기와 전체 JS·CSS의 내용·헤더를 대조한 뒤 전환한다. `builds/latest.json` 등
  배포 메타데이터는 제외한다. 존재하는 공개 빌드 파일만 불변 응답을 반환하고, 없는 경로·HTML·인증별
  응답은 캐시하지 않는 계약을 배포마다 검사한다. 새 규칙의 콘솔 저장·응답 검증 전까지는 9개 규칙이
  마지막으로 확인한 운영 설정이며, 후속 후보를 적용 완료로 간주하지 않는다.
- 이미지도 `media.blariyo.com`의 발행 객체 경로만 대상으로 한다. 향후 서명·크기 변환·권한 쿼리가 도입되면
  이 규칙을 재검토한다. 관리 미리보기·비공개 R2·정책 version·페이지 번호 쿼리는 합치지 않는다.
- 실제 Free 계정에서 선택 가능한 캐시 옵션과 규칙 한도를 확인한다. 미지원이면 경로 한정 정규화 대안을
  검토하되 모든 쿼리 요청 차단·자동 유료 전환으로 대체하지 않는다.
- 존재하지 않는 파일의 404·403·5xx를 정상 파일처럼 장기 캐시하지 않는다. 확장자만으로 동적 URL을
  정적 파일로 판단하지 않으며, 쿠키·인증 유무가 캐시 내용에 영향을 주지 않는지 검사한다.
  HTML뿐 아니라 JSON 오류도 `no-store`여야 한다. 게이트웨이는 최종 4xx·5xx 응답의 Cache-Control을
  `no-store`로 정규화하며, 성공 응답의 원본 Cache-Control과 본문·상태는 유지한다. 이는 요청 차단
  규칙이 아니라 기존 오류 캐시 금지 계약의 방어다. 적용 전후 HTML/JSON 404·합성 401/403/500과
  정상 정적 파일·동적 API를 검증하고, 이미 저장된 오류 사본은 별도 범위 purge·만료와 구분한다.
  앱 원본도 같은 계약을 지킨다. 현재 Nitro 2에서는 Nuxt HTML 오류 처리 뒤에 JSON 오류 처리를 두어
  프레임워크가 만드는 상태·본문·보안 헤더를 유지하고 4xx·5xx의 Cache-Control만 `no-store`로 바꾼다.
  정상 응답의 캐시 정책은 바꾸지 않는다. 9월 23일 앱 배포 기록은 이 보완의 운영 반영 근거이며, 로컬 build·HTTP 회귀 검증과 경로 캐시 규칙의 후속 확대는 각각 별도로 판정한다.
- 캐시 규칙을 GET만 매칭하도록 만들면 단일 URL purge 동작에 영향을 줄 수 있다. 캐시 매칭과 허용
  메서드 제한은 분리하고 GET·HEAD·단일 URL purge·쿼리 변형을 함께 검증한다.

[Cloudflare 캐시 설정과 purge 주의사항](https://developers.cloudflare.com/cache/how-to/cache-rules/settings/).

### 7.2 이미지 캐시와 공개 범위

JS·CSS의 해시 파일 장기 캐시와 삭제·숨김 가능한 게시 이미지는 구분한다. 현행
[아키텍처의 캐시 정책](01-system-architecture.md#6-캐시-정책)은 공개 이미지에
`public, max-age=31536000, immutable`을 명시한다. 이는 설계값이며 현재 공개 이미지 응답에서
검증한 값이 아니다. 9월 23일 미디어 다운로드 해시 대조도 Cache-Control·HIT·숨김 후 purge 검증을 대신하지 않는다. 브라우저 TTL은 사용자 단말에 사본을 유지하는 기간이고, 엣지 TTL은 Cloudflare
사본의 유효기간이다. 브라우저 사본을 원격 purge로 회수할 수 있다고 설명하지 않는다.

후속 결정은 현행 1년 설계값을 유지할지, 브라우저 TTL과 엣지 TTL을 분리·조정할지다. 실제 헤더·
권리 숨김 계약·캐시 MISS와 비용 영향을 확인한 뒤 결정하며 조정값은 `(미정)`이다. 바꾸기로 하면
아키텍처·인프라·보안 정본을 먼저 동기화한다. 검증 전 1년 `immutable`을 신규 일괄 설정하지 않는다.

이미지를 발행하고 `HIT`를 만든 뒤, 숨김 요청·공개 API 404→public object 삭제→정확한 URL purge→
이미지 삭제 작업 성공 처리→다시 조회의 순서로 검증한다. 삭제·purge 실패 시 API의 404를 유지한 채
재시도하는 기존 계약도 시험한다. 쿼리 변형·여러 관측 위치·새 브라우저와 기존 브라우저를 구분한다.
한 위치의 HIT·purge 요청 수락만으로 전체 전파 완료라고 보고하지 않는다.

R2 `r2.dev` 경로와 추가 custom domain을 모두 재조회한다. public media는 승인된 custom domain만,
private·backup은 공개 접근이 없어야 한다. custom domain만 막아도 다른 공개 경로가 열려 있으면 보호를
우회할 수 있다. CORS 설정은 직접 다운로드를 차단하는 인증 수단이 아니다.
[R2 공개 접근과 캐시](https://developers.cloudflare.com/r2/buckets/public-buckets/).

미디어의 GET·HEAD와 실제 필요한 OPTIONS·Range 동작을 먼저 확인한 뒤 불필요한 메서드·명백한
스캔 경로를 개별 규칙 후보로 만든다. 빈 Referer나 쿼리 존재만으로 차단하지 않는다.

### 7.3 TLS·DNSSEC

- 이미지 custom domain의 최소 TLS를 1.2 이상으로 올리는 안을 정상 모바일·공유 미리보기로 검증한다.
  R2 custom domain 설정을 별도 확인하며 본 웹 도메인의 TLS 설정을 자동 승계한다고 가정하지 않는다.
- DNSSEC는 Cloudflare 서명 활성화와 등록기관 Squarespace의 DS 등록을 한 변경 절차로 관리한다.
  서로 다른 DNS resolver에서 정상 조회·검증을 확인한다. 되돌릴 때 등록기관 DS가 남은 채 서명만
  끄면 장애가 날 수 있으므로 DS 정합성·전파/TTL을 고려한 순서를 먼저 준비한다.

[R2 TLS](https://developers.cloudflare.com/r2/buckets/public-buckets/#minimum-tls-version--cipher-suites),
[DNSSEC 절차](https://developers.cloudflare.com/dns/dnssec/).

### 8.2 AWS·계정·권한

- AWS 로그인 후 IPv4·IPv6 방화벽을 각각 읽고 80/443·앱·DB 직접 접근 경로와 SSH 허용 범위를 확인한다.
  Lightsail 방화벽은 outbound·private network의 모든 경로를 차단하는 장치가 아니다. 호스트 방화벽과
  Docker port·network도 대조한다. TLS·DNS·provider 통신을 이해하지 않은 outbound 일괄 차단은 보류한다.
- SSH 제한 전 현재 접속과 별도 복구 수단을 유지하고 두 번째 접속을 시험한다. Tunnel outbound 연결과
  관리자 정상 접근이 살아 있는 상태에서 원본 노출을 줄인다.
- AWS 루트·Cloudflare·도메인 등록기관·관리 이메일 MFA와 복구 수단, 불필요한 관리자·장기 키를 확인한다.
  앱에 VM 생성·결제·계정 전체 관리 권한을 넣지 않는다. R2의 앱·백업 bucket 권한과 purge token 권한을 대조한다.
- IMDSv2는 현재 blueprint·사용 코드·metadata 호출을 확인한 뒤 필수화한다. 지원 여부를 확인하지 않고 바꾸지 않는다.
- 모든 사용 리전의 VM·디스크·snapshot·기타 자원과 청구를 확인하고 미사용 자원 처리는 별도 목록으로 확정한다.

[Lightsail 방화벽](https://docs.aws.amazon.com/lightsail/latest/userguide/understanding-firewall-and-port-mappings-in-amazon-lightsail.html),
[AWS 루트 계정](https://docs.aws.amazon.com/IAM/latest/UserGuide/root-user-best-practices.html),
[Lightsail IMDSv2](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-configuring-instance-metadata-service.html).

### 8.3 작업 폭주와 복구

관리자 업로드는 허용 크기 안에서도 동시 실행으로 메모리를 소모할 수 있다. 인증 후 작업 수·실행 시간·
총 용량을 제한하고, 정상 파일 크기를 임의로 줄여 기존 계약을 깨지 않는다. JSON·multipart·proxy의
한도를 대조하고 전송 overhead를 포함한 최대 정상 업로드가 통과하는지 확인한다.
재시도는 횟수·간격·동시 실행 상한을 가지며 실패한 작업을 무한 호출하지 않는다. 백업·숨김·예약 작업은
일반 업로드 제한과 분리하여 기능별 자원 여유를 확보한다.

direct 수집은 공개 전에도 private R2의 raw HTML·media, DB run/request/queue 기록을 만든다. 공개 이미지 비용만으로 수집 예산을 계산하지 않는다. 보존·삭제의 법무 결정과 writer별 일일 총량·재시도 비용을 함께 정한다. 현행 direct 경로의 robots/Crawl-delay·영속 일일 budget 미연결은 [수집 설계](07-spring-collector-design.md)와 [로드맵 P1-06](../roadmap.md)에 남은 활성화 조건이다. 요청 간격·회당 항목 수 제한만으로 이를 충족했다고 보지 않는다.

암호화 백업과 복구키의 별도 보호 사본, 복원 검증을 준비한다. 같은 계정의 다른 bucket만으로 계정 탈취에
대한 독립 복구가 완성됐다고 보지 않는다. 백업 잠금은 삭제 방지 장점과 보존기간·삭제 요청 반영·비용의
충돌을 검토한 뒤 별도로 정한다. public media에는 숨김/삭제를 막는 잠금을 적용하지 않는다.

합성 공유 IP 인원 수는 용량 보장이 아니라 오탐 탐색용 시험안이며 실제 이용 예상·관찰로 보정한다.

Cloudflare에 임의로 실행하지 않는다. Cloudflare 실제 집행 확인도 별도 좁은 시험 범위·횟수·중단 조건을
정한 뒤 수행한다. 격리 시험 통과가 운영 용량을 증명하지는 않는다.

### 관측과 개인정보

IP별 계수는 짧게 만료되는 메모리 상태로 사용하고 신규 방문자 식별 쿠키·장기 IP 열람 이력을 만들지 않는다.
저장 로그에는 시간, 규칙/경로 그룹, 계층, 상태 코드, 지연, 제한의 모의/실제 결과·집계 분포만 추가하는
방향을 우선한다. 원문 IP·쿼리·쿠키·Authorization·Access JWT·이메일을 진단 로그에 추가하지 않는다.
Nginx 제한 로그를 위해 원문 요청이 포함되는 error log 수준을 무심코 높이지 않는다.
자체 진단 로그는 기존 최대 7일·용량 제한을 유지한다. 추가 개인 식별 기록이 꼭 필요하면 목적·보존·접근과
[현재 개인정보 정책](../legal/m0-core/privacy.html)의 정합성을 먼저 검토하며 확정 v0.1을 덮어쓰지 않는다.

## 10. 적용·중단·비상 대응 기준

### 정상 이용을 위한 완화 범위

공개 읽기의 정상 이용을 우선한다. 요청 횟수·순간 허용량·차단 시간·추가 봇 규칙의 적용 범위는
정상 이용 결과에 따라 조절하거나 해당 추가 규칙만 해제할 수 있어야 한다. IP 하나를 사용자 한 명으로
간주하지 않으며, 공개 읽기에 VPN·쿠키 차단·빈 Referer만을 이유로 일괄 차단을 추가하지 않는다.
업로드 크기·개수·동시 처리·timeout은 정상 작업과 서버 자원을 함께 검사한 뒤 조절한다.

완화해도 관리자 인증·권한 검사, 비공개 파일/백업 보호, DB·내부 API 격리, 입력·파일 형식 검증은 유지한다.
비용 알림은 이용 중단과 분리한다. 정상 수요와 안전한 처리 용량을 동시에 만족하지 못하면 캐시·처리 비용·
용량·예산을 검토하며 제한만 낮춰 정상 유입을 공격처럼 처리하지 않는다.

기존 적용한 정적 캐시·알림·게이트웨이 오류 `no-store`는 새로운 이용량 차단 정책이 아니다.
정상 이용 회귀의 근거 없이 선제 해제하지 않는다. 이번 완화 기준의 문서 반영만으로 운영 설정을
변경하거나 다음 앱 배포에 새 차단 규칙을 포함하지 않는다. 항목별 적용 시점은
[배포 구분](../operations/security-protection-status.md#8-현재-설정-유지와-다음-배포의-구분)을 따른다.

### 적용 직전 확인

- 정상 수용 시험 N01–N08과 해당 변경의 C/A/R 시험이 통과해야 한다. 해당 기능 미활성에 따른 제외는 근거를 기록한다.
- 순서·표현식·활성값·배포 revision·측정값·되돌리기 방법을 비밀 없이 남긴다. 실제 제한값이 미정이면 활성화하지 않는다.
- 대표 트래픽으로 모의 계산을 최소 24시간 관찰하는 안을 기본으로 한다. 빈 사이트·적은 표본은 충분한 근거가 아니다.
  대표 데이터가 없으면 알림·캐시 등 검증된 항목만 진행하고 차단은 보류한다.
- 한 번에 규칙 또는 계층 하나만 바꾼다. Cloudflare와 Nginx 제한을 동시에 켜지 않는다.
- 적용 직후 정상 확인, 30분 집중 관찰, 다음 날 재확인, 7일 추세 확인을 수행한다. 이 기간은 계획값이다.

### 즉시 중단·되돌리기

새 규칙 때문에 정상 시나리오에서 403·429·챌린지·이미지 깨짐·로그인 반복·관리자 숨김 실패가 **1건이라도
재현되면** 해당 규칙을 해제하거나 모의 계산으로 되돌린다. 원인을 확인하지 않은 채 예외 IP를 계속 늘리지 않는다.
같은 정상 부하에서 p95가 기준선보다 20% 이상 늘어나는 현상이 5분 지속되면 변경을 중단하고 원인을
확인한다. 이 수치는 초기 점검안이며 저표본에서는 실제 정상 시나리오 결과를 우선한다. 신규 OOM·DB
연결 고갈은 즉시 중단 사유다. 규칙을 끄면서 Access·기본 DDoS·원본 방화벽 전체를 해제하지 않는다.

### 공격·비용 급증 시 제안 절차

1. 공격 징후와 정상 공유 유입을 비교하고 어느 hostname·경로·작업·자격증명에서 비용/부하가 생기는지 확인한다.
2. 문제 경로·작업만 제한한다. 공개 조회, 관리자 숨김, 백업·복구 접근을 가능한 한 유지한다.
3. 키 오용이면 필요한 키만 폐기·교체하고 정상 작업의 새 키 연결을 검증한다.
4. 전체 읽기/미디어 중단은 별도 비상 정책이 정해진 경우의 최후 수단이다. 비용 알림 하나로 자동 중단하지 않는다.
5. 발동 사유·범위·책임자·다음 확인 시각·최대 유지 시간·해제 조건을 기록하고 정상 시험 후 순차 해제한다.

현재 [비용 이상 대응](05-security-operations.md)의 정상 성장 시 비용 승인·유료 전환 원칙은 유지한다.
공개 이용 제한을 포함한 비상 모드는 **제안**이며 이 문서만으로 활성화하지 않는다. 적용 전
[인프라 계획 §8](../planning/02-infra-plan.md#8-운영보안-의사결정)과 보안·운영의 비용 이상 대응에
정상 성장/공격 구분, 사용자가 감수할 영향과 한도를 반영한다. VM을 정지해도 모든 저장·자원 비용이
즉시 사라진다고 가정하지 않는다.
