# 다중 게시판·M1.5 익게의 후속 테스트

[전체 구현 안내](README.md)와 구분해 읽는다. 이 파일의 6개 케이스는 **후속 설계·미실행**이다.
현재 M0 테스트 suite에 실패 케이스로 넣거나, 미구현 기능을 skip해 전체 통과로 보고하지 않는다.
M1.5 설계·API를 구현하는 시점에 정확한 요청·오류 코드·fixture를 확정해 실행 케이스로 전환한다.

근거: [회원·익게 제품 계약](../planning/08-member-community-plan.md),
[회원·익게 기술 계약](../system-design/06-member-community-design.md),
[게시판 데이터 모델](../system-design/02-data-model.md).
아래 FUT-01·02의 관리자 화면/API는 선택적 CMS 기능이며 M1.5의 필수 구현으로 새로 결정한 것이 아니다.

## FUT-01 — 게시판을 생성하고 이름·노출 순서를 변경한다

- **P1 / 게시판 관리 기능을 채택할 때**. 목표: 관리자가 SQL 없이 ADMIN 게시판을 관리한다.
- 결정 필요: 관리자 API path·응답, slug 생성 규칙·오류 코드, 정렬 충돌 처리 방식은 `(미정)`.
- 준비: meme과 새 게시판 생성을 허용받은 운영자. 동일 slug·display_order 충돌 데이터.
- 실행: 생성→이름 수정→순서 변경→공개 목록과 관리 화면 새로고침. 무권한 요청과 충돌도 따로 보낸다.
- 기대: 게시판 row와 공통 목록/상세 경로가 연결되고 게시판마다 새 post 테이블을 만들지 않는다.
  권한 없는 변경·중복 slug는 거부하며 기존 글의 board_id는 유지된다.
- 추가 검증: 기존 slug 변경은 현재 DB trigger가 거부한다. slug 변경 기능을 넣으려면 alias/redirect 계약부터
  별도 설계한다. 테스트가 통과하도록 trigger를 해제하지 않는다.
- 구현 시작 조건: 관리 기능 범위와 API 정본 승인. 현재는 migration seed 추가만으로도 고정 게시판 운영이 가능하다.

## FUT-02 — 비활성화와 동시 게시판 관리를 일관되게 처리한다

- **P0 / 게시판 관리 기능을 채택할 때**.
- 결정 필요: 관리 API의 version·동시성 방식·오류 코드, 게시판 삭제 제공 여부 `(미정)`.
- 준비: 공개 글이 있는 ADMIN 게시판, 같은 관리 버전을 읽은 운영자 A/B.
- 실행: A 비활성화 후 B가 오래된 값으로 수정. 이어 공개 게시판 목록·직접 상세·새 글 작성·재활성화를 확인한다.
- 기대: 현재 is_active 계약을 사용하는 비활성화는 신규 공개 조회를 차단하고 게시판 목록에서 제외한다.
  기존 row와 콘텐츠는 보존하며 stale 변경이 A의 설정을 덮어쓰지 않는다.
- 추가 검증: 메뉴에서만 감추는 별도 기능은 현재 is_active와 다르므로 새 정책 없이 같은 필드로 구현하지 않는다.
  게시판 목록의 cache/ETag 때문에 즉시 반영되지 않을 수 있는 범위와 무효화 정책도 관리 기능 설계에 포함한다.

## FUT-03 — ADMIN·USER 게시판의 읽기·쓰기 경계를 나눈다

- **P0 / M1.5**. 준비: meme=ADMIN, community=USER·초기 비활성, 회원 기능 gate와 합성 회원/관리자.
- 실행: gate 비활성·활성 조합별로 board 목록과 community 직접 조회. 활성화 후 회원 글 작성과 기존 관리자
  `/admin/posts`를 통한 USER 글 생성·수정·발행을 시도한다.
- 기대: 준비 전 익게 미노출. 준비 후 비회원 읽기 가능, 참여는 유효 회원·필수 동의·제재 확인 후만 허용.
  기존 관리자 게시글 command는 USER를 거부하고 운영 조치는 moderation 경로를 사용한다.
- 추가 검증: USER가 포함된 board DTO/OpenAPI/BFF를 함께 확장한다. 현재 M0의 ADMIN 전용 응답 변환을
  둔 채 DB row만 활성화해 전체 게시판 목록이 실패하지 않게 한다.
- 구현 시 API·오류 코드는 M1.5 계약에서 확정한다. 운영자라고 회원 글 본문을 기존 관리자 편집기로 수정하지 않는다.

## FUT-04 — 익게 입력과 작성자 권한을 검사한다

- **P0 / M1.5**.
- 준비: 유효 회원 A/B, 만료 세션, 동의 필요 상태, 제재 회원. 각 입력의 NFC 정규화·trim 후 길이를 계산한다.
- 실행: 제목 0/1/200/201, 본문 0/1/10000/10001, 댓글 0/1/1000/1001 code point와 제목 줄바꿈을 시험한다.
- 기대: 허용 경계만 성공. 제목 줄바꿈 금지, 본문·댓글 줄바꿈은 LF로 통일. HTML/Markdown은 문자열이다.
  최초 익게는 이미지·공지·예약·초안·출처 필드를 받지 않는다.
- 추가 검증: A만 본인 공개 글 수정/삭제. B와 제재·동의 미완료 상태의 참여는 거부. 수정 후 최초 발행 순서 유지.
  숨김 글은 본인도 수정·재공개 불가, 삭제는 허용. 삭제·숨김 댓글은 공개 본문·작성자 없는 자리 표시다.

## FUT-05 — 랜덤 이름과 개인정보 비노출을 검사한다

- **P0 / M1.5**.
- 준비: 회원 A/B와 서로 다른 글 X/Y. A가 X에 처음 댓글을 동시에 2개 작성하는 상황.
- 기대: A는 X에서 항상 같은 이름, X의 글쓴이라면 글쓴이 배지. Y에서는 A가 이전에 사용하지 않은 이름.
  동시 최초 참여에서도 participant가 중복 생성되지 않는다.
- 추가 검증: 댓글 삭제·탈퇴 후 X의 이름을 다른 회원에게 재배정하지 않는다. 공개 API·HTML·SSR payload·
  metadata에 accountId·서비스 표시명·IP·provider 식별자 없음. 다른 회원의 활동 목록 접근 차단.
- 주의: 같은 회원의 다른 글 이름이 매번 다른지만 보면 부족하다. 과거 사용 이름과 사전 고갈 시 동작도
  [이름 배정 계약](../system-design/06-member-community-design.md#random-name-assignment)에 맞춰 검사한다.

## FUT-06 — 작성 상한과 탈퇴·제재의 동시 요청을 검사한다

- **P0 / M1.5**.
- 준비: 글 5건/10분·30건/일, 댓글 30건/10분·300건/일, 신고 10건/일의 경계 직전 합성 데이터.
- 실행: 상한 직전 두 요청을 동시에 제출. 성공 요청 재전송·삭제 후 재작성·KST 날짜 경계도 각각 실행한다.
- 기대: 허용량을 넘는 신규 성공 없음. 성공한 신규 생성만 일 사용량에 반영하고 재전송·삭제로 우회하지 못한다.
- 추가 검증: 탈퇴·제재 처리와 글 작성을 경쟁시켜 계정 잠금과 상태 재검사로 접수된 제한 이후 신규 쓰기를 막는다.
  제재 시작 전/종료 시각·REVOKED는 정본 predicate로 판단하고 정리 cron 완료를 기다리지 않는다.
- 범위: 이 케이스는 참여 차단 경계다. 탈퇴 원격 삭제 ledger·복원 후 삭제 재적용 전체 검증은 회원·복구의 별도
  테스트 계획으로 작성해야 하며, 이 케이스 통과로 회원 탈퇴 기능 전체를 완료 처리하지 않는다.
