# 문서 최신화 TASK 계획

목적: 최신 배포·DB 반영 기록을 현행 운영 문서와 진행표에 반영하여 다음 작업·배포·복구 판단이 오래된 설명에 의존하지 않게 한다.

## 요청과 현재 범위

- 요청: 문서 정리 계획을 TASK 단위로 나눠 worklog에 기록.
- 계획 작성일: 2026-09-24 KST. **계획 기록 당시** 실행 TASK는 모두 미착수였다. 이후 사용자의 별도 실행 요청으로 TASK-01~07의 문서 최신화·검증을 수행했다. [실행 결과](RESULTS.md)를 따른다.
- 계획 작성 당시 시작 Git: HEAD `82c0ba9`, `main...origin/main [ahead 5]`, 작업 트리 clean. origin/main은 로컬 추적 참조이며 원격을 조회하지 않았다. 실행 시작 시에는 이 계획과 worklog 색인이 기존 미커밋 변경이었다. 두 기준선을 혼동하지 않는다.
- 계획 작성 당시 변경: 이 계획과 TASK 파일, 날짜별·전체 worklog 색인만 작성했다. 이후 실행의 13개 현행 문서 변경은 [실행 결과](RESULTS.md)에 별도로 기록한다.
- 계획 작성 단계에는 후속 TASK의 문서 수정·실행을 포함하지 않았다. 이후 문서 최신화에서도 commit·push·배포·DB/외부 설정 변경은 수행하지 않았다.
- 담당: 문서 수정·대조는 개발 담당, 실제 인수·운영 결정은 운영 담당. 확정 기한은 없으며 단계별 검토 후 진행한다.

## 공통 작업 원칙

- 사실마다 관측 시각·환경·SHA 또는 release·증거·미검증 범위를 남긴다. 문서 수정일과 실제 검증일을 구분한다.
- 구현·로컬 검증·CI·운영 배포·실제 운영자 인수는 각각 판정한다. CI 성공은 해당 SHA에만 적용한다.
- docs는 현행 안내, worklog는 당시 실행 증거다. 과거 실행 결과를 현재에 맞춰 소급 수정하지 않는다.
- 문서 안의 과거 검사 결과는 날짜를 표시하고 최신 결과를 연결한다. 오래된 값을 일괄 치환하지 않는다.
- 운영 release·수량 등 변동값은 운영 상태 문서에서 관리하고 나머지는 필요한 요약과 링크로 연결한다.
- 미정인 URL 입력 권한·보존 기간·실행 PC/OS·시험 자원을 임의 확정하지 않는다. 법무 placeholder·활성화 조건을 유지한다.
- 문서 기록만으로 실제 운영자 인수·Discord·다른 PC·보존 회수·차단 출처를 완료 처리하지 않는다.
- 이후 실행에서는 각 TASK에 변경 파일·검증·잔여사항을 기록한다. 새 결과 파일은 실제 실행 시 작성한다.

## 계획 당시 재개 방법과 완료 조건

1. 저장소 지침·현재 Git 상태를 재확인하고 TASK-01부터 시작한다. 이 계획 작성 후 생긴 변경을 보존한다.
2. 각 TASK의 선행 조건과 원문 근거를 읽고 상태를 진행으로 바꾼 뒤 해당 범위만 수정한다.
3. 실행 결과와 미검증 조건을 기록하고 TASK-07에서 전체 문서의 일치를 확인한다.
4. 문서 최신화 완료와 M0 개발·운영 인수 완료는 별도로 보고한다. 이 계획의 모든 TASK가 끝나도 M0가 자동 완료되지는 않는다.

계획 기록 자체의 검증 결과는 [당시 기록 검증](VALIDATION.md), 이후 문서 최신화·통합 검증은
[실행 결과](RESULTS.md)를 따른다. 문서 최신화 완료는 M0 제품·운영 인수 완료가 아니다.
