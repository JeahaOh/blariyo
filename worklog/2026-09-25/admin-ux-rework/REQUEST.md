- 상태: 요청서 문서화 완료. 이 문서 저장으로 구현·검증을 실행하거나 Goal을 시작한 것은 아니다.

## 실행 프롬프트

Blariyo 관리자 화면 개선 작업을 이어서 구현해줘. Goal 스킬을 사용하고, 작업을 task 단위로 나누어
각 task의 구현과 검증을 수행해. 검증에 실패하거나 완료 조건을 충족하지 못하면 원인을 수정하고
다시 검증해. 계획 제시나 코드 작성만으로 끝내지 말고, 전체 완료 조건을 충족할 때까지 진행해.

### 1. 작업 저장소와 목표

- 저장소: `/Volumes/MicroVault/iCloudDrive/git/private/blariyo`
- 개발 앱: `http://localhost:3000`
- 주요 화면: `/admin`, `/admin/batch`, `/admin/login`
- 사용자가 요청한 개선 범위는 다음 3가지 모두다.
  1. 관리자 화면의 디자인·레이아웃·정보 구분
  2. 목록·상세·버튼 배치와 반복 검수 사용성
  3. 로그인부터 검수·초안 편집·발행까지의 작업 흐름
- 기존 수집 결과의 원문·본문 순서·이미지·외부 링크·SNS를 확인할 수 있어야 한다.
- 기존 관리자 기능과 오류 복구 동작을 유지하면서 사용 흐름을 개선한다.

### 2. Goal 시작 규칙

1. 실행 환경에서 실제 제공되는 Goal 스킬의 `SKILL.md`를 찾아 처음부터 끝까지 읽고 적용한다.
2. 이미 같은 범위의 활성 Goal이 있다면 상태와 남은 task를 확인해 이어서 진행한다.
3. 관련 Goal이 없다면 이번 목표와 완료 조건으로 Goal을 생성한다. 토큰 예산을 임의로 정하지 않는다.
4. 실제 스킬·도구가 지원하는 상태와 호출 규약을 따른다. 존재하지 않는 명령이나 상태를 만들지 않는다.
5. Goal 스킬을 찾지 못하면 적용했다고 보고하지 않는다. 필요한 경로·설치 정보만 질문하고,
   그 답에 의존하지 않는 저장소 확인과 작업 분해는 진행한다.
6. 모든 필수 task와 검증이 완료되기 전에는 Goal을 완료로 표시하지 않는다.
7. 일시적인 테스트 실패나 구현 난도를 외부 차단으로 처리하지 않는다. Goal의 중단·차단·완료는
   실행 환경의 실제 규칙을 따르고, 작업 기록의 task 상태와 구분한다.

### 4. 재개 시 확인할 이전 작업 정보

아래는 이전 대화에서 전달된 상태다. 현재 완료 사실이나 실행 결과가 아니며, 먼저 실제 파일과
현재 개발 앱을 확인해 맞는 부분만 재사용한다.

- Hot 수집 결과를 개발 DB에 저장하고 관리자 목록·상세에서 읽는 검증까지 진행한 기록이 있다.
  과거 수집 수량을 현재 DB의 고정 기대값으로 쓰지 않는다.
- 관리자 화면 계약과 로컬 로그인 관련 코드를 작성했지만, 당시 공통 관리자 레이아웃·검수 화면
  재배치·전체 빌드·브라우저 검증·개발 앱 반영은 남아 있었다.
- 로컬 인증 관련 신규 파일로 다음이 전달되었다.
  - `apps/web/shared/admin-return.ts`
  - `apps/web/server/utils/local-admin.ts`
  - `apps/web/server/api/admin/session.get.ts`
  - `apps/web/server/api/admin/local-session.post.ts`
  - `apps/web/server/api/admin/local-session.delete.ts`
  - `apps/web/app/pages/admin-login.vue`
- 관련 수정 파일은 `apps/web/nuxt.config.ts`, `apps/web/server/middleware/admin.ts`,
  `apps/web/server/plugins/production.ts`, `scripts/local/start-development.mjs`였다.
- 당시 `nuxt.config.ts`에 `~/assets/css/admin.css` 참조가 추가되었지만 CSS 파일 생성은 남아 있었다.
  실제 존재 여부와 빌드 영향을 먼저 확인한다.
- 이미 실행 중인 개발 앱이 최신 소스를 반영했는지는 별도로 확인한다.
- 다른 작업의 변경이 함께 있을 수 있으므로 현재 diff와 작업 소유 범위를 구분한다.

### 5. 작업 범위와 보존 원칙

- 작업 전후 `git status --short --branch`를 확인하고 기존 수정·untracked 파일을 보존한다.
- 기존 API·DB·편집기·컴포넌트·디자인 기준을 우선 재사용한다. 불필요한 프레임워크나 라이브러리를
  추가하지 않는다.
- 개발 DB의 기존 수집 항목·게시글·본문·미디어·검수 상태는 보존한다. 시작 시 읽기 전용으로
  수량·상태·필요한 내용 해시를 기록하고 종료 시 대조한다.
- 승인·반려·초안 생성·수정·발행 등 상태를 바꾸는 테스트는 격리된 테스트 DB와 테스트 저장소에서
  수행한다. 사용자 개발 DB를 테스트 fixture로 재사용하지 않는다.
- 실제 수집 데이터를 자동 승인하거나 발행하지 않는다. DB 초기화·데이터 일괄 삭제를 하지 않는다.
- 인증 비밀·token·세션 쿠키·환경 변수 실값을 화면·URL·로그·문서·스크린샷에 노출하지 않는다.
- 범위 내 source·test·설계·작업 기록을 수정하고, 검증된 새 빌드를 해당 저장소의 개발 앱에 반영한다.
- 로컬 서버 재시작 전 포트·PID·소유 작업을 확인한다. 다른 작업이 사용하는 서버·프로세스에 영향을
  주지 않도록 격리 검증을 우선한다. 공동 사용 중인 서버의 교체가 필요하면 조율한다.
- commit·push·merge·운영 배포·운영 DB 변경은 이번 작업 범위에 포함하지 않는다.
- 합리적인 구현 선택은 정본과 사용자 요청 안에서 직접 결정한다. 단계마다 진행 허가를 다시 묻지 않는다.

### 6. Task 관리와 기록

실행을 시작하면 `worklog/<실행일>/admin-ux-rework/TASKS.md`를 생성하거나 같은 작업의 기존 기록을
이어 쓴다. 날짜가 달라지면 이 요청서를 참조하고 새 실행 기록에 이전 기록 링크를 남긴다.
같은 작업을 session·task의 별도 최상위 경로에 중복 보관하지 않는다.

각 task에는 다음을 기록한다.

- ID, 목표, 선행 task, 변경 대상과 실제 변경 파일
- 완료 조건과 검증 방법
- 실행 명령, 실행 시점, 성공·실패·생략 결과, 증거 경로
- 실패 원인, 수정 내용, 재검증 결과
- 현재 상태, 남은 일, 다음 실행 단계

Task 상태는 작업 기록에서 다음과 같이 관리한다. 이 표기는 Goal 도구의 상태와 별개다.

```text
TODO → IN_PROGRESS → VERIFYING → DONE
                         ↓
                       REWORK → VERIFYING
```

- 완료 조건을 모두 충족하고 증거를 기록한 task만 `DONE`으로 표시한다.
- 테스트를 실행하지 못했거나 생략했다면 통과로 처리하지 않는다.
- 후속 변경이 완료된 task의 동작에 영향을 주면 해당 검증을 다시 연다.
- 외부 입력·권한이 필요한 항목은 차단 원인과 필요한 입력을 기록하고, 독립적으로 가능한 task는 계속한다.
- 기존에 통과한 검사는 새 변경·실패·미해결 우려가 없으면 이유 없이 반복하지 않는다.

### 7. 구현 Task

#### ADM-00 — 현재 상태와 기준선 확인

- Git 상태·기존 변경·관련 소스·현재 실행 앱을 확인한다.
- 이전 인증 코드와 미완성 CSS 참조, 실제 적용된 화면의 차이를 확인한다.
- 관리자 화면의 개선 전 모습을 확인하고 필요한 화면 증거를 남긴다.
- 개발 DB와 미디어를 읽기 전용으로 확인해 보존 대조 기준을 만든다.
- 사용 가능한 검증 명령·테스트 격리 방식·실행 중인 서버 소유 범위를 확인한다.
- 완료 조건: 구현됨·수정 필요·미검증을 구분한 기준선과 ADM-01~07의 실제 실행 계획이 기록되어 있다.

#### ADM-01 — 화면·인증·업무 흐름 계약 정렬

- 관련 planning·보안 설계·관리자·수집 개발 명세를 실제 구현과 대조한다.
- 공통 관리 메뉴, 목록·상세 배치, 모바일 전환, 상태별 행동, 로컬 로그인과 복귀 규칙을 정렬한다.
- 작업 범위 안의 명확한 보완은 직접 반영한다. 기존 출시 차단 조건과 미정 값을 임의로 제거하지 않는다.
- 완료 조건: 구현 기준이 관련 정본 사이에서 충돌하지 않고, 필요한 참조 링크가 유효하다.

#### ADM-02 — 관리자 공통 레이아웃과 스타일

- 관리자 전용 작업 공간에 공통 메뉴·현재 위치·페이지 제목·작업 상태를 명확히 배치한다.
- 관리자 화면에 맞는 가로 폭과 간격을 적용하고, 공통 버튼·입력·상태 표시의 우선순위를 통일한다.
- 일반 사용자 화면과 관리자 화면의 레이아웃 적용 범위를 분리해 공개 화면 회귀를 방지한다.
- `admin.css` 등 필요한 스타일 파일과 실제 참조를 완성한다.
- 데스크톱의 충분한 작업 공간과 모바일의 목록·상세 전환을 제공한다.
- 검증: 1440·1280·768·390·320px 화면, 가로 넘침, 긴 제목·본문, 키보드 탐색과 포커스,
  빌드 및 실제 브라우저 표시를 확인한다.
- 완료 조건: 주요 작업 영역과 버튼이 가려지거나 겹치지 않고 화면 크기별로 조작할 수 있다.

#### ADM-03 — 개발 환경 로그인과 복귀 흐름

- 작성된 로컬 로그인 코드를 검토하고 재사용한다. 파일이 있다는 이유로 안전성·정상 동작을 가정하지 않는다.
- 개발 앱의 `/admin/login`에서 같은 브라우저로 로그인하고 요청한 관리자 화면으로 돌아가게 한다.
- 로그인 여부·실패·로그아웃·재인증 안내를 이해하기 쉬운 문구로 제공한다.
- 미저장 입력이나 응답 미확정 작업 중 인증이 만료되면 내용을 보존하고 재인증 후 이어갈 수 있게 한다.
- 개발 실행기의 명시적 활성화, 비운영 환경, loopback 접속, Host·Origin 일치와 전달 헤더 차단을
  보안 정본에 맞춰 검증한다.
- GET·다른 출처 요청·비활성 설정·운영 환경에서 로컬 세션이 생성되지 않아야 한다.
- HttpOnly·SameSite 등 쿠키 설정, 만료, 허용된 관리자 복귀 경로, 외부 URL 리다이렉트 차단을 확인한다.
- API의 401·403 의미와 운영 Access 인증을 유지한다.
- 완료 조건: 정상 로그인·로그아웃·복귀와 거부 경계를 자동 검사 및 실제 브라우저에서 확인했다.

#### ADM-04 — 수집 목록·상세와 검수 사용성

- 데스크톱에서 목록과 선택한 상세를 함께 볼 수 있게 배치한다.
- 모바일에서 목록→상세→목록으로 이동하고 필터·페이지·선택 항목·포커스를 보존한다.
- 출처·제목·수집 상태·검수 상태·시간을 구분하고 현재 선택 항목을 명확히 표시한다.
- 긴 본문·다수 이미지·SNS·외부 링크를 포함한 실제 수집 내용의 확인 흐름을 정리한다.
- 로딩·빈 결과·권한 오류·통신 오류·이미지 실패·재시도를 처리한다.
- 서버가 지원하지 않는 검색·필터를 동작하는 것처럼 표시하지 않는다.
- 원문·본문 순서·미디어를 임의로 생략하거나 변경하지 않는다.
- 완료 조건: 여러 항목을 연속 확인해도 목록 맥락을 잃지 않고, 각 화면 크기에서 상세와 행동이 연결된다.

#### ADM-05 — 검수에서 초안 편집·발행까지 연결

- 원문 확인→검수→승인 또는 반려→초안 생성→편집→발행 흐름에서 현재 단계와 다음 행동을 보여준다.
- 현재 상태에서 허용되는 행동만 적절한 우선순위로 제공하고 위험한 행동에는 필요한 확인을 유지한다.
- 초안 편집기로 이동한 뒤 원래 수집 항목의 검수 맥락으로 돌아올 수 있게 한다.
- 기존 미저장 이탈 방지, 중복 클릭 방지, 버전 충돌 처리와 응답 미확정 요청의 복구를 유지한다.
- 응답이 불확실한 상태에서는 원래 요청 내용과 중복 방지 키를 보존하고, 같은 요청으로 결과를 확인한다.
- 검증은 격리 환경에서 로그인→검수→승인→초안→편집→발행→공개 확인을 끝까지 수행한다.
- 반려·재검수·중복 초안 방지·연속 클릭·버전 충돌·네트워크 오류·401 후 복구도 확인한다.
- 기존 예약·취소·숨김·재공개 등 관리자 기능은 영향 범위에 맞춰 회귀 검증한다.
- 완료 조건: API·DB·필요한 미디어 결과가 화면 상태와 일치하고 내용 유실·중복 처리·의도하지 않은 공개가 없다.

#### ADM-06 — 통합 검증과 화면 확인

- 변경 범위에 맞는 typecheck·lint·build·단위·통합·브라우저 검사를 실행한다.
- 기존 검사를 보존하고, 새 동작이나 실제 결함을 검증하는 데 필요한 테스트만 보강한다.
- 관리자 인증·검수·편집·오류 복구 검사와 관련 공개 화면 회귀를 확인한다.
- 주요 화면 크기에서 스크린샷을 생성하고 실제 내용을 열어 배치·잘림·겹침·행동 우선순위를 확인한다.
- HTTP 200이나 스크린샷 파일 생성만으로 화면 검증을 통과 처리하지 않는다.
- 검증 로그와 화면 증거는 비밀을 제외하고 실행 기록에서 연결한다.
- 완료 조건: 필요한 검사가 모두 통과하고 필수 시나리오에 실패·미실행·판단 보류가 남아 있지 않다.

#### ADM-07 — 개발 앱 반영과 최종 인수 확인

- 검증된 새 빌드를 해당 저장소의 개발 앱에 반영하고, 필요한 경우 소유가 확인된 로컬 서버만 재시작한다.
- `http://localhost:3000/admin/login`과 `/admin/batch`에서 실제 적용된 화면을 확인한다.
- 같은 브라우저의 로그인·메뉴·필터·목록·상세·이미지를 확인한다. 기존 개발 콘텐츠는 읽기 전용으로 확인한다.
- 개발 DB·게시글·수집 상태·본문·미디어가 시작 기준선과 달라지지 않았는지 대조한다.
  다른 작업에서 발생한 변화가 있다면 근거를 확인하고 이번 작업과 구분한다.
- `git diff --check`와 최종 Git 상태로 변경 범위를 점검한다.
- ADM-00~06의 완료 조건과 증거를 다시 대조하고 남은 결함이 있으면 해당 task로 돌아간다.
- 완료 조건: 새 화면이 실제 개발 앱에 적용되어 있고, 데이터 보존과 전체 필수 검증이 확인되었다.

### 8. 실패·미완료 시 반복 규칙

각 task는 다음 순서로 수행한다.

```text
완료 조건 확인
→ 필요한 구현
→ 정적 검사와 해당 기능 검증
→ 실패 또는 미충족 발견
→ 재현 및 원인 분류
→ 필요한 최소 수정
→ 실패한 검사 재실행
→ 영향받은 인접 기능 검증
→ 증거 기록
→ 완료 조건 충족 시 DONE
```

- 같은 실패가 반복되면 같은 명령만 재실행하지 말고 원인 가설과 확인 방법을 바꾼다.
- 테스트 삭제·skip·검증 조건 완화·근거 없는 timeout 증가로 통과시키지 않는다.
- 데이터 초기화·미디어 제거·인증 비활성화로 문제를 숨기지 않는다.
- 코드 수정, build 성공, 브라우저 통과, 실제 개발 앱 반영은 각각의 증거로 기록한다.
- 내부에서 해결 가능한 오류는 수정한다. 사용자 입력·권한·외부 상태가 실제로 필요한 경우에는
  필요한 항목과 이유를 구체적으로 알리고 독립 작업을 이어간다.
- 사용자 응답을 기다리는 시간이 경과했다고 승인이나 답변을 얻은 것으로 간주하지 않는다.
- 필수 검증이 남았다면 부분 완료·미검증·차단으로 정확히 보고한다. 완료 조건을 낮추지 않는다.

### 9. 진행 공유와 중단 후 재개

- 작업 중 약 60초 이상 설명 없이 진행하지 않는다. 현재 task, 확인된 결과, 다음에 해결할 항목을 짧게 공유한다.
- 상태 질문에는 실제 완료와 미검증을 구분해 답하고, 명시적인 중단 요청이 없으면 진행 중인 작업을 이어간다.
- 장시간 검사는 실행 중임과 확인할 결과를 알린다. 실행되지 않은 검사를 통과로 보고하지 않는다.
- 중단되거나 세션을 옮길 때는 현재 task·변경 파일·실행 중인 프로세스·실패 원인·다음 명령·보존 주의사항을 남긴다.
- 재개할 때 작업 기록과 실제 상태를 대조하고, 끝난 작업을 무조건 처음부터 반복하지 않는다.
- 불필요한 중복 탐색과 검증은 줄이되 필요한 증거는 생략하지 않는다.

### 10. 전체 완료 조건

다음 항목을 모두 충족해야 이번 Goal을 완료로 처리한다.

- 관리자 디자인·레이아웃, 목록·상세·버튼, 로그인·검수·발행 흐름의 3개 개선 범위를 구현했다.
- ADM-00~07의 모든 필수 완료 조건과 검증 증거가 기록되어 있다.
- 데스크톱·태블릿·모바일에서 주요 관리자 작업을 수행할 수 있다.
- 개발 브라우저 로그인과 정상 복귀, 인증 거부 경계를 확인했다.
- 격리 환경에서 검수부터 발행까지 끝까지 수행하고 API·DB·필요한 미디어 결과를 확인했다.
- 충돌·중복 요청·인증 만료·통신 실패 후 복구에서 내용 유실이나 잘못된 상태 전이가 없다.
- 필요한 typecheck·lint·build·기능·브라우저 검사가 통과했다.
- 실제 개발 앱에 최신 구현이 적용된 것을 확인했다.
- 기존 개발 데이터와 다른 작업의 변경을 보존했다.
- 남은 결함·필수 미검증 항목을 숨기지 않았으며, 필수 항목이 남으면 완료로 처리하지 않았다.

### 11. 최종 보고 형식

핵심부터 한국어로 다음을 보고한다.

1. 최종 판정: 완료·부분 완료·미검증·차단 및 판단 근거

3. 직접 확인할 개발 URL과 로그인·사용 순서
4. ADM-00~07별 상태와 증거 경로
5. 실행한 검사, 통과·실패·생략 결과, 브라우저 화면 크기와 화면 증거
6. 기존 DB·본문·미디어·검수 상태 보존 대조 결과
7. 변경 파일과 `git diff --check`·Git 상태, 실제 개발 앱 반영 여부
8. 남은 문제·외부 입력·실제 운영자 인수 등 검증 한계
9. commit·push·운영 배포의 실행 여부

Source 구현, 격리 검증, 개발 앱 적용, 실제 운영자 인수와 운영 배포를 서로 구분해서 보고한다.
