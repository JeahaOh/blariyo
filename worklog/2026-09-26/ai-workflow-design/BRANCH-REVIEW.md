## 판정

**기본 브랜치 전략은 문서에 정의됐다. 릴리스 운영 세칙과 실제 강제 적용까지 완료된 상태는 아니다.**

| 항목 | 확인 결과 |
| --- | --- |
| 개발 흐름 | `feature/<주제영역> → main → release` |
| feature | 기준 main 커밋에서 일반 변경, main 대상 PR |
| main | 개발 결과 통합 |
| release | 선택한 main 커밋의 배포 후보 고정, 승격 PR·후보 검증 |
| 직접 반영 | main·release의 일반 직접 commit·push 금지. 문서·긴급 수정도 자동 예외 아님 |
| 기존 변경 | 도입 당시 미커밋 변경의 보완·기록 가능. Git 반영 전 보존·작업 브랜치 이관 또는 명시적 예외 확인 |
| 공통 작업 방식 | 일반 작업은 worktree 미생성, 예외는 지정한 `.worktree/<주제영역>/`, 모든 작업은 날짜·주제별 worklog |

근거는 [AGENTS.md](../../../AGENTS.md) 76~111행과 [harness 설계](../../../docs/ai/harness.md) 77~104행이다.
아래 보완안은 검토 제안이며 새 운영 규칙으로 확정하거나 실제 적용하지 않았다.

## 남은 설계 보완

### B1 — Medium: 선택한 후보 커밋을 PR·병합 결과·이미지에 연결하는 방법이 미정

- 근거: `AGENTS.md:103`, `docs/ai/harness.md:92`, [.github/workflows/ci.yml](../../../.github/workflows/ci.yml) 110·138~145행.
- 확인: 선택한 main 커밋을 기준으로 승격한다고 정했지만, PR의 소스 기준을 고정하는 방법과 병합 방식은 없다.
  feature→main 및 main→release에서 사용할 병합 방식, 최종 검증 SHA와 이미지 식별값의 대응도 명시되지 않았다.
- 영향: main이 계속 변경되는 동안 어떤 시점까지 후보에 포함하는지 작업자 판단에 맡기게 된다.
  병합 방식에 따라 최종 SHA가 달라지면 기존 검사·이미지를 어느 후보의 증거로 사용할지도 불명확하다.
- 최소 보완: 선택 SHA, PR 소스 고정 방법, 병합 방식, 후보 변경 시 재검증 조건,
  실제 배포할 SHA·이미지 digest의 대응을 운영 정본 한곳에 규정하고 AGENTS에서 연결한다.

### B2 — Medium: 동결 중 결함 수정·운영 긴급 수정의 경로가 미정

- 근거: `AGENTS.md:101`~109, `docs/ai/harness.md:90`~99.
- 확인: release의 역할과 직접 수정 금지는 있지만 동결 기간의 허용 변경, 결함 수정 브랜치의 기준점·PR 대상,
  운영 긴급 수정의 기준점·main 재반영·완료 조건은 없다. 직접 반영을 자동 예외로 보지 않는 규칙 자체는 명확하다.
- 영향: release가 고정된 동안 main에 다음 기능이 쌓이면 결함 하나를 고칠 때 다음 기능까지 함께 승격하거나,
  수정이 main에 누락되는 경로를 막을 운영 절차가 부족하다. 실제 사고를 재현했다는 의미는 아니다.
- 최소 보완: 일반 후보 수정과 운영 긴급 수정의 출발점·PR 방향·재검증·main 재반영을 각각 정한다.
  운영 긴급 수정의 기준은 현재 배포 식별자로 확인하며 release HEAD와 같다고 가정하지 않는다.

## 실제 적용 상태와 전환 선행 조건

아래는 현재 문서가 이미 구분한 미적용 범위다. 새로 발견한 구현 실패나 원격 보호 부재로 판정하지 않는다.

- 로컬 main은 `e51f1b5`, release는 `e2a6240`이며 `git rev-list --left-right --count main...release`는 `8 2`다.
  main에만 있는 변경에는 관리자 UX·분석 구현이 있고, release에만 있는 두 커밋은 거버넌스 기록 정리와 M0 현황 문서다.
  양쪽을 대조·보존하는 전환 순서가 필요하다. 이 조회는 원격 최신 상태를 증명하지 않는다.
- [CI](../../../.github/workflows/ci.yml) 3~6행은 PR·main push·수동 실행이며,
  110행의 이미지 게시 조건은 main이다. release push에 연결된 후보 검증·게시 경로는 현재 source에 없다.
  [배포 정책](../../../docs/operations/deployment-policy.md) 43~44행도 검증된 main 이미지와 digest 배포를 규정한다.
  후보 확정 방식과 CI·운영 문서의 전환은 함께 설계해야 한다.
- `git config --show-origin --get core.hooksPath`는 미설정(exit 1)이고,
  이전 `.git/harness-hooks/pre-commit` 파일은 없으며 기본 hooks 폴더에도 sample 외 파일이 없다.
  현재 로컬 hook 연결 상태를 확인한 것이며 hook을 설치하거나 실행하지 않았다.
- 원격 보호 규칙·필수 검사·직접 push 거부 동작은 조회·시험하지 않았다.
  세 AI의 실제 새 세션 로딩·준수와 harness 자동 강제 적용도 검증하지 않았다.
- 과거 거버넌스 기록은 보관·폐기 이력이다. 이전 develop 중심 설계나 보관된 구현을 이번 목표의 실행 기준으로 되살리지 않는다.

  애플리케이션 source를 변경하지 않았으며 애플리케이션·브라우저·운영 검증은 실행하지 않는다.
