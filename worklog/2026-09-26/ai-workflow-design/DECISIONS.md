## 사용자가 확정한 기준

### 브랜치

- 흐름은 `feature/* → main → release`로 한다.
- `feature/*`는 작업, `main`은 개발 결과 통합, `release`는 배포 후보 고정에 사용한다.
- `release` 승격과 실제 운영 배포는 별도 단계로 구분한다.

### Worktree

- 일반 작업에서는 별도 worktree를 만들지 않는다.
- 복잡한 공통 영역이나 아키텍처 변경에서 격리가 필요한 경우에만 사용한다.
- 사용 시 기본 프로젝트 루트 아래 `.worktree/<주제영역>/`에 생성한다.
- 고정 기준 경로: `/Volumes/MicroVault/iCloudDrive/git/private/blariyo/.worktree/<주제영역>/`.
- worktree 안에서 추가 worktree를 만들 때도 기준 경로는 위 기본 프로젝트 루트다.
- 주제영역 이름을 사용하며 AI 이름이나 세션 이름을 디렉터리의 주제로 삼지 않는다.
- 이 결정은 앞선 설계안의 '작업마다 독립 worktree 생성' 제안을 대체한다.

### 작업 기록

- 작업 기록은 작업 크기와 관계없이 반드시 `worklog`에 생성한다.
- 경로는 `worklog/YYYY-MM-DD/<주제영역>/`로 한다.
- 이 결정은 앞선 설계안의 '작은 작업은 기록 파일 생략 가능' 제안을 대체한다.

## 함께 적용할 것을 권장하는 세부 규칙

아래 항목은 이번 검토의 제안이며 사용자 확정·구현 완료로 표시하지 않는다.

1. 기본 프로젝트의 `/.worktree/`를 Git 추적과 기본 프로젝트 기준 검색·빌드·검사에서 제외한다.
   해당 worktree를 작업 루트로 선택했을 때는 그 안의 source를 정상 검사한다.
2. 주제영역 이름은 `auth-contract`, `collector-architecture`처럼 짧은 소문자·하이픈 형식을 사용한다.
   같은 경로가 있으면 담당·브랜치·기존 변경부터 확인하고 덮어쓰거나 임의 재사용하지 않는다.
3. worktree 사용 시 기록도 해당 worktree의 `worklog/YYYY-MM-DD/<주제영역>/`에 작성한다.
   코드와 기록을 같은 작업 브랜치에서 관리하고 병합을 통해 기본 작업 폴더에 반영한다.
4. 날짜는 한국 시간의 실제 작업일로 한다. 날짜가 바뀌면 같은 주제영역의 새 날짜 기록을 만들고
   이전 기록과 작업 ID를 연결한다. 과거 결과를 현재 결과로 소급 덮어쓰지 않는다.
5. 작은 작업은 기록 파일 하나로 충분하다. 요청·변경 또는 검토 결과·검증·잔여 사항을 기록한다.
   비밀과 개인정보 원문은 기록하지 않으며 수행하지 않은 검증은 미실행으로 표시한다.
6. 일반 작업은 같은 작업 폴더에서 수정 담당 한 명을 두고 순차 처리한다.
   다른 세션의 수정·검증 중 브랜치 전환과 동시 Git 변경을 피한다.

## 브랜치 흐름 변경

후속 사용자 지시에 따라 일반 흐름을 `feature → release → main`으로 바꾼다.
feature→release는 CLI 병합을 허용하고 release→main은 GitHub 웹 GUI로 병합한다.
긴급 수정은 main에서 `hotfix-*`를 만들고 main에 반영한 뒤 main→release→진행 중 feature 순서로 전달한다.
이 결정은 위 최초의 feature→main→release 결정을 대체하며, 과거 결정·검토 결과는 당시 이력으로 남긴다.

- 현행 절차: [Git workflow](../../../docs/ai/git-workflow.md), 공통 요약: [AGENTS.md](../../../AGENTS.md).
- 이번 변경·적용 한계·검증: [브랜치 전략 변경 기록](BRANCH-STRATEGY.md).
- GitHub 설정·hook 설치·실제 병합과 배포는 수행하지 않는다. 문서 반영과 강제 적용은 별도다.
