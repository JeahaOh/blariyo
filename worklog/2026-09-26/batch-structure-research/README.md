## 1. 다음 세션이 먼저 읽을 판단

**세션 마지막 추천은 “현재 M0 마무리 → 실제 부하 측정 → 필요하면 짤 게시판에 선택적 캐시 추가”다.**
이 순서는 검토 의견이며, 승인된 로드맵이나 추가 필수 과제가 아니다.

- 게시판별 캐시 정책을 두는 방향은 장기적으로 유용할 수 있다. 읽기 집중도가 높고 변경이 적은 공개 데이터에 특히 적합하다.
- 지금 파일 캐시·서버 증설·스크래퍼 이전을 한꺼번에 진행할 근거는 부족하다. 실제 병목과 절감 효과는 미측정이다.
- 기존 API 응답 형식과 DB 조회 경로를 유지하면서 캐시를 선택적으로 추가하는 방향을 추천했다. 전면 재설계는 권하지 않았다.
- 대화 중 **Lightsail 4GB 한 대에 Web/API/DB/배치를 통합**하는 안을 추천한 시점이 있었다. 이후에는 **운영 단순화를 위한 후보이며 즉시 도입 추천은 보류**하는 것으로 의견을 조정했다. 중간 추천만 인용해 확정안으로 처리하지 않는다.
- **스크래핑 배치와 캐시 생성 작업은 별개다.** 캐시 생성 작업을 API 서버에 두면 파일을 공유할 수 있으므로, 파일 캐시 때문에 스크래퍼까지 같은 서버로 이동할 필요는 없다.
- 캐시를 도입하더라도 PostgreSQL이 원본이고 JSON은 다시 만들 수 있는 사본이다. 파일 자체를 서비스 데이터의 정본으로 바꾸자는 제안이 아니다.

- 동시 실행 1개, 중복 실행 방지, 재시도 상한, 자원 제한, 정상 종료·재개는 후보 운영 조건이다. Discord 명령 접수의 상시 실행 여부도 수집 시간표와 별도로 판단해야 한다.
- 빌드·테스트는 기존 GitHub Actions 흐름을 유지하는 방향을 논의했다. 이미지 게시와 실제 운영 배포는 별개다.
- Jenkins 설치 자체가 무중단 배포를 제공하지 않는다. 사용자 의견에 따라 무중단 배포 설계를 이번 검토의 선행 조건으로 두지 않는다.

## 4. IP·DB 연결과 비용에 관한 논의

### 연결 후보

- **같은 호스트:** Docker 내부 네트워크로 API·DB를 연결하고, 캐시 생성 작업과 API가 같은 파일 볼륨을 사용한다. 서로 다른 컨테이너에 같은 경로 문자열을 적는 것만으로 파일이 공유되지는 않는다.
- **같은 계정·리전의 별도 Lightsail:** 사설 IP 연결을 후보로 검토했다. 현재 PostgreSQL Compose의 내부 연결을 그대로 외부 서버에서 사용할 수 있다고 가정하지 않는다. 접속 지점·DB 역할·호스트 접근 제어·암호화 연결의 추가 검토가 필요하다.
- **집의 Raspberry Pi:** Tailscale, Cloudflare의 사설 연결 기능, 제한된 SSH 터널 등을 후보로 논의했다. 운영 DB를 인터넷 전체에 공개하는 안으로 정리하지 않았다.
- **Tailscale:** 무료 여부는 이용 목적·요금제·조건에 따라 확인해야 한다. 개인용 무료 조건을 서비스 운영에 자동 적용하거나 영구 무료로 단정하지 않는다.
- **Cloudflare:** 현재 공개 웹용 Tunnel 설정이 곧 Raspberry Pi의 DB 접속 경로를 제공하는 것은 아니다. 사설 DB 연결에는 별도 구성 검토가 필요하다.
- **NordVPN:** 사용자는 고정 IP를 보유한다고 밝혔다. 이를 접속 출발지 허용 목록에 활용하고 제한된 SSH 터널로 연결하는 안을 논의했다. 고정 출발지 IP만으로 두 장비의 사설 연결이 완성되지는 않는다. Raspberry Pi의 해당 기능 지원, 라우팅, 재연결과 장기 터널 운영은 미검증이다.
- 원격 배치는 최소 권한의 별도 DB 계정을 사용하는 방향이다. 실제 주소·포트·자격 증명·네트워크 정책은 이 기록에 기재하거나 설정하지 않았다.

다음 금액은 **세션 중 공식 문서를 조회해 비교한 Linux/public IPv4 일반형 정가**다.
실제 계정 청구액이나 향후 가격을 확정한 것이 아니며, 채택 시 재조회해야 한다.

| 비교 | 세션에서 사용한 기본 월 정가 |
| --- | --- |
| Lightsail 2GB 한 대 | $12 |

- “2GB면 무료, 4GB부터 유료”로 정리하지 않는다. 무료 플랜·크레딧의 계정별 조건과 일반 정가는 별개다.
- 세금·스냅샷·초과 전송·기타 서비스·계정 크레딧은 위 비교에 포함하지 않는다. 과거 운영 기록의 크레딧 잔액을 현재 잔액으로 사용하지 않는다.

## 5. JSON 캐시를 도입한다면 검토할 처리 흐름

**아래는 미구현 후보 흐름이며 현행 API 동작 설명이 아니다.**

1. API가 게시판별 캐시 사용 여부와 요청의 캐시 대상 범위를 판단한다.
2. 대상 범위 안이고 현재 공개 상태·허용 버전에 맞는 정상 JSON이 있으면 사용한다.
3. 캐시가 없거나 무효·손상·읽기 실패이면 DB에서 응답을 만든다. 캐시 대상 밖이면 처음부터 DB를 조회한다.
4. 본문과 목록을 각각 조회한 뒤 기존 API 응답 형식으로 조합한다. Web은 그 응답으로 HTML을 렌더링한다.
5. 초기 후보에서는 **파일 생성은 별도 캐시 생성 작업이 담당**한다. API의 모든 캐시 누락 요청이 파일을 생성하는 방식은 제안하지 않았다.

논의한 설정 예시는 `목록 사용 여부`, `상세 사용 여부`, `목록 페이지 범위`, `상세 최근 N개`다.
이는 DB 필드명이나 migration 계약이 아니다. 관리 UI를 만들지, 운영 설정으로 시작할지도 미정이다.

- 목록과 본문은 독립적으로 켤 수 있어야 한다. 상세 파일에 하단 목록까지 영구 고정하면 두 설정이 결합되므로 피하는 방향이다.
- 최근 N개는 캐시에 미리 넣어두는 권장 수량이 아니라 **캐시를 사용할 수 있는 대상 범위**로 논의했다. 범위 밖 파일이 남아 있어도 응답에 사용하지 않는다.
- 이미지 원본을 JSON에 복제하는 제안이 아니다. 기존 공개 응답에 필요한 데이터만 캐시하는 방향이다.
- 응답별 요청 식별자나 사용자별 정보까지 공용 JSON에 고정하지 않는다.
- **JSON과 HTML은 별개다.** API 데이터를 JSON으로 캐시하고 Nuxt가 HTML을 만들 수 있다. HTML 파일 전체를 사전 생성하는 구조는 이 검토의 마지막 추천에 포함하지 않았다.
- 초기의 S3 JSON 직접 제공·없을 때 API 요청 아이디어보다, 후속 대화의 **API 내부 파일 읽기·DB 대체 조회·목록/상세 CDN 미사용**을 검토 전제로 삼는다.
- PostgreSQL의 공유 버퍼와 OS 캐시는 DB 접근 비용을 줄이지만 애플리케이션 응답 JSON을 자동 생성·갱신하는 기능은 아니다. materialized view도 저장된 조회 결과와 갱신이 필요한 DB 기능이며 별도의 후보일 뿐이다.
- 파일 접근을 조회 로직과 분리하면 향후 Redis·MongoDB 등을 검토하기 쉬워진다. 단, 저장소마다 원자적 교체·만료·오류 처리 방식이 다르므로 단순 설정 변경만으로 완전 호환된다고 약속하지 않는다.

## 6. 공개 상태와 갱신에서 남은 설계 문제

캐시 존재 여부만 검사하면 숨겨진 글이나 이전 목록을 응답할 수 있다. 특히 **JSON이 없을 때만 공개 상태 버전을 확인**하는 방식은 이미 존재하는 오래된 파일을 막지 못한다.

| 문제 | 검토 방향 | 미결정·검증 사항 |
| --- | --- | --- |
| 실제 발행 | 수집 결과 검수 승인은 초안 승격이며 공개 발행과 구분. 실제 발행·예약 발행 시 공개 캐시 갱신 | 발행과 무효화·생성 작업 연결 방식 |
| 숨김·삭제 | 기존 캐시 사용을 즉시 막고 DB 경로로 전환한 뒤 재생성 | DB 저장 완료와 캐시 차단 사이의 경쟁 상태 해결 |
| 오래된 생성 작업 | 숨김 전 시작한 작업이 뒤늦게 파일을 내놓아도 다시 노출되지 않아야 함 | 버전·세대 검사와 게시 허용 절차 |
| 최근 N개·페이지 이동 | 새 글 발행 등으로 목록 구성과 대상 집합을 함께 갱신 | 정렬 기준, 고정글, N번째 경계, 상세의 현재 목록 페이지 |
| 설정·게시판 상태 변경 | 캐시 OFF, 범위 축소, 게시판 비활성화도 기존 파일보다 우선 | 정책 반영과 파일 정리의 순서 |
| 여러 파일 교체 | 임시 파일 완성 후 교체하고 완성된 묶음만 사용 | 단일 파일 교체만으로 DB와 모든 파일의 일관성이 해결되지는 않음 |
| 조회수 | DB 기록은 유지하고 본문 캐시와 표시 값을 분리하는 방향 | 표시 지연 허용 범위와 별도 값 갱신 방식 |
| 장애·재시작 | 캐시가 손상되거나 신뢰할 상태를 확인할 수 없으면 DB로 대체 | 재생성 재시도, 초기 상태, 오류·지연 관측 |

- 현재 제품 계약은 **숨김 commit 이후 시작된 조회에서 목록 제외·상세 404**다. 단순한 비동기 파일 삭제만으로 이 계약을 충족했다고 판단하지 않는다.
- 캐시 조회마다 DB에서 글 순위·버전을 다시 계산하면 읽기 부하 절감 효과가 줄어들 수 있다. 로컬 정책·대상 집합·버전을 사용할 경우에도 갱신과 재시작 시의 신뢰성을 먼저 해결해야 한다.
- 조회수는 캐시 도입의 절대적 장애물은 아니다. 다만 DB 쓰기는 남고, 화면의 조회수를 얼마나 늦게 표시해도 되는지 결정해야 한다.
- 대화 중 나온 **조회수 표시용 데이터 1분 갱신**은 어시스턴트가 제시한 초기 예시다. 사용자가 승인한 주기나 현재 동작이 아니다.
- 캐시를 써도 Web의 HTML 생성, 조회수 기록, 검수·발행 DB 작업은 남는다. 전체 서버 부하나 서버 비용이 특정 비율로 감소한다고 추정하지 않는다.
- API 인스턴스가 여러 대가 되면 로컬 파일 공유·무효화가 추가 문제가 된다. 파일 캐시는 초기 단일 호스트 후보이며 장기적으로 공유 저장소가 필요한지는 그때 검토한다.
- 일반 참고: [Cache-Aside 패턴의 적합 조건과 일관성 한계](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside). 해당 문서의 요청 시 캐시 채우기 예제를 이번 후보 흐름에 그대로 채택한 것은 아니다.

## 7. 현행 설계와의 차이 — 자동 반영 금지

아래는 문서화 시점에 확인한 정본·소스다. 다른 세션의 구현이 진행 중이므로 후속 작업 전에 다시 읽는다.
운영 서버·계정·실제 트래픽을 이번 문서화에서 확인한 것은 아니다.

| 현행 근거 | 현재 기준 또는 구현 | 이 검토안과의 관계 |
| --- | --- | --- |
| [서비스 계획](../../../docs/planning/01-service-plan.md) | M0 게시글 API·HTML 무캐시, 숨김 후 새 조회 차단 | JSON 캐시 채택 시 변경이 필요한 핵심 계약. 지금 변경하지 않음 |
| [인프라 계획](../../../docs/planning/02-infra-plan.md) | Lightsail 2GB, 실측에 따른 증설 검토, 무중단 배포 제외 | 4GB와 서버 재배치는 미채택 후보 |
| [수집 설계](../../../docs/system-design/07-spring-collector-design.md) | 별도 컴퓨터의 Java direct batch, API의 검수·초안 승격·발행 책임 | 같은 서버로 통합됐다고 해석하지 않음 |
| [데이터 모델](../../../docs/system-design/02-data-model.md) | 게시판 모델과 기존 데이터·outbox 계약 | 캐시 설정·생성·무효화 계약은 별도 검토 필요 |
| [API 설계](../../../docs/system-design/03-api-design.md) | 목록·상세·조회수와 상세 하단 목록 계약 | 응답 형식은 가능한 한 유지하는 방향 |
| [공개 조회 서비스](../../../apps/api/src/features/public/public.service.ts) | repository를 통한 목록·상세 조회와 별도 조회수 처리 | 캐시 적용 완료의 증거가 아님 |
| [공개 조회 구현](../../../apps/api/src/persistence/public.repository.ts) | 공개 상태 조건을 포함한 DB 조회·조회수 증가 | 읽기 캐시 후에도 기록 경로 검토 필요 |
| [회원·커뮤니티 설계](../../../docs/system-design/06-member-community-design.md) | 회원·커뮤니티 읽기·개인 상태 및 캐시 정책 | 짤 캐시를 익게에 자동 확대하지 않음 |

실제로 채택한다면 게시판 설정, 읽기 경로, 발행·숨김 처리, 오류 처리와 경계 검증이 필요하다.
단순히 설정 필드 네 개를 추가하는 변경은 아니지만, Web/API/DB를 전면 재작성해야 하는 제안도 아니다.
제품 계획·기술 설계·기능 명세와 구현을 함께 맞추는 후속 작업이며, 이 기록만으로 그 작업을 개시하지 않는다.

## 8. 재검토에 필요한 근거와 미정 사항

후속 요청이 있을 때 판단 자료로 사용할 목록이다. **승인된 구현 task나 자동 실행 목록이 아니다.**

1. 목록·상세 API의 응답 시간과 DB 조회 시간, 반복 조회가 집중되는 페이지·글 범위.
2. 배치 실행 중 API 지연, CPU·최대 메모리·DB 연결·쓰기 부하, 출처별 수집 성공과 소요 시간.
3. Raspberry Pi 또는 클라우드 후보 환경에서의 실제 실행 가능성. 1시간 처리와 4GB 수용 가능성은 미검증.
4. 캐시 범위·정렬·고정글 처리·설정 관리 방식, 조회수 표시 지연 허용치: **미정**.
5. 숨김 즉시 차단, 생성 작업 경쟁, 목록/상세 독립 설정, 10/11페이지·200/201번째 경계, 파일 손상·재시작 시 대체 조회 검증.
6. 서버 통합·분리, 스케줄러, 원격 DB 연결, 증설 여부와 실제 계정 비용: **미정**.

## 9. 이번 기록 작업의 검증과 적용 범위

- 완료 대상은 **이 세션의 대화 기록**이다. 캐시 설계 확정·구현·성능 개선·운영 적용을 완료로 보고하지 않는다.
- 현행 정본의 무캐시·숨김 차단·2GB 실측 증설 기준과 이 문서의 후보 의견을 구분했다.
- 검증: 상대 링크 10개 대상 존재 확인, 검토안·최신 추천·날짜 구분·201번째 처리·자동 구현 금지 문구 확인.
- 범위 한정 `git diff --check`, 신규 파일의 `git diff --no-index --check` 진단과 직접 공백 검사에서 오류 없음. 작업 전후 상태 비교에서 이 문서 경로만 추가됐고 HEAD는 동일하다.
- 앱 테스트·성능 측정·실제 DB/외부 사이트 접속·계정 청구 조회는 이 문서화 작업에서 실행하지 않는다.
- 제품·기술 정본, 소스·migration·배포 설정, 과거 기록은 변경하지 않는다. 서버 생성·증설·배포·commit·push도 수행하지 않는다.

> **다음 세션 인계:** 이 파일은 검토안 보관본이다. 사용자에게 별도의 채택·변경 요청이 없으면
> 현행 M0 작업에 캐시·서버 이전·Jenkins·Redis 등을 추가하지 않는다. 새로운 결정이 생기면 정본과
> 후속 기록에 반영하고, 이 문서의 과거 의견을 당시 확정 사실로 바꾸지 않는다.
