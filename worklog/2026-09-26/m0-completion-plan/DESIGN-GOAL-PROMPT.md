# M0 설계 보완 실행용 goal 프롬프트

이 파일은 **설계 보완 실행에 사용한 요청문**이다. 최초 작성 당시에는 goal을 시작하지 않았다.
작업별 상세 범위와 완료 조건은 [DESIGN-TASKS.md](DESIGN-TASKS.md)에 있다.

2026-09-26 후속 결과: 이 설계 goal은 [실행 기록](../m0-design-completion/README.md)의 조건으로 완료됐다.
아래 요청문은 실행 당시 범위를 보존한다. 다음 구현에 이 설계 전용 요청문을 그대로 사용하지 않는다.

```text
목표: Blariyo M0 기존 설계의 변경 사항을 반영하고 미결 기술 계약을 마감한다.

이 목표를 goal로 수행해줘. M0 기본 설계는 이미 있으므로 처음부터 다시 설계하지 말고,
최근 사용자 결정과 기존 미결 계약에 필요한 문서만 보완해줘.
단순 검토나 제안으로 끝내지 말고 아래 범위의 관련 정본·개발 명세를 직접 작성·수정하고
문서 검증과 구현 인계까지 완료해줘. 애플리케이션 구현은 이번 goal 범위가 아니야.

0. 실행 제어 규칙

1) Scope Lock
   요청 범위 밖 작업 금지.

2) Done Criteria
   시작 전에 완료 조건 명확화. DESIGN-TASKS.md의 작업별 조건과 공통 완료 조건을
   기준으로 산출물·검증 방법을 실행 기록에 명시한 뒤 작업한다.

3) Retry Budget
   동일 문제 최대 2회. 최초 시도를 포함해 2회까지 시도하고, 해결되지 않으면
   blocked로 종료한다. 명령이나 표현을 바꿔 같은 문제의 횟수를 초기화하지 않는다.

4) Progress Guard
   2회 연속 실질적 진전 없으면 중단한다. 시도마다 산출물·검증 근거·차단 요인 해소의
   변화를 기록한다. 같은 조회·실패·설명을 반복한 것은 진전으로 계산하지 않는다.
   2회 연속 진전이 없으면 blocked로 종료한다.

5) Hard Stop
   완료 / blocked / 사용자 판단 필요 중 하나가 되면 더 이상 continuation하지 말고
   종료한다. 완료는 개별 task가 아니라 이번 goal 전체의 완료 조건 충족을 뜻한다.
   종료 상태·근거·남은 작업·재개 조건만 보고하고 자동 재시도·대기·범위 확장을 하지 않는다.

아래의 자율 진행 지시도 이 실행 제어 규칙 안에서 적용한다.

1. 착수와 기준

- 저장소 루트 AGENTS.md, docs/ai/README.md와 적용되는 프로젝트 스킬을 먼저 읽어줘.
- git status --short --branch로 브랜치·기존 변경을 확인하고, 공유 폴더의 진행 중 담당을
  확인해줘. 기존 사용자·다른 세션 변경은 보존하고 브랜치나 작업 폴더를 임의로 옮기지 마.
- worklog/2026-09-26/m0-completion-plan/DESIGN-TASKS.md를 작업 목록으로 사용해줘.
  같은 폴더 README.md는 결정 경위이고 현행 제품·기술 사실은 정본에서 재확인해줘.
- docs/status.md, docs/roadmap.md, 관련 planning/system-design/development-specs,
  실제 source·migration을 대조해 현재 계약과 보완 부분을 구분해줘.
- 실행 기록은 실제 KST 작업일의 worklog/YYYY-MM-DD/<주제영역>/에 남겨줘.
  담당·작업 폴더·브랜치·변경 경로·상태·갱신 시각을 기록하고 이 작업 목록을 연결해줘.
  이전 작업 기록은 덮어쓰지 마.

2. 이미 확정한 정책

- batch 소유 수집 이미지·첨부·원문 HTML·본문은 검수 완료·반려 시점부터 7일 후 삭제한다.
- 미검수 수집 자료는 수집일부터 28일 보관한다.
- 중복 방지용 최소 식별자는 무기한 보관한다. 앞선 식별자 1년 보관안은 철회했다.
- API 소유 게시글 사본과 수집 원본을 구분한다. 게시글 사본은 기존 콘텐츠 정책을 유지한다.
- 운영 DB는 PostgreSQL, 공개 전·공개 이미지/첨부는 R2, DB 백업만 Google Drive다.
- 기존 백업의 dump→age 암호화→SHA-256 manifest, 03:30·15:30 KST 일정과 최근 7일
  보존을 유지한다. Drive 검증 전 기존 정상 백업을 중단하지 않는다.
- M0에는 검증된 출처만 포함한다. 21개 adapter 존재나 과거 17개 저장 성공은
  운영 검증 통과를 뜻하지 않는다.
- 서버·DB 관리·백업·복구는 사용자만 담당한다. 친구는 게시물 업무 권한만 갖는다.
- 장애 알림은 Discord다. 채널 생성·사용자만 참여는 확인된 사용자 보고이고 실제
  연결·실수신은 별도 검증 대상이다. 친구 초대를 필수로 만들지 않는다.
- 출처 설정 초기 설계는 개발자에게 위임했다. 실제 설정의 읽기 전용 조회를 우선한다.
- 청록색 #00A19B는 유지한다. 수집 장비는 미정이며 RPi4는 후보일 뿐이다.

3. 수행할 작업

DESIGN-TASKS.md의 세부 산출물·완료 조건을 따라 다음 6개 작업을 수행해줘.

- M0-D01: 최소 중복 키, 검수/수집 시각과 만료, 재검수·동시 처리, 삭제 소유권과 권한,
  사본·report/queue·임시 파일 처리, 백업 복원 후 만료 재적용을 설계한다.
- M0-D02: Web URL 요청을 batch로 전달하는 두 기존 대안을 비교해 한 가지를 선택한다.
  API/Web 외부 fetch 금지와 batch queue/item 소유권을 유지하며 접수·중복·확인·재시도·
  상태 조회 및 실제 출처 설정의 읽기 전용 API·화면 계약을 확정한다.
- M0-D03: Drive 인증의 계정별 적용 조건, 업로드·파일 식별·재시도·만료 정리,
  독립 다운로드/해시/격리 복원·Discord 장애 알림·전환/되돌리기 조건을 설계한다.
- M0-D04: 사용자·친구·서비스 계정의 행동별 권한을 기존 접근 통제에 매핑하고
  허용/거부 시험을 정의한다. 새 권한 관리 화면이나 범용 프레임워크는 추가하지 않는다.
- M0-D05: M0 출처 편입 기준과 현재 증거표를 작성한다. 기존 증거의 시점·환경·한계를
  명시하고 증거가 부족한 출처는 후보/미검증으로 둔다. 실제 재수집은 실행하지 않는다.
- M0-D06: 정본·개발 명세·OpenAPI·상태/로드맵·기존 구현 task의 모순을 해소하고
  설계 결정→문서 절→구현 task→검증 시나리오의 인계표를 작성한다.

기술 선택은 확정 정책 안에서 직접 결정하고 대안·선택 이유·운영 영향·되돌리기 조건을
남겨줘. 비교표만 만들고 필수 계약을 미정으로 남기지 마.
설계 때문에 필요한 migration과 테스트는 명세로 작성하고 실행 파일이나 제품 코드는
작성하지 마. 기존 UX·COL·OPS·CON 식별자를 유지하며 후속 구현 순서에 연결해줘.

4. 문서 변경 범위

- 주 대상은 DESIGN-TASKS.md에 연결된 docs/system-design/와 관련
  docs/development-specs/ 문서 및 OpenAPI다. 새 문서는 기존 문서에 수용하기 어려운
  경우에만 추가하고 정본 진입점에서 연결해줘.
- 이미 확정된 정책 반영과 일관성 유지에 필요한 planning, implementation-tasks,
  status/roadmap, 운영 준비 문서도 필요한 부분만 수정해줘.
- 법무 영향은 관련 미발행 추가안·안내에 반영하고 발행본, 실제 법무 검토,
  출시 차단 해제를 완료로 처리하지 마. 확인되지 않은 실값은 만들지 마.
- 현행 구현과 목표 설계를 구분해줘. 기존 R2 백업 구현을 Drive 적용 완료로 쓰지 마.
- 독립적인 Core UX 구현이 이 설계 전체를 기다려야 한다고 범위를 확대하지 마.

5. 자율 진행과 경계

- 확정된 정책을 재질문하지 말고, 정책 안의 필드·상태·권한·실패 처리 등 기술 선택은
  직접 정해줘. 장비/OS/가동 시간, Drive 계정 종류·용량, Discord 연결값은 적용 조건과
  실연동 전 확인 항목으로 분리해 문서 설계를 계속해줘.
- 새 정책 결정이 정말 필요한 충돌이 발견되면 근거와 구체적인 선택지만 제시하고,
  사용자 판단 필요 상태로 종료해줘. 답을 기다리며 다른 작업을 계속하거나 자동으로
  continuation하지 마. 원본 삭제와 백업 보존의 충돌을 임의 유예나 무기한 보관 예외로
  해결하지 마.
- 외부 서비스 사양이 선택에 필요하면 공식 문서를 확인하고 출처·확인일을 남겨줘.
  계정 접속·설정 변경·비밀 값 읽기/기록·Drive 업로드·Discord 전송은 수행하지 마.
- 애플리케이션 source·migration·실행 설정을 수정하거나 DB/object에 쓰고 삭제하지 마.
  운영 연결·수집 활성화·배포 및 stage·commit·push·merge도 수행하지 마.
- COL-REANALYZE-01의 에펨코리아·뽐뿌·유튜브 커뮤니티 재분석은 대기 유지해줘.
  PGR21을 이 task에 추가하거나 사이트에 새 요청을 보내지 마.

6. 검증과 종료

- planning·system-design·개발 명세·OpenAPI·관련 legal 문서 사이의 정책·필드·상태·
  권한·저장소·보존기간 일치 여부를 검사해줘.
- 상대 링크·참조 파일·변경된 anchor, git diff --check와 의도한 파일만 변경됐는지
  확인해줘. OpenAPI를 변경했다면 저장소의 문서 검증 방법으로 계약 형식도 검사해줘.
- D01~D06 각각에 결과·근거 파일/절·문서 검사·후속 구현/운영 검증을 남겨줘.
- 필수 기술 계약을 문서화하고 문서 검증·구현 인계까지 끝났을 때 goal을 완료해줘.
  실제 계정값·장비 선택은 명시한 적용 조건과 후속 확인 시점으로 분리할 수 있지만,
  해결되지 않은 정책 충돌이나 필수 기술 선택을 완료로 표시하지 마.
- 최종 답변에는 보완한 설계, 변경 파일, 검증 결과, 구현 순서, 실연동 직전 필요한
  입력만 간결하게 보고해줘. 설계 완료를 M0 구현·운영 인수 완료로 표현하지 마.
```
