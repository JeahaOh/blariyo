# M0 기존 설계 보완 작업 목록

- 작성일: 2026-09-26 KST.
- 목적: 기존 M0 설계에 최근 확정 정책을 반영하고, 구현에 필요한 미결 기술 계약을 마감한다.
- 범위: **설계 보완 6개 작업**. 기본 설계를 처음부터 다시 작성하거나 M0 전체를 구현하는 작업이 아니다.
- 실행 요청문: [DESIGN-GOAL-PROMPT.md](DESIGN-GOAL-PROMPT.md).
- 작성 당시 상태: 작업 목록·요청문 작성, 설계 작업 모두 **대기**. 아래 표·체크박스는 당시 계획을 보존한다.
- 후속 결과(2026-09-26): **M0-D01~D06 설계 보완 완료**. 실제 판정과 검사 결과는 [설계 완료 기록](../m0-design-completion/README.md), 개발 착수·실연동 잔여는 [후속 확인](../m0-design-completion/DEVELOPMENT-READINESS.md)을 따른다. 애플리케이션 구현·운영 인수 완료는 아니다.

## 1. 기준과 선행 확인

제품·기술 기준은 [현재 상태](../../../docs/status.md), [로드맵](../../../docs/roadmap.md),
[수집 기획](../../../docs/planning/content-collection/README.md),
[인프라 계획](../../../docs/planning/02-infra-plan.md)에서 확인한다.
[기존 계획 §12·13](README.md#retention-scope-roles-20260926)은 결정 경위와 보완 필요성의 기록이다.

| 확정 사항 | 이번 설계에서 유지할 기준 |
| --- | --- |
| 검수한 수집 자료 | 이미지·첨부·원문 HTML·본문을 검수 완료·반려 시점부터 7일 후 삭제 |
| 미검수 수집 자료 | 수집일부터 4주, 즉 28일 보관 |
| 중복 방지 | 최소 식별자를 무기한 보관. 앞선 식별자 1년 보관안은 철회 |
| 콘텐츠 사본 | batch 소유 수집 원본과 API 소유 게시글 사본을 구분. 게시글 사본은 기존 콘텐츠 정책 유지 |
| 저장소 | 운영 DB는 PostgreSQL, 공개 전·공개 이미지와 첨부는 R2, **DB 백업만 Google Drive** |
| 백업 기본값 | 기존 dump·암호화·manifest 방식과 매일 03:30·15:30 KST, 최근 7일 보존 유지 |
| M0 출처 | 증거로 검증된 출처만 적용. 기존 21개 목록과 과거 17개 저장 성공을 운영 통과로 간주하지 않음 |
| 운영 권한 | 사용자만 서버·DB 관리·백업·복구 담당. 친구는 게시물 업무 권한만 부여 |
| 알림 | Discord 사용. 채널 생성·현재 사용자만 참여는 사용자 보고이며 실연동·수신은 미검증 |
| 나머지 선택 | 출처 설정 초기 설계는 개발자에게 위임, 우선 읽기 전용 조회. 청록색 `#00A19B` 유지 |

- 실행자는 먼저 현행 정본·실제 source·migration을 대조해 기존 계약과 변경 부분을 구분한다. 문서 간 충돌을 새 정책 선택으로 확대하지 않는다.
- 수집 장비는 미정이며 RPi4는 후보일 뿐이다. 장비·OS·가동 시간, Drive 계정 종류·용량, Discord 연결값은 실연동 전 입력으로 분리한다.
- 기술 설계는 위 정책 안에서 실행자가 결정한다. 실값이 없으면 적용 조건과 확인 시점을 명시하며 비밀 값은 문서에 기록하지 않는다.

| 4 · M0-D04 | 운영자·공동 운영자 권한 매핑 | 운영 역할 확정 | D02·D03의 접근 대상 | 대기 |

공개 화면·관리자 사용성처럼 독립적인 Core 구현은 이 설계 전체가 끝날 때까지 기다릴 필요가 없다.

## 3. 작업별 범위와 완료 조건

### M0-D01 — 보존·삭제·중복 방지

- 대상 정본: [데이터 모델 §9](../../../docs/system-design/02-data-model.md#9-보존과-삭제), [수집 개발 명세](../../../docs/development-specs/m0-collection-assist/collection-assist/collection-assist.dev.md), [보안·운영](../../../docs/system-design/05-security-operations.md).
- 후속 구현 연결: [COL-04](../../../docs/implementation-tasks/collection-controls.md#col-04-direct-보존회수-구현-및-실증).
- 설계할 내용:
  - 수집·검수 완료·반려 시각의 기준 필드, 7일/28일 만료 계산, 재검수·검수 중 만료·동시 처리의 우선순위.
  - 원본 삭제 뒤 남길 최소 중복 키의 필드·정규화·유일성·충돌 처리. 원문·본문·전체 URL을 무조건 영구 보관하지 않도록 최소화 근거 명시.
  - raw/media/body/report/queue/confirmation 및 로컬 임시 파일의 보관 범위. 본문이나 개인정보가 부수 사본에 남는 경로 포함.
  - batch 소유 삭제 작업과 API 소유 콘텐츠 사본의 경계, 참조 보호, 불변 trigger와 제한된 삭제 권한, 실패 재시도·부분 삭제 복구.
  - 백업에 포함되는 자료와 삭제 이력, 복원 뒤 만료 자료·사본이 재노출되거나 다시 생성되지 않도록 하는 절차.
- 산출물: 상태·시각·보존 대상 표, 최소 식별자 모델, 삭제 순서·권한·동시성 계약, 필요한 migration의 설계, 검증 시나리오.
- 완료 조건: 경계 시각·재검수·중복 재접수·부분 실패·보호 사본·복원 사례마다 예상 결과와 검증 방법이 정해져 있다. 실제 migration 파일 작성·DB 삭제는 수행하지 않는다.

### M0-D02 — Web URL 입력 전달·출처 설정 조회

- 대상 정본: [입력 경계](../../../docs/roadmap.md#관리자-url-입력의-미정-경계), [아키텍처](../../../docs/system-design/01-system-architecture.md), [API 설계](../../../docs/system-design/03-api-design.md), [데이터 모델](../../../docs/system-design/02-data-model.md), 수집 개발 명세와 [OpenAPI](../../../docs/development-specs/m0-collection-assist/openapi/m0-collection-assist.yaml).
- 설계할 내용:
  - API 소유 입력 요청을 batch가 조회·확인하는 방식과 인증된 batch 입력 endpoint 방식을 비교하고 **한 가지를 선택**한다. 장비 미정·비상시 가동·네트워크 노출·운영 비용을 고려한다.
  - 접수·중복·처리 확인·재시도·실패·상태 조회 계약, 인증과 DB role, 요청 만료·batch 중단/재시작 시 처리.
  - API/Web은 외부 원문을 fetch하지 않고 batch만 자신의 queue·item 상태를 확정하는 경계.
  - 실제 출처 설정의 읽기 전용 조회 항목·설정 버전·활성/차단 상태·오류 응답. 파일에 적힌 설정과 실행 중 설정을 혼동하지 않는 표시 기준.
- 산출물: 선택 근거, 요청/응답·오류·상태 전이·소유권 계약, 관리자 화면 상태와 API/명세 대응표.
- 완료 조건: 전달 방식을 구현자가 다시 선택할 필요가 없으며 DB·API·OpenAPI가 같은 계약을 설명한다. 출처 설정 편집 UI나 legacy 수집 경로 재활성화는 추가하지 않는다.

### M0-D03 — Google Drive DB 백업 전환

- 대상 정본: [인프라 설계](../../../docs/system-design/04-infrastructure-design.md), [보안·운영 §9](../../../docs/system-design/05-security-operations.md#9-백업).
- 현행 구현 근거: [백업 도구 안내](../../../deploy/backup/README.md). 현행 R2 업로드와 Drive 목표 설계를 명확히 구분한다.
- 설계할 내용:
  - 계정 종류별 인증·토큰 갱신·권한·연결 전 확인 항목. 미정 계정에 맞춰 확정되지 않은 ID나 용량을 만들지 않는다.
  - 암호화된 dump와 manifest의 업로드·파일 식별·중단 후 재개·중복 방지·재시도·용량 부족·만료 정리.
  - 독립 다운로드→해시 확인→격리 PostgreSQL 복원→D01의 만료 정책 재적용→서비스 재개 순서.
  - 백업 성공·실패 판정, Discord 알림 내용·중복 제한, 인증 장애 대응, 별도 복구 키 보관과 사용자 전용 접근.
  - Drive 복원 검증 전 기존 정상 백업을 유지하는 전환·되돌리기 조건. 기존 R2 백업 사본은 별도 보존 기준으로 처리.
- 산출물: 전송·검증·복구·만료·전환 절차, 설정 항목 표, 실패별 대응 및 인수 시나리오.
- 완료 조건: 계정별 적용 조건과 실패 처리가 정의되고 DB 백업 7일과 수집 자료 만료가 구분돼 있다. 백업 속 만료 자료가 정책보다 오래 남는 문제가 있으면 해결 계약 또는 실제 정책 충돌을 명시하며 임의 보존 예외로 덮지 않는다. 실제 인증·업로드·복원은 후속 작업이다.

### M0-D04 — 운영 권한 매핑

- 대상 정본: 인프라 계획, 보안·운영, [관리자 개발 명세](../../../docs/development-specs/m0-core/admin-post-management/admin-post-management.dev.md), [운영자 준비 체크리스트](../../../docs/operations/owner-setup-checklist.md).
- 후속 구현 연결: [운영 인수 task](../../../docs/implementation-tasks/operations-acceptance.md).
- 설계할 내용:
  - 사용자·친구·서비스 실행 계정별 게시물 작업, 수집 검수, 설정 조회, 서버·DB 관리, R2 관리, Drive 백업 다운로드·복구의 허용/거부 표.
  - 기존 인증·접근 통제와 실제 API의 대응, 직접 URL/API 접근 시 거부, 계정 회수와 서비스 자격증명 분리.
  - 친구의 게시물 이미지 작업은 필요한 앱 기능으로 제공하되 서버·스토리지 관리 자격증명은 공유하지 않는 경계.
  - Discord 운영 알림은 현재 사용자 채널을 기준으로 하며 친구 초대를 선행 조건으로 추가하지 않는다.
- 산출물: 역할×행동×통제 위치 표, 최소 설정 변경 목록, 허용·거부 인수 시나리오.
- 완료 조건: 화면 메뉴 숨김과 서버 권한 검사를 구분하고, 공동 운영자의 서버·백업 접근 거부를 검증할 수 있다. 새 권한 관리 화면·범용 권한 프레임워크를 요구하지 않는다.

### M0-D05 — M0 출처 편입 기준·증거표

- 대상 정본: [출처 정책](../../../docs/planning/content-collection/source-collection-policy.md), [출처 검증 기록](../../../docs/planning/content-collection/reference-site-validation.md), [COL-03](../../../docs/implementation-tasks/collection-controls.md).
- 설계할 내용:
  - M0 편입 조건을 목록 발견·실제 원문·본문 순서/이미지/첨부·DB/object readback·요청 통제·운영 증거로 구분한다.
  - 현존 증거의 출처·시점·환경·대상 SHA와 부족한 항목을 정리한다. 증거가 모자라면 후보/미검증으로 남긴다.
  - 실제 적용 출처 목록과 활성화 전 검증 대상을 분리한다. 21개 adapter 존재나 과거 17개 저장 성공으로 운영 통과 수를 확정하지 않는다.
- 산출물: 편입 기준, 근거가 연결된 출처별 증거표, 후속 검증 대상 목록.
- 완료 조건: 증거표와 편입 조건이 완성돼 있다. 운영 증거 부족은 후속 검증 task로 연결하며 출처 성공·활성화를 허위로 완료 처리하지 않는다.
- 제외: [COL-REANALYZE-01](../collection-source-reanalysis/README.md)의 에펨코리아·뽐뿌·유튜브 커뮤니티 재분석. 이 task는 대기 유지하며 PGR21을 임의로 추가하지 않는다. 이번 설계에서 새 사이트 요청을 실행하지 않는다.

### M0-D06 — 문서 정합성 검증·구현 인계

- 대상: 앞선 작업에서 영향이 생긴 정본·개발 명세·OpenAPI와 [설계 준비도](../../../docs/system-design/design-readiness.md), [요구사항 상태](../../../docs/development-specs/requirements-status.md), 로드맵·현재 상태·기존 구현 task.
- 설계할 내용:
  - D01~D05 결정→정본 절→개발 명세→기존 구현 task→검증 시나리오의 연결표.
  - 변경된 기술 계약을 구현 순서·의존성·예상 수정 영역·migration/호환성·되돌리기·인수 증거로 구체화한다. source를 수정하지 않는다.
  - 법무 문서에 영향이 있으면 [법무 안내](../../../docs/legal/README.md)와 [개인정보처리방침](../../../docs/legal/privacy-policy.md)의 미발행 추가안만 필요한 만큼 정렬한다. 발행본·법무 검토·출시 차단 해제를 완료로 표시하지 않는다.

- 완료 조건: 아래 공통 완료 조건을 만족하고 모든 작업의 결과·미검증 범위가 기록돼 있다.

## 6. 실행 제어·중단 기준

| 규칙 | 적용 기준 |
| --- | --- |
| Scope Lock | 요청 범위 밖 작업 금지 |
| Done Criteria | 시작 전에 작업별 조건과 §4의 공통 완료 조건을 확인하고 산출물·검증 방법 명시 |
| Retry Budget | 동일 문제는 최초 시도 포함 최대 2회. 해결되지 않으면 `blocked`로 종료하며 명령·표현 변경으로 횟수를 초기화하지 않음 |
| Progress Guard | 시도마다 산출물·검증 근거·차단 요인 해소를 기록. 2회 연속 실질적 진전이 없으면 `blocked`로 종료 |
| Hard Stop | goal 전체 `완료` / `blocked` / `사용자 판단 필요` 중 하나가 되면 continuation 없이 종료 |

- 종료 시 상태·근거·남은 작업·재개 조건을 보고한다. 완료 조건을 낮추거나 작업 범위를 늘려 계속하지 않는다.
- 사용자 판단이 필요한 새 정책 충돌이 발견되면 선택지와 근거를 보고하고 종료한다. 답을 기다리며 다른 task를 계속하지 않는다.
- 이미 실연동 전 확인으로 분리한 장비·계정값은 그 자체로 현재 설계의 사용자 판단 필요 상태가 아니다. 적용 조건으로 설계할 수 없는 충돌이 있을 때만 해당 종료 상태를 사용한다.
