- 실제 7일 관찰은 테스트 시간 전진으로 단축하거나 대체하지 않는다.

## 4. 작업 묶음별 구현·완료 기준

### 00. 개발 기준선 확정

- main의 관리자 접근·검수 UI·분석 관련 제품 변경과 release의 최신 현황 문서를 대조한다.
- 포함·보류할 변경과 의존성을 기록하고 기존 feature/m0-core의 수정·미추적 파일을 보존한다.
- 일반 구현은 기준 main SHA를 확인한 feature 브랜치에서 진행한다. 다른 담당 작업 중 브랜치를 전환하지 않는다.
- 완료 증거: 기준 SHA, 적용할 변경 목록, 제외 사유, 영향 정본·검사 목록.
- 이 단계는 원격 merge·push·배포를 자동 실행하는 권한이 아니다.

### 01. 공개 화면 마감

- UX-01: 정책 버전 변경 후 로딩이 끝난 본문 상단으로 이동하고 키보드 초점을 일관되게 처리한다.
- UX-02: 상세 페이지의 서버 렌더링 HTML에 공유 이미지 대체텍스트·크기 정보를 제공한다. 이미지 없음·기본 이미지도 검사한다.
- UX-03: 목록 페이지 변경 뒤 새 결과 제목 초점 또는 동등한 보조기기 안내를 제공한다.
- UX-04: 하단 목록 오류를 해당 영역에서 재시도하고, 공유 성공·취소·실패·미지원 상태를 구분한다. 중복 요청도 검사한다.
- UX-06: [색상 기준](../../../docs/planning/07-color-palette.md)을 확정한 뒤 앱·정적 화면의 탭 색상을 정렬한다.
- 주요 경로: `apps/web/app/components/PolicyViewer.vue`, `PostList.vue`, `apps/web/app/pages/[boardSlug]/index.vue`, `apps/web/app/pages/[boardSlug]/posts/[postId].vue`, 관련 CSS.
- 완료 증거: 관련 단위/HTTP 검사, 모바일·데스크톱·키보드 브라우저 검사, 실제 화면 캡처.
- 기준: [Core 화면 task](../../../docs/implementation-tasks/core-ux.md). main에 이미 반영된 동작은 00에서 확인해 중복 구현하지 않는다.

### 02. 관리자 반복 업무 인수

- [운영자 인수 절차](../../../docs/testing/operator-acceptance.md)의 12건을 운영자가 직접 수행한다.
- 작성→검색→편집→이미지 순서·대체텍스트→즉시 발행→숨김→회수→재공개와 예약·취소를 포함한다.
- 소요 시간·혼동·재작업·복구 실패를 기록한다. 최초 측정 전 임의 처리 시간 목표를 합격 기준으로 만들지 않는다.
- 미저장 이탈, 저장 응답 유실, 동시 수정 충돌, 업로드 실패 재시도, 작은 화면 복귀를 함께 인수한다.
- 예약·회수는 실제 격리 실행기의 worker로 확인한다. 테스트에서 내부 함수를 직접 호출한 결과를 실행기 증거로 쓰지 않는다.
- 완료 기준: 내용 유실·중복 발행·잘못된 공개 각각 0건, 발견 결함의 수정 후 재확인 또는 잔여 수용 기록.
- 자동 브라우저 통과와 실제 운영자 확인을 별도로 남긴다.

### 03. 운영 상태·배포 후보·복구 확인

- 먼저 현재 SHA·이미지 digest(이미지 식별값), 기능 flag, DB migration ledger, timer, 최근 백업을 읽기 전용으로 재조회한다.
- 승인된 콘텐츠로 Access 다중 인증의 허용/거부, 업로드·발행·숨김, 예약·취소·중복 없음과 실패 복구를 인수한다.
- 이미지 회수는 공개 URL·캐시·저장소에서 별도 확인한다. API 상태 성공만으로 회수 완료를 판정하지 않는다.
- 운영자가 장애 알림을 실제 수신했는지 확인한다.
- 새 코드 배포가 필요하면 그 후보 SHA의 원격 CI·API/Web 이미지 digest와 현재 DB 호환성을 확인한다.
- 배포 직전 18시간 이내 백업·격리 복원 증거와 호환 버전 복귀 경로를 확보한다. 9/23 백업을 현재 증거로 재사용하지 않는다.
- V008에서 구 API가 readiness 실패한 기존 기록을 고려해 단순 이미지 교체만으로 복귀 가능하다고 가정하지 않는다.
- 실제 복귀·재부팅·새 VM/미디어 복구는 수행 여부와 범위를 각각 기록한다. 새 VM/미디어 복구 훈련은 로드맵 P2-04로 추적한다.
- GTM은 GA4 OFF와 별개로 실제 태그·요청·쿠키·공개 안내를 대조한다. GTM HTML 삽입만으로 동의·정책 조건 충족을 판정하지 않는다.
- robots·사이트맵·noindex는 배포 후보와 현재 DB의 공개/비공개 상태를 대조한다. 검색엔진 실제 색인은 별도 관찰한다.
- 기준: [운영 인수 task](../../../docs/implementation-tasks/operations-acceptance.md), [배포 실행서](../../../docs/operations/deployment-runbook.md), [법무 안내](../../../docs/legal/README.md).

### 04. Web URL 입력 연결

- 현재 legacy 후보 접수와 direct batch 입력을 분리하고 QD-03을 먼저 확정한다.
- 권장 설계안: API 소유의 제한된 요청 접수함에 Web 요청을 기록하고, batch가 소비해 batch 소유 큐를 확정한다.
- 이는 미확정 제안이다. 접수함의 DB/API 계약·인증·권한·완료 확인 방식은 기술 정본에 반영한 뒤 구현한다.
- API는 외부 원문을 fetch하거나 batch 결과·큐를 무제한 수정하지 않는다. batch는 content·검수 상태를 쓰지 않는다.
- 요청 식별자, 정규화·중복, 접수/처리/성공/실패 상태, batch 중단·재시작, 처리 확인 응답 유실을 설계한다.
- 완료 증거: Web 접수→batch 큐→처리 결과→검수 화면 연결, 재전송 중복 방지, 역할 간 쓰기 거부, 미승인 공개 0건.
- 주요 영향: `admin-collect.vue`, API의 새 접수 계약, batch queue/worker, 소유권별 migration·OpenAPI·생성 타입.

### 05. 실제 출처 설정 조회

- 첫 버전은 실제 실행 중인 검토된 설정의 읽기 전용 조회를 권장한다. legacy 수정 화면을 direct 설정 화면으로 간주하지 않는다.
- 노출 정보: 설정 버전/해시, 적용 시각, source별 활성·차단 상태와 이유, 허용 범위·요청 한도.
- batch가 적용한 설정과 화면 표시가 다르면 불일치를 알린다. 적용 확인·갱신 경로를 기술 계약에 포함한다.
- 설정 변경은 검토된 파일과 배포 절차로 관리하는 안을 우선 검토한다. 웹 편집은 권한·감사·충돌 계약이 별도로 필요하다.
- 완료 증거: 실제 적용 설정 식별자 대조, 오래된 상태·실행기 미연결 표시, 비밀값 미노출, API에 batch 설정 쓰기 권한 없음.

### 06. direct 요청 통제

- 단건·목록·queue가 공유하는 요청 경로에 robots 판정, Crawl-delay, 일일 한도와 redirect 제한을 연결한다.
- redirect 최대 3회 계약을 유지한다. 0/3/4회, 순환, host 경계를 검사하고 네 번째 redirect 목적지로 요청하지 않았음을 확인한다.
- 재시도·redirect·미디어 요청의 한도 차감 방식, 기준 시간대, 날짜 경계, 여러 실행기 경쟁, 재시작 후 누적값을 확정한다.
- robots 확인 불가·금지 시 보호 대상 본문/미디어 요청이 발생하지 않아야 한다. robots 확인 요청 자체와 구분해 측정한다.
- `--dry-run`은 현재 DB·object 무쓰기이면서 외부 요청은 발생한다. 영속 한도와의 충돌을 정본에서 해결하고 승인 없이 무쓰기 범위를 바꾸지 않는다.
- 주요 경로: `SourceRequests.java`, `DirectBatchRunner.java`, `DirectUrlRunner.java`, batch 소유 한도 저장과 관련 migration.
- 완료 증거: 요청 수·시각 관측, 금지 대상 요청 0건, 재시작·날짜 경계·동시 실행 테스트, 한도 저장 실패 시 요청 중단.
- 기준: [수집 통제 task](../../../docs/implementation-tasks/collection-controls.md), [direct 기술 계약](../../../docs/system-design/07-spring-collector-design.md).

### 07. direct 원본 보존·회수

- QD-04에서 raw HTML·media·report·run/item·queue·confirmation·감사 기록별 기간과 예외를 확정한다.
- 승격 후 원본, 진행/검수 중 대상, content 참조, 분쟁 보류, 실패 후 미참조 파일의 유예를 함께 정의한다.
- 구체 기간은 `(미정)`이며 legacy metadata 30일을 자동 적용하지 않는다.
- batch 소유의 제한된 삭제 권한과 완료 snapshot 보호 규칙을 함께 설계한다. API·batch에 무제한 삭제 권한을 추가하지 않는다.
- 삭제 예정 목록에는 대상·사유·시점·참조 확인 결과를 남기고, 허용된 비운영 시험 대상부터 삭제한다.
- DB와 object 사이 부분 실패를 재시도할 수 있도록 단계·처리 결과를 기록한다. 보호 여부는 삭제 직전에도 재확인한다.
- 완료 증거: 삭제 예정 목록→제한 삭제→DB·object 독립 재조회, 보호 대상 삭제 0건, 반복 실행·중단 복구·승격 경쟁 검사.
- 저장 목적·접근·보존/파기·고지 정합성은 [수집 기획](../../../docs/planning/content-collection/README.md)과 [법무 안내](../../../docs/legal/README.md)에 연결한다.

### 08. 별도 PC·원격 자원·Discord 실연동

- 실제 사용할 macOS 장비부터 시작하고 Windows·별도 Linux 요구는 각각 검증 상태를 남긴다.
- 비운영 DB·전용 object prefix·제한 역할·Discord 시험 guild/channel을 사용한다. secret 원문을 기록하지 않는다.
- batch→DB/object 저장→API 조회·검수→content 초안 승격을 실행하고 파일 GET의 크기·해시와 DB 값을 대조한다.
- batch의 content/검수 쓰기 거부, API의 batch 쓰기 거부, dry-run 무쓰기, 중단·재시작, 승격 실패 보상을 검사한다.
- Discord는 실제 Gateway에서 확인 전 외부 수집 없음, 본인 확인, 취소·만료·권한 없음·중복 interaction·완료/실패 조회를 검증한다.
- 완료 증거: OS·장비·코드 SHA·시험 자원 범위별 결과와 독립 readback. 로컬 파일 저장 성공으로 원격 object 검증을 대체하지 않는다.

### 09. 출처별 수집 완전성

### Google Drive 검토 — 백업과 서비스 파일을 분리

**권고: Drive는 암호화 백업 사본에 사용 가능하다. 공개 이미지·수집 운영 파일은 현재 R2를 유지하는 안을 우선한다.**
이는 공식 API 기능과 현재 앱 저장소 계약을 대조한 설계 판단이며 사용자 채택 결정·실연동 결과가 아니다.

| 용도 | 판단 | 필요한 구현·검증 |
| --- | --- | --- |
| PostgreSQL DB 백업 파일 | 가능 | `pg_dump` 산출물 암호화→Drive 업로드→독립 다운로드/해시→격리 `pg_restore`; 실패·재인증 알림과 보존 |
| 파일의 별도 백업 사본 | 가능 | 객체 목록·버전/해시와 실제 파일을 함께 보관, 비공개 권한·복구 시험·만료 정책 |
| 운영 DB 자체 | Drive로 대체하지 않음 | PostgreSQL은 계속 DB로 사용. 실행 중 DB 데이터 디렉터리의 단순 동기화를 정상 백업으로 취급하지 않음 |
| 공개 이미지 제공 | 현재 R2 유지 권고 | 기존 custom domain·캐시·공개/비공개·회수 계약 유지. Drive 변경은 다운로드 권한·quota·미디어 경로를 새로 설계해야 함 |
| 수집 중 private 원본 저장 | 기술 검토 가능하나 M0 기본안은 R2 유지 | 현재 S3/R2·object key·역할 경계와 Drive file ID·권한·삭제 모델의 adapter 변경 및 readback 필요 |

- 기존 [백업 도구](../../../deploy/backup/README.md)는 `pg_dump -Fc`→age 암호화→R2 업로드 구조이며 media 전체 복제는 포함하지 않는다. Drive 채택에는 전송/검증 경로 구현이 추가로 필요하다.
- 처음에는 기존 R2 백업을 유지하고 Drive에 독립 사본을 추가하는 안을 권장한다. R2 백업을 완전히 대체하려면 Drive 실다운로드·복원·인증 갱신·실패 알림을 검증한 뒤 전환한다.
- 개인 Google 계정/Workspace 여부·저장 용량·백업 보관기간은 `(미정)`이다. 개인 Drive 자동화에는 사용자 OAuth가 필요할 수 있으며 service account 단독에는 저장 quota/파일 소유권이 없다.
- 실행 중 DB 파일을 동기화하지 않고 DB가 생성한 일관된 백업을 전송한다. 복호화 비밀키는 백업과 별도로 보관한다.
- 첨부 만료는 원본과 백업 사본·복원 시 재생성까지 함께 검토한다. Drive에 장기 사본을 남겨 놓고 첨부 삭제 완료로 보고하지 않는다.
- 아래 공식 문서는 2026-09-26 읽기 전용으로 확인했다. 계정 접속·플러그인 설치·Drive 업로드·저장소 전환은 수행하지 않았다.
