# M0 후속 진행 계획

- 요청: 실제 운영자는 사용자 본인. 프로젝트 진행 계획부터 작성.
- 작성: 2026-09-30. 상태: 계획 작성 완료 / 아래 실행 단계는 미착수.
- 담당: 구현·환경 준비·검증·기록은 Codex, 실제 사용과 운영 판단은 사용자(OWNER).
- 목표: 기존 구현을 빠짐없이 통합한 후보를 만들고, 사용자의 Core 실제 업무 확인 후 운영을 안정화한다.
- 이번에 실행한 Git 작업은 [rebase 결과](README.md)로 분리한다. 새 기능 개발·feature 통합·원격 push·배포·실수집은 실행하지 않았다.

## 2. Git 통합 방법 선택

사용자 후속 질문은 cherry-pick 필요 여부였다. 같은 main 8개를 현재 rebase 결과 위에 다시 cherry-pick하지 않는다.

| 방법 | 맞는 경우 | 이 작업에서의 장단점 | 계획 판정 |
| --- | --- | --- | --- |
| 기존 release 기준에서 main merge | main의 8개 변경을 모두 유지 | 원본 커밋·원격 release 조상 보존. 사전 검사 충돌은 문서4개, 앱 source 충돌0개 | 권장 |
| 기존 release 기준에서 선택 cherry-pick | main 변경 일부를 제외하고 필요한 커밋만 선택 | 공유 release 이력 보존. 새 SHA가 생기고 문서→계약→구현 의존성을 선택해야 함 | 일부 제외 요구가 있을 때 |
| 현재 rebase 결과 유지 | 공유 이력 재작성까지 의도한 경우 | 이미 로컬 수행. 원격 release 고유4커밋과 분기해 단순 push 불가. 현재 hook은 강제 push도 거부 | 현재 결과는 보존하되 후속 원격 반영 기본안으로 추천하지 않음 |

**권장 실행안:** 현재 2126c05를 보존한 뒤, 이전 release bb19c48에서 통합 후보를 만들고 main을 merge한다. 현재 기능 브랜치도 이전 release를 조상으로 갖기 때문에, 4커밋 전체를 유지할 때는 해당 feature merge가 우선이다. 일부만 옮길 때만 아래 커밋을 순서대로 cherry-pick한다. 검증 후 로컬 release를 후보로 정렬하고, 원격 release가 후보의 조상인지 확인해 일반 push 가능한 상태로 만든다. 이번에는 이 교체·merge·push를 수행하지 않는다.

M0 기능 브랜치 전용 커밋:

1. 5ab6dc1 — M0 설계 계약·인계.
2. 71ed8ef — 구현 task·goal 요청문.
3. f1fc07d — M0 보존/입력/권한·운영 도구 구현과 검증 기록.
4. c49d27f — 배치 구조·캐시 검토 기록. 반영해도 캐시/서버 통합안을 채택하는 것은 아니다.

기존 미커밋 파일은 소유권과 변경 내용을 확인해 작업별로 반영한다. stash/reset/clean으로 치우지 않는다. 기존 운영 정책과 hook을 자동 해제하거나 원격 force push로 해결하지 않는다.

## 4. 통합 시 집중할 지점

현재 rebase된 release와 기능 브랜치를 단순 merge하는 사전 검사에서는22개 파일 충돌이 나왔다([목록](INTEGRATION-PREVIEW.json)). 이는 후속 작업의 위험 표본이며 권장한 기존 release 기반 후보 또는 cherry-pick에서 정확히 같은 수가 난다는 뜻은 아니다.

- 공개 목록/상세·admin-batch: main의 관리자/분석 UI와 M0의 접근성·direct/만료 처리를 함께 보존한다.
- consent/nuxt/브라우저 fixture: main의 analytics-v1 이벤트와 M0의 읽기/삭제 실패·재시도를 함께 유지한다. 분석 활성화로 확대하지 않는다.
- OpenAPI·schema·migration evolution: 기능별 정본을 합친 후 생성기로 실행 계약/타입을 재생성한다. 생성물을 한쪽 버전으로 고정해 통과시키지 않는다.
- DB: 기존 적용 migration은 불변. 새 V009/V010·Collector007~010과 역할·보존 계약의 적층을 검증한다.
- 상태·법무·설계: 9/25 배포 기록, 9/27 로컬 구현, 9/30 공개 GET을 각각 구분한다. 출시 차단·실값 미정을 근거 없이 지우지 않는다.
- 과거 worklog 충돌: 당시 사실을 현재 결과로 고치지 않고 원래 양쪽 기록과 출처를 보존한다. 새로운 판단은 새 기록에 남긴다.

검증은 API/Web build·타입/lint·공통 계약 검사 후, 영향받은 관리자/동의/공개 화면 브라우저와 direct/보존/권한 실DB·Collector·선택 복원을 수행한다. 불변 migration·기존 원문/이미지 보존을 별도 확인한다. 과거 SHA의 PASS를 통합 후보에 자동 승계하지 않는다.

## 5. 사용자에게 필요한 부분

- 실제 운영자는 사용자로 확정돼 있다. 별도 운영자를 찾거나 담당자 미정으로 두지 않는다.
- Codex는 기존 계정/설정 위치부터 확인하고 비밀 원문을 채팅으로 요구하지 않는다. 사용자는 실제 MFA, 사용성 판단, 알림 실수신과 콘텐츠 공개 범위만 직접 확인한다.
- 기존 EDITOR 권한 계약은 유지한다. 사용자 OWNER 흐름의 인수와 별도 역할 경계 검증을 구분하며, 이번 발언만으로 친구 계정 사용 여부나 권한 정책을 임의 변경하지 않는다.
- GA4 활성화·광고·회원·캐시·서버 증설·차단 출처 재분석은 이 마감 계획의 신규 선행 조건으로 추가하지 않는다.
