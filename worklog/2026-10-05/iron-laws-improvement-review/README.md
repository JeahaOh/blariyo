## 4. 개선 후보와 수용 조건

우선순위는 이 검토 안의 상대 순서다. 현재 운영 인수 작업의 우선순위를 바꾸지 않는다. 일정·실행 담당은 미확정이며, 아래 시점은 착수 제안이다. 실제 보안 결함의 심각도 판정은 수행하지 않았다.

### IMP-01 · P1 · 로컬 검증 결과를 실제 입력에 연결

- 근거: E2·E3·E7, `docs/ai/harness.md:33,65`, `docs/testing/README.md:262`, `scripts/ci/validation.py:26–73`.
- 공백·영향: CI에는 기계 판독 가능한 receipt(검증 결과 기록)가 있지만 공통 로컬 작업은 수동 기록 중심이다. 같은 HEAD 아래 dirty 파일이 달라져도 과거 PASS를 잘못 인용할 여지가 있다.
- 제안: 기존 명령을 감싸는 작은 로컬 실행기와 결과 검증기를 만든다. `schemaVersion`, 검사 ID, 관련 입력 경로·hash, HEAD/dirty, 명령·도구 버전, 시작/종료 시각, 종료 코드, 실행/실패/생략 수, 필수 여부, 결과·사유를 기록한다. 비밀 환경변수 값은 저장하지 않는다.
- 원칙: 결과 파일은 해당 작업의 worklog 아래 둔다. 입력 집합에서 기록 산출물은 명시적으로 구분해 자기 hash 변경을 피하되, 테스트·설정·계약·lockfile은 포함한다. 전체 저장소 hash만으로 무관한 문서 수정까지 매번 앱 재시험하지 않는다.
- 수용: 관련 코드·검사 정책 변경 시 이전 결과 무효, 기록 본문만 갱신하면 제품 검사 유효성 유지, 미실행·누락·지원하지 않는 결과 형식은 통과 불가. 생성기가 쓴 종합 PASS를 그대로 믿지 않고 항목에서 재계산한다.
- 적용 후보: `docs/ai/harness.md`, `docs/testing/README.md`, 로컬 검사 실행 도구. 기존 CI receipt 형식은 호환성 검토 없이 교체하지 않는다.
- 기대/비용: 오래된 PASS 재사용 방지 / 입력 의존성 관리 필요. 착수 제안: 다음 harness 보완의 첫 작업.

### IMP-02 · P1 · 테스트·정책을 약화해 통과시키는 변경 탐지

- 근거: E6, `AGENTS.md` G06·G07, `docs/ai/harness.md:34`.
- 공백·영향: 금지는 명확하지만 현재 공통 자동 검사에서는 테스트 삭제·skip 증가·검사 대상 축소를 변경 전후로 모아 보여 주지 않는다.
- 제안: 변경 diff에서 테스트 삭제, `test.skip`/`only`, Node 테스트의 `{ skip: ... }`, Java `@Disabled`, assertion 변경, ESLint/TypeScript 무시, 검사 명령·workflow·예외 설정 변경을 별도 검토 목록으로 표시한다.
- 주의: 외부 구현의 문자열·개수 비교만 복사하면 Node의 `assert.equal` 같은 표현과 의미 변경을 놓칠 수 있다. assertion 수 감소 자체는 결함 확정이 아니다. 정상 리팩터링·요구 변경은 기존 사용자 요청과 정본 근거로 판정한다.
- 수용: 대표 우회 변형을 탐지하고, 동일 의미 테스트 이동·중복 정리는 검토 대상으로 구분한다. 제품 검사 PASS가 정책 변경 검토를 덮지 않는다. 이미 승인된 정책 변경을 다시 승인 대상으로 만들지 않는다.
- 적용 후보: harness 검사 도구·정책과 관련 fixture. 테스트 원본을 사용자 폴더에서 강제 복원하는 외부 동작은 가져오지 않는다.
- 기대/비용: 지적을 숨겨 통과시키는 실수 예방 / 단순 패턴의 오탐·누락을 수동 검토해야 함. 착수 제안: IMP-01 뒤.

### IMP-03 · P1 · 검사 완료와 검사 범위 충족을 분리

- 근거: E1·E3·E4·E7, `docs/ai/harness.md:43–51`, `docs/system-design/05-security-operations.md:34–50`.
- 공백·영향: 명령 성공만 보면 필수 경로 누락, 지원하지 않는 언어, 파일 읽기 실패를 놓칠 수 있다. 통합된 로컬 검사 범위 집계는 확인하지 못했다.
- 제안: 변경 종류→필수 검사 대응을 작게 정의하고, 실제 검사 파일·제외 경로/사유·미지원·상한 초과·읽기 실패를 별도 집계한다. 파일 검사 비율과 요구사항 수용 비율은 합치지 않는다.
- 예: Vue 변경은 Web 타입·해당 화면 회귀, API 권한 변경은 역할별 거부 통합 시험, Collector URL 정책은 외부 요청 제한 시험, OpenAPI/계약 변경은 생성 결과·계약 검사에 연결한다. 변경과 무관한 전체 검사를 매번 요구하지 않는다.
- 수용: 검사 대상 0개·필수 파일 미검사·필수 검사 미실행은 전체 PASS 불가. 의도적 비적용은 사유를 남긴다. 지원하지 않는 분석은 기존 테스트/수동 검토로 보완하고, 정적 분석만으로 운영 인수를 완료 처리하지 않는다.
- 적용 후보: `docs/testing/README.md`, harness의 검사 선택·결과 집계. GitHub 유료 보호나 추가 CI는 선행 조건으로 두지 않는다.
- 기대/비용: 미검사 영역이 성공으로 가려지는 문제 감소 / 변경 종류와 검사 매핑 유지 필요. 착수 제안: IMP-01 결과 형식에 함께 설계.

- 제안: 향후 정적 검사에서 필요한 예외에 규칙 ID, 최소 경로/대상, 사유, 승인 근거, 담당, 만료 또는 재검토 조건을 둔다. 대상 코드·정책·보안 전제가 바뀌면 관련 예외만 재검토한다.
- 수용: 사유 없는 예외, 만료 예외, 복제 코드에 자동 승계한 예외를 유효로 보지 않는다. 전체 기존 지적을 baseline으로 일괄 승인하지 않는다.

- 기대/비용: 임시 예외의 영구화 방지 / 작은 예외 저장 형식과 검토 책임 필요. 착수 제안: 실제 예외가 필요한 검사 도입 시.

### IMP-06 · P2 · 중요한 결함 수정은 테스트가 결함을 구별하는지 확인

- 기대/비용: 수정 코드가 없어도 통과하는 약한 테스트 탐지 / 실행 비용 증가. 착수 제안: 다음 영향 큰 결함 수정에 한정 적용, 모든 문서·UI 수정의 필수 조건으로 확대하지 않음.

도구 한계를 실제 소스·표와 대조한 결과:

- `SUPPORT_MATRIX.md:61,64`에서 SQL/명령 삽입 규칙 IL-501/504의 TypeScript 조합은 미검증으로 표시된다. 이는 모든 TypeScript 규칙이 무효라는 뜻도, 검증됐다는 뜻도 아니다.
- `engine/languages.py:34–55`에 `.vue` 파서 매핑이 없다. Nuxt 단일 파일 컴포넌트의 script/template 전체 분석을 보장할 근거가 없다.
- E2 §3의 회귀시험 후보 생성은 Python 모듈 함수와 일부 계열로 제한된다. E5는 Java 등의 파일 간 입력 흐름 추적 한계를 밝힌다.
- E3의 독립 검증기는 보고서 내부 모순을 확인한다. 엔진이 일관되게 틀린 의미 판단이나 실행·승인자의 진위까지 증명하지 않는다.
- E2·E5의 평가 결과는 프로젝트 자체 표본이다. Blariyo 실사용 정확도·성능은 이번 미측정이다.
- 함수 80줄·파일 600줄 같은 외부 기본값, 범용 계층 규칙을 우리 정본보다 우선하지 않는다. 위반 수를 줄이려는 대규모 리팩터링은 이 검토의 범위가 아니다.
