| 선택지 | 장점 | 비용·문제 | 판정 |
| --- | --- | --- | --- |

## 2. 작업 순서·예상 공수

1인 순차 작업 기준 **구현·평가4~7작업일 + 실제 변경5건 관찰**을 초기 추정으로 둔다. 측정한 공수가 아니며 납기 약속이 아니다. 기존 lint 부채 수정, 환경 복구, 원격 실행 대기, 운영 인수는 추정에서 제외한다. 1단계 결과에 따라 재산정한다. 착수일·완료일은 `(미정)`이다.

| 단계 | 우선순위 | 예상 | 산출물·완료 조건 |
| --- | --- | --- | --- |
| 0. 담당·기준선·규칙 확정 | P1 | 0.5일 | 인계·release SHA·작업 branch 확인, 도입/제외 규칙과 검사 범위 확정 |
| 1. 기존 검사 연결 | P1 | 0.5~1일 | API/Web 포함 공통 lint 명령, 실패가 성공으로 바뀌지 않는 실행 경로 |
| 2. 검증 결과 자동 기록 | P1 | 1~2일 | 입력/명령/결과/범위를 기록하고 변경·누락·미실행을 구분하는 최소 도구 |
| 3. 검사 약화 변경 표시 | P1 | 0.5~1일 | 테스트·설정 변경에서 검토 후보 표시, 정상 변경/우회 표본 대조 |
| 4. 외부 규칙 비교 평가 | P2 | 1~2일 | 같은 표본의 기존 ESLint·Anti Slop·iron-laws 비교표, 규칙별 채택안 |
| 5. 선택 반영·운영 관찰 | P2 | 0.5일 + 관찰 | 채택 규칙/버전/출처/담당 기록, 실제 변경5건에서 오탐·누락·시간 관찰 |

단계0→1→2→3→4→5 순서로 진행한다. 0~3만으로 1차 도입 완료를 판정할 수 있다. 외부 규칙을 보류해도 기존 검사와 증거 자동화는 유지한다. 각 단계는 별도 리뷰 가능한 변경 단위로 만든다.

## 3. 단계별 실행 계획

### 0 — 담당·기준선·지침

- 실제 구현 전 현재 공유 폴더 담당의 종료/인계를 확인한다. 기존 dirty를 자동 stash·이동하지 않는다.
- 현재 release와 필요한 미반영 변경의 관계를 확인한 뒤 `feature/ai-quality-evidence`를 제안 작업 브랜치로 사용한다. 이름·기준 SHA는 착수 시 확정한다. 다른 담당 검증 중 브랜치 전환과 일반 작업의 worktree 생성은 하지 않는다.
- 정본에서 새 원칙이 필요한 경우 `AGENTS.md`에만 최소 추가하고 `CLAUDE.md`·`GEMINI.md`의 공통 진입 구조를 유지한다. 제품 기능·법무·기술 계층은 변경하지 않는다.
- 기록 자동화 계약은 `docs/ai/harness.md`, 사용법은 `docs/testing/README.md`에 반영한다. 문서의 구현 상태는 실제 단계별 결과만큼만 갱신한다.
- 기본 추상화·폴더 구조·schema 도구 도입을 이번 범위에 추가하지 않는다.

### 1 — 기존 검사 실행 누락 보완

- `package.json`에 공통 `lint` 명령을 추가해 아래 기존4개를 모두 연결한다. Web은 기존 CI의 build/타입 준비 이후 실행하여 `.nuxt` 입력 생성 조건을 보존한다.

```sh
npm run lint -w @blariyo/api
npm run lint -w @blariyo/web
npm run lint:scripts
npm run lint:tests
```

- `.github/workflows/ci.yml`의 기존 quality에서 중복 호출 없이 공통 명령을 사용한다. 기존 타입·단위·계약·DB·브라우저·Collector 범위를 줄이지 않는다. 필요 없는 새 workflow는 만들지 않는다.
- 첫 실행 결과는 기존 부채와 이번 변경 오류를 나눠 기록한다. 알려진 실패도 통과로 처리하거나 ignore를 늘리지 않는다. 소규모 범위 내 수정으로 해결되지 않으면 해당 단계는 부분 완료로 남기고 수정 범위를 별도로 제시한다.
- 최소 확인: lint 전체 출력·종료 코드, 기존 `npm run test:ci`, workflow 문법 검사. API/Web 코드 수정이 필요해지면 해당 기능 회귀 검사를 추가한다.
- 수용 조건: 네 lint의 실제 실행을 확인하고, 격리 표본에서 위반이 있으면 실패·없으면 성공한다. `tsc`나 build 성공을 lint 성공으로 대신하지 않는다.

### 2 — 검증 결과 자동 기록과 유효성 검사

- 처음부터 범용 harness를 만들지 않는다. 기존 명령을 호출하고 결과를 기록하는 작은 실행기와 기록 확인기만 만든다. 제안 경로는 `scripts/quality/verify.ts`, `scripts/quality/receipt.ts`, 대응 테스트다. 착수 시 기존 유틸과 중복을 다시 확인한다.
- `quality`와 업무별 검사 프로필을 구분한다. `quality` 통과를 DB·브라우저·Java·운영 검사 통과로 확대하지 않는다. 필요한 전체 프로필 목록은 변경 경로와 현행 테스트 계약에서 도출하고 실행 전에 기록한다.
- 시작/종료 시 HEAD, 대상 파일 내용 hash, 파일 추가·삭제·rename·실행 권한, 검사 설정/lockfile/실행기 버전을 기록한다. 대상에는 관련 untracked source도 포함한다.
- 영향 범위를 확실히 추적하지 못하면 관련 workspace와 공유 계약을 넓게 잡는다. 변경 파일만 hash하고 가져오는 모듈을 빠뜨리지 않는다. 생성 소스는 포함하고 단순 build 출력·이번 결과 파일은 입력에서 제외하되 제외 목록을 표시한다.
- 실행 중 입력이 바뀌면 기록은 무효다. 시작/종료 비교가 중간의 변경 후 복구까지 증명하지는 못하므로 공유 편집 중인 폴더에서는 신뢰 가능한 검사로 집계하지 않는다. 기존 G03 담당 분리를 유지한다.
- 출력은 해당 작업의 `worklog/YYYY-MM-DD/<주제>/verification/`에 한정한다. 결과 파일이 자기 입력 hash에 다시 포함되지 않게 한다. 로그 원문에 비밀·외부 데이터가 있을 수 있으므로 비밀값·전체 환경변수·인증값은 저장하지 않는다. 환경 종류/도구 버전과 검사에 필요한 비밀이 아닌 설정만 식별한다.

| 기록 항목 | 판정 기준 |
| --- | --- |
| 실행 | 명령과 인자 배열, 작업 경로, 시작/종료 시각, 도구 버전, 종료 코드 |
| 입력 | HEAD + 관련 source/config/lock/검사 도구 hash + 포함/제외 경로 |
| 범위 | 요청한 검사, 실제 실행한 검사, 미실행/미지원 검사 |
| 결과 | `pass`, `fail`, `not_run`, `unknown`; 테스트 수/실패/skip 수는 읽은 경우만 저장 |
| 유효성 | 입력 변경, 기록 누락, 형식 불일치, 검사 프로세스 중단을 별도 표시 |
| 종합 | 필요한 검사와 각 결과를 다시 계산. 기록의 종합 PASS 문자열을 그대로 신뢰하지 않음 |

- 명령을 실행하는 작업자와 기록을 쓰는 도구가 같은 권한을 가지므로 위변조 방지 인증으로 설명하지 않는다. 원격 CI의 기존 receipt와 별개이며 원격 재사용 기준을 완화하지 않는다.
- 테스트 출력 형식을 인식하지 못하면 테스트0건을 성공으로 추측하지 않는다. lint처럼 건수 개념이 없는 검사는 `null`과 적용 불가 사유를 사용한다. 허용된 비필수 skip과 필수 검사 생략을 구분한다.
- 필수 수용 사례: 정상 실행, 명령 실패, 0건/출력 파싱 실패, 프로세스 중단, 필수 검사 누락, 코드/설정 변경, untracked 입력 추가, 생성 증거만 변경, 실행 중 바뀌어 종료 시 남은 입력 변경, 기록 손상. 잘못된 성공 집계가 없어야 한다.
- 최초에는 명시적 로컬 명령으로 사용한다. 모든 commit에서 DB/browser를 강제하거나 기존 Git hook을 즉시 확장하지 않는다.

### 3 — 테스트·검사 정책 약화 검토

- 제안 경로 `scripts/quality/review-guards.ts`. 기준 release/작업 시작 snapshot과 현재 diff를 비교한다. CI에서 처리한다면 PR base를 기준으로 사용하고 기준을 기록한다.
- 삭제된 테스트, `skip`/`only`, 필수 검사 호출 제거, assertion 감소, lint disable/ignore, tsconfig strict 완화, workflow 조건/실패 무시, 검사 범위·예외 변경을 후보로 표시한다.
- 문자 수·assertion 수만으로 의미적 약화를 단정하지 않는다. fixture 설명문, 테스트 이동/이름 변경, 같은 의미의 assertion 교체, 사용자 요청에 따른 정책 변경을 정상 대조 사례에 넣는다.
- 출력에는 경로·행·변경 전후 규칙·검토 사유를 남긴다. 자동으로 테스트/예외를 고치거나 도구가 스스로 승인하지 않는다.
- 초기에는 검토 보조로 운영한다. 미해결 후보가 있으면 검토 잔여로 보고하되 코드 결함 확정과 구분한다. 확실한 필수 검사 누락은 2단계에서 완료 집계를 거부한다.
- 수용 조건: 선택한 우회 표본 전부 탐지, 정상 대조 사례의 오판 없음. 평가하지 않은 우회까지 탐지한다고 주장하지 않는다.

### 4 — Anti Slop·iron-laws 비교 시험

- [검토 기록](README.md)의 SHA로 source를 고정한다. 실험 의존성은 앱 runtime과 분리하고 lock/출처/라이선스를 기록한다. `latest` 자동 업데이트·외부 스킬의 일괄 설치·autofix는 사용하지 않는다.
- 표본 제안: API 업무2파일, HTTP/오류 경계2, Web TS2, Vue2, Node 테스트2, Java2, 검사 설정2의 **14파일**. 실제 경로와 코드 hash는 착수 때 확정한다. 이는 정확도 모집단을 대표한다는 주장이 아니다.
- 각 채택 후보에 정상/결함 표본을 최소1쌍 추가한다. 실서비스 source를 깨뜨리지 않고 별도 시험 fixture를 사용한다. 두 도구가 지원하지 않는 언어는 미지원으로 집계한다.
- Anti Slop 우선 후보: 누적 복사 탐지, 연속 단언, 넓힌 타입의 재단언. 근거 주석 요구는 별도 후보로 둔다. 입력 `unknown`/`typeof` 금지와 스타일 규칙은 기본 제외한다.
- iron-laws 우선 후보: 오류 은폐·비밀·AI 규칙 파일 위험 지시·반복문 I/O. 의존성/구조 진단은 기존 도구와 추가 효과가 확인될 때만 포함한다. 실제 비밀 대신 가짜 fixture를 쓴다.
- 같은 입력에서 기존 ESLint 결과와 비교한다. 기록: 검사 파일 수, 적용/미지원 규칙, 추가 확인된 문제, 중복, 오탐, 의도적으로 심은 결함의 미탐, 실행 시간, 검토에 든 시간.
- cold1회/warm3회의 시간을 구분한다. 평가하지 않은 Java/Gradle/Vue 영역을 전체 통과로 표현하지 않는다.
- error 승격 제안 기준: 후보 표본에서 미해결 오탐0, 결함 표본 탐지, 기존 검사보다 추가 탐지 또는 명시적 중복 방어 가치, 유지보수 담당과 예외 범위 확정. 기준을 통과해도 전역 정확도100%라는 뜻은 아니다.
- **추가 가치가 없으면 외부 도구0개 설치도 정상 결과**다. 특정 도구 도입 건수를 성공 지표로 삼지 않는다.

### 5 — 선택 반영·관찰·되돌리기

- 채택 규칙만 version/SHA·검사 범위·제외 사유·업데이트 방법과 함께 기록한다. Anti Slop의 복사 코드와 라이선스 유지, Oxlint/플러그인 버전 일치, iron-laws의 Python 환경 분리를 확인한다.
- 실제 변경5건에서 정상 입력 경계 훼손, 불필요한 코드 증가, 오탐, 누락, 검사 대기 시간을 기록한다. 표본 구성은 TS 변경3건·Vue1건·Java1건을 제안하며 해당 변경이 없으면 관찰 미완료로 남긴다.
- 기존 ESLint·타입·구조·DB·browser 검사 결과가 유지되고 새 규칙이 해결한 문제가 추적 가능해야 완료다. 원격 반영은 별도 권한 범위에서 실행한 CI 증거로 확인한다.
- 보류 기준: 정상 경계를 unsafe cast로 바꾸게 함, 광범위 포맷/리팩터링 요구, 필수 검사의 누락·왜곡, 지원하지 않는 파일을 통과로 집계, 근거 없는 예외 증가.
- 되돌리기: 시험 단계는 필수 검사에 연결하지 않았으므로 채택을 보류한다. 정식 도입 뒤 문제가 생기면 원인과 영향·규칙 변경 근거를 검토하고 새 도구의 전용 변경만 되돌리는 안을 준비한다. 통과를 위해 즉석 disable·ignore를 추가하지 않는다. 기존 검사와 당시 실패 증거는 유지한다.

## 4. 변경 경로와 권한

아래는 미래 구현의 제안 allowlist이며 이번 수정 파일 목록이 아니다. `scripts/quality/` 및 신규 설정 이름은 아직 존재하지 않는 제안이다.

| 변경 단위 | 예정 경로 | 별도 확인 |
| --- | --- | --- |
| 최소 지침·증거 계약 | `AGENTS.md`, `docs/ai/harness.md`, `docs/testing/README.md` | 중복 규칙/자동 승인 절차 추가 금지 |
| 기존 lint 연결 | `package.json`, `.github/workflows/ci.yml`, `docs/testing/ci.md`, 루트 `README.md` | 기존 실패와 API/Web 검사 준비 조건 |
| 실행·기록·검토 도구 | `scripts/quality/*.ts`, `tests/quality-*.test.ts`, 필요한 script lint/typecheck 설정 | 실행 도구도 기존 lint/typecheck 대상에 포함 |
| 선택 규칙 설치 | 채택 시에만 `tools/oxlint/anti-slop/`, Oxlint 설정, `package-lock.json`, iron-laws 전용 환경/설정 | 표본 결과·출처·라이선스·정확한 버전 |
| 진행 동기화 | 구현 착수/완료 시 `docs/status.md`, `docs/roadmap.md`, 해당 날짜 worklog | 계획 작성만으로 구현 상태 변경 금지 |

- 앱 source 수정이 필요하면 lint 결과와 관련 기능을 먼저 특정하고 기존 담당과 경로를 분리한다. 예정 경로에 없던 대규모 수정을 자동 포함하지 않는다.
- 작성·검증 담당은 구현 작업을 맡은 Codex/개발자1인으로 지정한다. 채택/예외의 최종 판단과 일정은 사용자다. 하위 에이전트 병렬 작업은 이 계획에 포함하지 않는다.
- commit·push·merge·배포는 각각 실제 요청 범위에 따른다. 이 계획 수립은 해당 권한을 부여하지 않는다. main 병합은 기존 GUI 원칙을 유지한다.

## 5. 비주얼라이징과 이번 완료 기준

- 현재 세션에 `visualize:visualize` 스킬이 있으며 파일도 읽어 확인했다. 대화 내 흐름도·비교·인터랙티브 설명에 사용할 수 있다.
- 이번 계획은 고정된 단계와 의존 관계이므로 Mermaid 흐름도가 적합하다. 값 조절·시나리오 비교가 필요할 때 인터랙티브 시각화를 사용한다. 프로젝트에 별도 패키지를 설치할 필요가 없다.
- 이번 완료 기준: 계획의 단계·대상 파일·수용 조건·미지원·보류/복구·담당/권한을 작성하고 상대 링크·공백·변경 범위를 확인한다. 실제 도구 설치와 앱 검사는 미실행이다.
- 문서 검증: 계획의 상대 링크6개 대상 존재, `git diff --check` 종료0, 신규 파일 `git diff --no-index --check`는 추가 diff에 따른 종료1이며 공백 오류 출력 없음. 작업 전후 branch/HEAD를 확인하고 다른 세션 변경은 보존했다. 이번 쓰기는 이 계획과 README 후속 링크뿐이다. commit/push·설치·앱 검사 미실행.
