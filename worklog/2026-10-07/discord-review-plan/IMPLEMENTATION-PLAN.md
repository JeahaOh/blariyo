## 1. 구현 범위와 완료 기준

- 글마다 `번호 | 제목 | 출처` 헤드1개와 본문 스레드1개를 자동 생성한다. 원문 순서대로 텍스트1문장/이미지1개씩 전달한다.
- 등록된 검수자의 헤드👍만 승인 의사로 인정한다. **매일07:30·17:00 Asia/Seoul**에 이전 미처리 건을 포함해 확인·승인·발행한다. 수집04:30·15:30 일정은 다른 담당의 구현을 따른다.
- 미반응2일 후 반려, 관리자 선처리 시 메시지 삭제, Discord 발행 성공/반려 확정 후 헤드·본문 스레드 삭제를 구현한다. 발행 실패는 메시지와 초안을 보존한다.
- 자동 반려 기산점은 질문 회신 전 **본문 완전 전송 완료+48시간 이후 첫07:30/17:00 회차**를 권고안으로 둔다.48시간 정각 실행과 다르며 정상 운영에서도 추가 대기는 최대14시간30분 미만이다. 장애 시간은 이 상한에 포함하지 않는다.
- 로컬과 운영은 별도 DB/채널/credential을 사용한다. 같은 글이라도 환경별 처리이며 로컬 검수로 운영 글을 발행하지 않는다. 로컬 정기 수집이 운영 Discord 채널에 중복 전송되지 않게 환경·DB 식별자를 시작 시 검증한다.
- 완료는 source·migration·자동 검사, 테스트 Discord 실제 흐름, 운영 배포, OWNER 인수/실시간48시간 관찰을 분리해 판정한다.
- 제외: AI 선별/요약, 수집 parser 변경, 실시간 반응 발행, slash/button UX, 공개 원본 URL, 새 Redis/메시지 브로커, 회원 게시물 신고 처리.

## 4. DB 설계안

API가 소유하는4개 기록을 추가한다. Collect 원본과 독립 설치 경계를 유지하며 item 외래 키 유무는 기존 검수 계약을 따른다.

| 테이블 가칭 | 주요 데이터·제약 |
| --- | --- |
| `collect.discord_review_delivery` | environment/itemId/revision, 재시도해도 유지하는 reviewNo, itemVersion/reviewVersion/contentDigest/renderDigest, head/thread/channel ID, `EXPORTING/READY/BLOCKED/CLOSED`, readyAt/rejectDueAt, cleanup상태·각 대상 삭제 결과. `(environment,itemId,revision)` unique |
| `collect.discord_review_part` | deliveryId, partNo, 원문 block/문장/분할 index, text/media hash, messageId, 전송상태·오류. `(deliveryId,partNo)` unique |
| `collect.batch_review_command` | commandId/itemId, action·actor·origin, 고정 입력/digest·단계·postId, 요청 키, claimOwner/leaseUntil/generation, retryAt/errorCode. 활성 item당1개 partial unique, 동일 요청 키+다른 입력은409 |
| `collect.discord_review_run` | 환경·07:30/17:00 slotKey, 대상선정 cutoff·진행 위치·카운터·점유/복구 상태. slotKey unique, 중복 timer는 같은 실행에 합류 |

- 제약: 사람 actor와 정확히 지정한 `system:discord-review-timeout`을 구분한다. system actor는 **UNREVIEWED→REJECTED+timeout 사유**만 허용하고 APPROVED/초안/발행은 DB/서비스에서 거절한다. 일반 AdminGuard의 관리자 형식·역할을 느슨하게 바꾸지 않는다.
- 기존 `batch_review_request`의 admin-only/200·201 receipt를202 작업 접수 테이블로 재해석하지 않는다. 새로운 command receipt에 접수/실행 상태를 보관한다. system 반려 경로는 별도 내부 메서드로 통제한다.
- table/sequence에 PUBLIC 권한을 주지 않는다. `blariyo_app`의 필요한 API 기록 접근과 backup SELECT, 원문 회수 역할의 제한 함수만 갱신한다. batch role은 신규 command/delivery 쓰기 금지다.
- payload에 본문·이미지 binary를 복제하지 않는다. 전송 조각은 가능한 한 source 참조+hash로 재구성한다. 필요한 임시 제목/텍스트는 원문 만료·전송 종료 회수에서 제거한다. 오래 보관하는 이력은 식별자·행위·결과 중심이며90일 본문 보관 같은 새 정책을 만들지 않는다.
- 미완료 cleanup은 헤드/스레드 ID를 먼저 지우지 않는다. 원문은 기한대로 회수하고 최소 삭제대상 ID로 Discord 회수를 계속한다. 반려 후7일 원문 보존과 Discord 처리 직후 삭제를 각각 시험한다.
- additive migration을 기본으로 하되 actor/함수 변경은 구버전 호환 검사 대상이다. 신규 system 행·진행 작업이 있으면 무조건 down하지 않도록 복구 조건을 명시한다.

## 5. 처리 흐름·API 계약

### 전송

1. 활성화 기준 이후 FETCHED·미검수·미연결·유효기한 내 항목을 찾는다. 안정적인 item 순서+unique insert로 페이지 이동 중 누락/중복을 방지한다. 관리자에서 이미 처리한 기존 건은 보내지 않는다.
2. DB/R2 snapshot을 고정하고 헤드→스레드→텍스트/이미지를 순차 생성한다. 번호·발행 제목·출처를 담고 원문 순서를 유지한다.
3. 각 조각의 응답 ID/hash를 저장한다. nonce의 짧은 유효 시간 이후 응답 유실은 메시지 표식/저장 ID 대조로 복구하며 불명확한 전송을 무조건 반복하지 않는다.
4. 전체 텍스트·이미지 전달을 확인하고 조기👍를 정리한 뒤 READY를 연다. 메시지 내용/필수 첨부 누락을 승인 직전에도 대조한다.2000자 초과는 분할, 이미지 크기 초과는 BLOCKED이지 일부 성공이 아니다.

### 정시 판정

1. DB slot lock 확보 → READY 후보를 제한 페이지로 가져옴 → 관리자 선처리/버전/원문 만료 확인.
2. 저장된 헤드 ID의 일반/슈퍼👍 및 지원 피부색 반응자 목록을 페이지 끝까지 조회하고 허용 운영자와 대조한다. bot/타인/바디 반응은 제외한다.
3. 유효👍가 있으면 현재 권한·snapshot·최신 반응을 다시 확인하고 승인·발행 명령을 원자 접수한다. HTTP/DB가 하나의 transaction은 아니므로 관측 시각과 경합 한계를 기록한다.
4. 없음이 정상 확인되고 rejectDueAt을 지났으면 제한된 system 반려를 실행한다.403/404/429/5xx·part 누락·만료 오류를 무반응으로 해석하지 않는다.
5. 반응 생성 시각은 REST 목록에 없으므로 **실제 정상 조회 당시 상태**를 기준으로 한다. 명령 접수 전👍 취소는 미승인, 접수 뒤 취소는 자동 발행 철회가 아니다.
6. 스캔 시작 cutoff 이전 READY 자료만 이번 run에 포함한다. 이후 READY는 다음 회차다. 페이지별 재개·현재 상태 검사는 유지한다. 스캔 지연/재기동 시점도 이력에 남긴다.

### 공통 승인·발행

- `POST /api/v1/admin/collect/batch-items/:itemId/commands`: DTO로 action/itemVersion/reviewLockVersion/contentDigest/title/boardSlug와 Idempotency-Key를 받는다. Web은 기존 관리자 인증, CLI는 등록 actor/자동 반려용 내부 정책으로 같은 service를 호출한다.
- `GET /api/v1/admin/collect/review-commands/:commandId`: 작업 결과·마지막 성공 단계·postId·오류·재개 가능 여부.
- `POST /api/v1/admin/collect/review-commands/:commandId/resume`: 관리자만 부분 실패 복구, 기존 body·postVersion과 일치하는지 검사.
- 새 경로/operationId는 설계 값이며 아직 없다. OpenAPI→생성 타입/validator→controller/DTO 순으로 연결한다.
- `QUEUED → REVIEWED → DRAFT_CREATED → PUBLISHED`, 반려는 `QUEUED → REJECTED`. 별도의 사용자 검수 중 상태는 만들지 않는다.
- 관리자 요청은 영속 접수 후 즉시 같은 executor 실행을 시도한다. 응답 유실/중단 시 status 조회 및 recovery가 이어받는다. 클라이언트가 단계별 새 요청을 임의 생성하지 않는다.
- 각 단계 키는 commandId+단계로 고정한다. 초안 commit 직후 장애는 receipt/postId 확인으로 복구하고 새 초안을 만들지 않는다. 외부 I/O 전체를 하나의 DB transaction으로 묶지 않는다.
- 잠금 순서는 명령/item→원문 중복→post-storage로 명시한다. 모든 기존 review/draft 진입점도 활성 명령·세대 검사에 참여해야 한다. 새 경로만 잠그고 구 경로를 우회로로 남기지 않는다.
- lease가 만료된 이전 worker는 단계 commit 전 generation이 일치해야 한다. 이미지 업로드와 DB commit 경계의 보상 정리는 기존 소유권 검사를 유지한다. 이미 public인 이미지를 실패 정리로 삭제하지 않는다.

### 삭제

- 관리자 선처리는 review transaction에서 delivery를 CLOSED로 만들고 cleanup을 등록한다. Discord 승인 경로는 PUBLISHED 확정 뒤, 반려는 REJECTED 확정 뒤 같은 방식으로 등록한다.
- 스레드 삭제와 헤드 삭제를 각각 수행·확인한다. 이미 대상 없음은 완료, 권한/제한/통신 오류는 재시도다. 원문 retention과 분리하고 발행/반려는 재실행하지 않는다.
- 발행 실패 메시지는 `재처리 필요`로 남긴다. 관리자에서 해당 초안을 발행해도 linked post의 최종 상태를 감지해 cleanup으로 이어지게 한다.

### 11.1. 삭제 실패 횟수와 결과 안내

1. 승인·발행/반려 결과와 삭제 대기를 먼저 영속 저장한다. 삭제 worker는 승인·초안 생성·발행 함수를 호출하지 않는다.
2. 글의 전달 건별로 `cleanupFailureCount`를 저장한다. **한 번의 정리 실행이 끝났는데 대상이 남으면 실패 1회**로 센다. 같은 실행의 여러 HTTP 오류나 head/thread 각각의 오류를 합산해 2회로 만들지 않는다. 중복 worker가 같은 시도를 두 번 집계하지 않도록 시도 ID와 점유 세대를 확인한다.
3. 삭제 순서는 헤드 → 스레드로 제안한다. 헤드 삭제가 실패하면 스레드는 보존하고 다음 정리 시도에서 재개한다. 이미 삭제된 대상은 확인 후 완료로 처리하고, 남은 대상만 재시도한다. 권한 오류·timeout을 ‘대상 없음’으로 처리하지 않는다.
4. 누적 실패가 **2회에 도달하면** 안내 작업을 등록하고, 다음 삭제 시도에 앞서 쓰기 가능한 해당 스레드에 현재 DB 결과를 남긴다. 상태 안내 예: `승인: 완료 / 발행: 완료 / 게시글: #번호·링크 / Discord 정리: 2회 실패, 삭제 재시도 예정`. 반려는 `반려: 완료 / 발행: 안 함`으로 구분한다.
5. 이후 실패 때마다 새 안내를 쌓지 않는다. `noticeMessageId`로 기존 안내 1건을 수정하며 현재 결과·실패 횟수를 갱신한다. 응답 유실은 전달 건·안내 종류의 고유 표식으로 기존 메시지를 대조한 뒤 재시도한다. 안내 전송 실패 횟수는 삭제 실패 횟수와 분리한다.
6. 안내를 쓴 뒤에도 삭제를 재시도한다. 헤드와 스레드의 정리가 끝나면 안내도 스레드와 함께 사라지며, 업무 결과·실패 이력은 DB에 남긴다. 안내 실패가 삭제 작업을 영구 차단하지 않게 한다.

- 승인됨과 발행됨은 별도 값이다. 관리자에서 승인만 한 경우에는 `승인: 완료 / 발행: 미완료`로 표시한다. 게시글이 이후 비공개/삭제됐다면 현재 상태를 표시하며 과거 발행 성공을 현재 공개 중으로 표현하지 않는다.
- 스레드가 이미 수동 삭제됐거나 쓰기 권한이 없으면 해당 스레드에 안내할 수 없다. 이 경우 `noticeUnavailable`과 이유를 저장하고 관리자에서 확인하게 한다. 자동으로 새 스레드를 만들거나 안내 성공으로 기록하지 않는다. 보관된 스레드는 허용된 권한 안에서 복구 후 안내하고, 잠김/권한 오류는 별도 실패로 남긴다.
- 상태 안내와 운영자 대화 메시지는 검수 본문에 포함하지 않으며, 그 메시지의 반응도 발행 제외 판단에 쓰지 않는다.

### 11.2. 본문 반응 판정 규칙

기존 보안 경계를 유지해 **내부 검수 권한과 연결된 등록 검수자의 반응**만 인정하는 안이다. 여러 검수자가 있으면 한 명이라도 제외 표시를 한 본문 단위를 제외한다. 봇·미등록 사용자·권한 회수자의 반응은 승인과 제외 모두에 사용하지 않는다.

| 대상 | 유효한 반응 | 처리 |
| --- | --- | --- |
| 헤드 | 👍 있음 | 승인·발행 명령 접수 조건. 본문 제외 목록을 함께 확정 |
| 헤드 | 👍 없음 | 승인 안 함. 본문 제외 표시가 있어도 글 승인이 되지 않으며 기존 무승인 만료 규칙 적용 |
| 본문 문장/이미지 | 반응 없음 또는 👍만 있음 | 해당 부분 포함 |
| 본문 문장/이미지 | 👍 외 반응 하나 이상 | 해당 부분 제외 |
| 본문 문장/이미지 | 👍와 다른 반응이 함께 있음 | **제외 우선** |
| 상태 안내·일반 답글 | 어떤 반응이든 | 본문 선택에 영향 없음 |

- 👍의 피부색 변형과 일반/슈퍼 반응은 같은 포함 표시로 해석하는 안이다. 나머지 Unicode/사용자 정의 이모지는 종류와 관계없이 제외 표시다. 헤드의 👍 외 반응을 자동 반려 명령으로 확대하지 않는다.
- `discord_review_part`에 메시지 ID → `contentUnitId` → 원문 블록·문장 구간/이미지 위치 매핑을 저장한다. renderer 버전·원문 digest와 표시 순서를 고정한다. 동일 URL 이미지라도 표시 단위가 다르면 해당 단위만 제외한다.
- 긴 한 문장이 메시지 길이 제한 때문에 여러 메시지로 나뉘면 하나의 문장 ID로 묶는다. 어느 조각에든 제외 반응이 있으면 **그 문장 전체**를 제외한다. 서로 다른 문장을 한 메시지에 묶지 않는다.
- LINK 블록은 링크 설명·URL을 하나의 본문 단위로 취급하는 안이다. 본문 링크 제외와 별개로 게시글의 필수 출처 정보는 유지한다.
- 예: `문장 A → 이미지 B → 문장 C` 중 이미지 B에 ❌가 있고 헤드에 👍가 있으면 `문장 A → 문장 C` 순서로 발행한다. 원문 저장소의 이미지 B는 삭제하지 않는다.

### 11.3. 판정 확정과 발행 본문 구성

1. 정시 scan에서 헤드와 manifest에 등록된 모든 본문 메시지의 반응을 조회한다. 반응 개수가 아니라 실제 반응자를 확인하고, 각 이모지의 일반/슈퍼 반응·사용자 목록 페이지를 모두 처리한다. 조회 실패·누락 메시지는 ‘제외 없음’으로 간주하지 않고 보류한다. [Discord 반응 조회 계약](https://docs.discord.com/developers/resources/message#get-reactions)
2. 원문 버전·검수 잠금 버전·전송 완료·현재 권한을 확인한 뒤 공통 명령에 `excludedUnitIds`, 선택 결과 digest, 원문 digest, renderer 버전, 단위별 근거와 관찰 시각을 함께 저장한다. 멀티 메시지 조회는 원자적이지 않으므로 ‘특정 시각의 완벽한 동시 상태’라고 보고하지 않는다.
3. 확정 전 제외 반응을 해제하면 다음 정상 조회 결과에 따라 다시 포함된다. **명령 접수 후에는 저장한 제외 목록을 고정**한다. 이후 반응 변경으로 재시도 본문을 바꾸거나 새 게시글을 만들지 않는다. 변경이 필요하면 관리자에서 기존 명령·초안과 버전을 확인해 별도 수정한다.
4. Discord 메시지의 텍스트를 발행 원문으로 신뢰하지 않는다. 보존된 원문과 단위 매핑으로 제외 부분만 제거한 발행 후보를 구성한다. 남은 문장·이미지 순서를 유지하고, 포함할 이미지만 게시용으로 복사한다. 선택하지 않은 이미지·문장은 공개 본문과 게시용 이미지 연결에서 제외한다.
5. 원본 수집 데이터의 완전성 검사는 유지한다. 별도로 발행 후보의 본문 유효성·이미지 참조 일치·용량·필수 출처를 검증한다. 원문이 손상됐는데 부분 제외로 검증을 우회하게 만들지 않는다.
6. 모든 본문이 제외됐거나 유효한 발행 후보가 만들어지지 않으면 **발행하지 않고 관리자 확인 필요 상태로 보류**한다. 헤드의 승인 의사와 실패 사유는 보존하며 무반응 자동 반려 대상으로 돌리지 않는다. 후보 검증은 승인 상태 전이 전에 수행한다.
7. 승인 → 선택 본문 초안 → 발행은 공통 명령으로 진행한다. 응답 유실/프로세스 재시작 때 저장된 명령·선택 digest·postId로 재개한다. 관리자와 동시 처리하면 먼저 확정된 상태를 따르며 뒤늦은 Discord 판정은 중복 실행하지 않는다.

| 유효한 헤드 반응 | 48시간 전 | 48시간 도달 후 첫 정상 판정 배치 |
