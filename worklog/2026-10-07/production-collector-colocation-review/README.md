## 판단

- 저트래픽·하루2회 실행에서는 동일 서버 배치를 시험할 여지가 있다. 방문자가 적다는 이유만으로 메모리·디스크 부하가 안전하다고 확정하지 않는다.
- 현행 [인프라 기획](../../../docs/planning/02-infra-plan.md)과 [설계](../../../docs/system-design/04-infrastructure-design.md)는 Lightsail2GB다. 운영 문서의 하드웨어 실측 시점은 과거이므로 현재 서버 사양·가용량을 이번에 실조회한 결과로 주장하지 않는다.
- 배포 Compose 상한은 PostgreSQL768MB, API256MB, Web384MB다. 합계1408MB는 상한이며 현재 사용량·고정 예약량이 아니다. gateway/OS/page cache도 필요하다.
- 현재 `run-batches.mjs`는 기본3개 출처를 별도 Java 프로세스로 실행한다. `run-batch.mjs`에는 JVM heap 한도가 명시되지 않았고 수집기가 외부 HTML/미디어를 메모리로 읽는다. 저트래픽이어도 동시 수집의 메모리 피크를 확인해야 한다.
- 오늘 오후 로컬139건/24분38초는 처리 규모 참고값이다. 운영 처리 시간·CPU/RSS 피크의 측정값이 아니며 단일 출처 실행 시간을 단순3배로 확정하지 않는다.

## 추천 초기 시험

1. 같은 호스트의 별도 수집 컨테이너에서 출처 동시 실행1, 기존5초 요청 간격 유지. API/Web 프로세스 안에 작업을 넣지 않는다.
2. CPU/메모리 상한과 제한된 batch DB 계정·object 권한, 실행 시간 제한·중복 방지·systemd04:30/16:30 timer를 적용한다. JVM heap과 native 메모리를 구분해 한도를 정한다. 자원 상한 기능 근거는 [Docker 공식 문서](https://docs.docker.com/engine/containers/resource_constraints/)다.
3. 먼저 운영의 실제 가용 메모리·기존 서비스 사용량을 읽고, 제한을 건 단일 수집기의 전체1회 CPU/RSS 피크·swap 증가·OOM·공개 응답시간을 비교한다. 여유가 없거나 응답 영향이 크면 실행 중단 후 분리 또는 증설을 판단한다. 운영 실수집은 이번 검토에서 실행하지 않았다.
4. 서버에서 빌드하지 않으며, 백업·배포와 무거운 수집 작업이 겹치지 않도록 확인한다. macOS 잠자기 문제를 없앨 수 있지만 외부 DNS/접근 제한·파싱 실패까지 해결되는 것은 아니다.

## 선택 비교와 제약

- 현행 로컬: 운영 자원 격리, PC 가동/잠자기/네트워크에 의존.
- 운영 동일 서버·동시1: 추가 서버 비용 없이 정시 실행 안정성을 높이는 초기 시험 추천안.2GB 메모리·디스크 경합 실측 필요.
- 운영 동일 서버·동시3: 빠르지만 현재 자원 제한/실측 없이 그대로 이관하는 방식은 비추천.
- 증설/별도 수집 서버: 피크 여유·격리 개선, 추가 비용. 현행 기획대로 사전 증설보다 실제 측정 후 결정한다.
- 현행 [수집 기획](../../../docs/planning/content-collection/README.md)은 웹/API와 다른 컴퓨터 실행이 정본이다. 사용자가 같은 서버 실행을 선택하면 이 경계를 먼저 갱신하고 배포해야 한다. 이번 질문을 운영 이전 승인으로 해석하지 않았다.
- 미검증: 운영 현재 가용 메모리/CPU/디스크, 수집기 실제 최대RSS, 운영 동시 실행 성능. runtime 조회·부하 시험·배포 미실행.
- 검증: 관련 원문·Compose·실행기 직접 대조, 참조 링크 존재, `git diff --check`. 기존 source·운영 자원 변경 없음.
