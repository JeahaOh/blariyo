# 검수 이력으로 수집 필터를 만드는 방안 검토

- 담당: Codex / 상태: 종료 / 갱신: 2026-10-08 06:25 KST.
- 작업 폴더: `/Volumes/MicroVault/iCloudDrive/git/private/blariyo` / 브랜치: `feature/discord-review`.
- 요청: 사용자가 며칠간 승인·보류·반려한 결과를 확인하고 패턴을 찾아 스크랩 단계의 필터로 활용할 수 있는지 검토.
- 범위: 정책·저장 구조 검토, 운영 DB 읽기 전용 집계, 이 기록 작성. 코드·DB·설정·정기 분석 예약·자동 필터는 변경하지 않는다. 기존 untracked 작업 기록은 보존한다.

## 결론

- 가능하다. 현재 명시적 검수 결과로 후보 규칙을 만들 수 있지만, 보류 의도·반려 이유·판정 변화 이력이 충분하지 않아 이를 전부 사용자 취향으로 간주하면 안 된다.
- 추천 순서: 초기3~7일의 결과로 후보 작성 → 실제 제외 없이 예측 결과와 이후 사람 판정을 비교 → 승인할 글을 놓치는지 확인한 규칙부터 제한 적용. 기간은 관찰 초안이며 표본 충분성이나 정확도를 보증하는 기준이 아니다.
- 실행 자동화는 아직 등록하지 않았다. 후속 분석 때 해당 기간의 DB 결과를 조회한다. 장기적인 일별 특징·판정 변화 수집에는 별도 구현이 필요하다.

## 지금 확인한 근거

- [검수 정책](../../../docs/planning/content-collection/README.md#8-discord-보고실행-연동): 헤드👍단독 승인/발행, ❌단독 반려, 둘 다/없음 무승인, 준비 완료48시간 후 첫 배치 만료 반려, 관리자 우선.
- [검수 기술 계약](../../../docs/system-design/10-discord-review.md): 업무 결과는 API/DB 정본이며 Discord 메시지는 처리 후 삭제한다. 메시지 목록만으로 과거 검수 결과를 복원하지 않는다.
- [명령 schema](../../../apps/api/migrations/V014__discord_review.sql): origin·action·stage·item/version/digest·제외 unit·결정 시각·게시글 연결이 남는다. SYSTEM 만료와 사람의 결정을 구분할 수 있다.
- [반응 판정](../../../apps/api/src/features/collection/discord-review-policy.ts): 무반응과 상충 반응은 모두 UNAPPROVED다. 본문 전체 제외는 NEEDS_ADMIN, 읽기 실패는 별도 보류다.
- [관찰 종료](../../../apps/api/src/persistence/discord-review.repository.ts): 최신 last_scan_result만 갱신하고 observation_chunks는 지운다. 날짜별 보류 변화와 누른 모든 반응을 영구 보관하는 분석 이력은 아니다.
- [명령 생성](../../../apps/api/src/features/collection/discord-review.service.ts): 승인 시 excludedUnitIds와 최소 관찰 증거가 남지만 모든 반응 배열이나 사람이 반려한 의미상 이유를 저장하지 않는다.
- 원본 본문·이미지는 검수 완료/반려 후7일, 미검수는 수집 후28일 보존 계약이다. 분석 목적으로 원문 보존을 자동 연장하지 않는다. 필요하면 기간 내 분석하고 최소 특징/집계의 별도 보존 계약을 설계한다.

## 분석에서 구분할 판정

| 관찰 | 분석에 쓰는 의미 |
| --- | --- |
| 사람의 최종 승인 | 채택 사례. 본문 일부 제외가 있으면 조건부 채택으로 분리 |
| 사람의 명시적 반려 | 비채택 사례. 취향·중복·이미지 누락 등 실제 이유는 결과만으로 확정 불가 |
| 무반응 | 아직 안 봄/수정 필요/판단 유보 모두 가능. 부정 사례로 쓰지 않음 |
| 👍/❌ 동시 반응 | 상충/보류 신호. 사람 수와 수정 의도를 추측하지 않음 |
| 48시간 자동 반려 | 시간 만료. 사람이 싫어한 사례에서 제외 |
| 조회 실패·전송 차단·발행 실패 | 기술 문제. 콘텐츠 품질과 분리 |
| 관리자 결정·재시도·중복 명령 | 최신 유효 관리자 결정을 우선하고 item/내용 버전별 중복 집계 방지 |

## 후보 패턴과 적용 위치

| 시점 | 분석 후보 | 절감 가능한 범위 |
| --- | --- | --- |
| 목록에서 상세 요청 전 | 출처·게시판·제목 특성·URL·중복. 해당 정보가 실제 목록에 있을 때만 사용 | 상세·이미지 요청 자체 감소 |
| 상세 본문 분석 후 | SNS 링크 의존·본문 누락·링크만 존재·이미지 수/첨부 메타데이터·반복 홍보 문구 | 후속 이미지 요청/저장 또는 검수 대기 건수 감소. 이미 수행한 상세 요청은 절감 아님 |
| 이미지 수집·품질 확인 후 | 잘림·저해상도·중복 이미지·내용 완성도 | 검수 부담 감소. 이미 다운로드한 이미지 비용 절감으로 보고하지 않음 |

- 출처/주제/형식별 승인·명시 반려 수, 본문 제외 비율, 대표 사례·반례를 함께 제시한다. 표본 수와 분모를 표시하고 출처별 수집량 차이를 선호로 오해하지 않는다.
- 같은 글의 재수집·다른 사이트 재게시를 묶고, 규칙을 만든 날짜 이후의 검수로 검증한다. 같은 글이 후보 생성과 검증 양쪽에 섞이지 않게 한다.
- [SNS 참고 사례 #63·#69](../social-post-capture-direction/README.md)는 SNS 전반을 제외하라는 근거가 아니다. 특히 #69처럼 캡처/이미지 확보로 보완할 사례는 수집 차단 대신 보완 대상으로 구분한다.
- 필터 후보마다 예측 제외 수·그중 실제 반려 수·실제로 승인된 글을 놓치는 수·추정 요청/용량 절감·반례를 보고한다. 증거가 부족하면 규칙 채택을 보류한다.
- 처음에는 기존 수집을 유지하면서 예상 제외만 표시한다. 이후 제한 적용하더라도 일부 후보를 계속 표본 검수해 필터가 잘못 배제하는 글을 발견할 수 있게 하고, 규칙 버전·중단/되돌리기 수단을 갖춘다. 실제 표본 비율·허용 오차는 미정이다.
- 제목 키워드나 출처의 일시적인 낮은 승인율만으로 출처 전체를 막는 결론을 내리지 않는다. 자동 승인·발행으로 범위를 넓히지 않는다.

## 후속 설계 입력

- 항목/내용 버전·환경·검수자 범위·최종 판단·사람/시스템 기원·결정 시각·최소 콘텐츠 특징·제외 단위 비율·판정 사유(있을 때)를 연결한 분석 데이터가 필요하다.
- 의도적인 보류와 미검수 분리, 선택적 반려 사유, 일자별 판정 변화 저장은 현행 공백이다. 기존 검수 흐름의 부담을 늘릴지와 최소 입력 방식을 후속 설계에서 검토한다.
- 이번에는 관련 planning/system-design의 변경안을 확정하거나 자동화를 설치하지 않았다. 채택 시 해당 정본·보존 계약·API/DB 명세를 먼저 맞춘다.
