# 2026-08-14 PostgreSQL 전환 결정

- 상태: 현행 데이터베이스 결정
- 결정: MySQL 8 대신 PostgreSQL 18을 M0의 단일 영구 데이터베이스로 사용한다.
- 적용 범위: 기획, 시스템 설계, 개발 Compose, Express DB driver, 연결·통합 테스트, 백업·복구 절차

> PostgreSQL 선택은 현행이다. 이 문서의 전환 당시 완결성 평가는 이후 [planning·system-design 경계 재검토](./2026-08-14-planning-system-design-boundary-review.md)로 대체됐다.

## 1. 결정 이유

1. 운영용 M0 migration과 production 데이터가 아직 없어 전환 비용이 가장 낮은 시점이다.
2. 게시 상태·정책 버전·outbox처럼 조건부 유일성과 상태별 조회가 중요한 모델에 partial index가 적합하다.
3. 절대 시각은 `TIMESTAMPTZ`, 외부 작업 payload는 `JSONB`, HMAC·SHA-256은 `BYTEA`로 명확히 표현할 수 있다.
4. 단일 VM·Docker Compose·일일 logical backup이라는 M0 운영 방식은 유지할 수 있다.

## 2. 확정 계약

- DBMS: PostgreSQL 18
- database encoding: `UTF8`
- database·session timezone: `UTC`
- application driver: `pg`
- 기본 port: container 내부 `5432`, 로컬 개발 host `45432`, 테스트 host `45433`
- 자동 번호: `GENERATED BY DEFAULT AS IDENTITY`
- JSON document: `JSONB`
- 고정 길이 hash: `BYTEA`와 `octet_length` 제약
- 운영 backup: `pg_dump --format=custom` 결과를 `age`로 암호화해 R2 private backup bucket에 저장
- 운영 restore: 새 PostgreSQL 18에 `pg_restore` 후 migration version과 핵심 데이터 smoke 검증

## 3. 기존 MySQL 경계

- `apps/data/mysql`의 로컬 파일은 자동 변환하거나 삭제하지 않는다.
- 기존 회원 CMS 실험용 schema와 seed는 M0 운영 정본이 아니다.
- 개발 연결 확인용 schema만 PostgreSQL 문법으로 옮기고, M0 운영 schema는 빈 PostgreSQL에 `V001`, seed는 `V002` migration으로 작성한다.
- 과거 세션 문서의 MySQL 언급은 당시 기록으로 보존하되 현행 결정으로 사용하지 않는다.
