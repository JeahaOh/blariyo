## 시작 절차

- git status --short --branch와 git diff --stat를 확인한다.
- 기존 변경과 untracked 파일을 보존한다.
- 과거 완료 보고를 그대로 신뢰하지 않고 현재 코드와 실행 상태를 확인한다.
- P0-01~P0-04별로 구현됨·수정 필요·미검증을 구분한다.
- 차이를 확인한 뒤 필요한 설계 정정과 구현을 이어서 수행한다.

## 구현 원칙

- 기존 API·DB·편집기와 디자인 기준을 재사용한다.
- 화면 계약을 변경하면 관련 planning·개발 명세를 함께 정정한다.
- 목록·검색·편집·이미지·상태별 액션을 하나의 관리자 흐름으로 연결한다.
- loading·빈 결과·권한 없음·오류·재시도·버전 충돌을 처리한다.
- 미저장 이탈, 중복 클릭, 저장 실패로 인한 내용 유실을 방지한다.
- 모바일과 데스크톱에서 주요 작업을 수행할 수 있게 한다.
- 새 관리자 프레임워크, 통계 대시보드, drag-and-drop,
  일괄 발행, 신규 수집 기능은 이번 goal에 추가하지 않는다.
- 수집 결과는 자동 승인·자동 발행하지 않는다.

## 검증과 완료 기준

- next-plan.md의 P0-01~P0-04 완료 기준을 충족한다.
- 변경 범위에 맞는 compile·typecheck·lint·unit·integration 검사를 실행한다.
- DB 테스트는 격리된 테스트 DB에서 수행한다.
- localhost:3000 관리자 화면을 실제 브라우저로 확인한다.
- 10~20건의 테스트 게시글로 작성·편집·이미지·즉시 발행·예약·취소·
  숨김·재공개 흐름을 검증한다.
- 브라우저 표시뿐 아니라 API·DB·필요한 미디어 저장 결과도 대조한다.
- 내용 유실·중복 발행·권한 오류·잘못된 공개가 없는지 확인한다.
- 테스트 인증과 실제 운영자 인증 검증을 구분한다.
- 실제 운영자 사용성 인수가 필요하면 개발자 검증과 별도 상태로 기록한다.
- 실행하지 않은 검증은 통과나 완료로 표시하지 않는다.

## 작업 권한

- 범위 안의 source·test·설계·실행 문서는 수정해도 된다.
- 로컬 검증용 데이터를 생성해도 된다.
- 기존 사용자 게시글과 수집 데이터를 일괄 삭제하거나 초기화하지 않는다.
- 확인된 이 저장소의 로컬 서버는 필요하면 재시작해도 된다.
- 운영 DB·bucket·서비스는 변경하지 않는다.
- 인증·접근 통제를 우회하지 않는다.
- credentials·token·쿠키·개인정보를 출력하거나 문서에 저장하지 않는다.
- commit·push·배포는 하지 않는다.

## 진행 방식

- 계획 제시에서 끝내지 말고 구현과 검증까지 수행한다.
- 합리적인 구현 선택은 기존 계약 안에서 직접 결정한다.
- 단계마다 진행 여부를 다시 묻지 않는다.
- 실패하면 원인을 수정하고 관련 검증을 다시 실행한다.
- 사용자 로그인·권한·중대한 제품 결정이 필요할 때만 질문하고,
  답변을 기다리는 동안 독립적으로 가능한 작업을 진행한다.
- 내부에서 해결 가능한 오류를 외부 차단으로 분류하지 않는다.
- 전체 완료가 아니면 남은 항목과 차단 원인을 명확히 기록한다.

## 토큰 사용과 서브에이전트 운영 지침

실행 시간을 줄이는 것보다 불필요한 토큰 사용을 줄이는 것을 우선해.

- 기본적으로 메인 에이전트가 직접 구현과 검증을 수행한다.
- 독립적인 작업의 병렬 처리가 실익이 있을 때만 서브에이전트를 사용한다.
- 서브에이전트는 동시에 최대 1개만 사용하고 재위임하지 않는다.
- 위임할 때 목표·관련 파일·수정 가능 범위·완료 기준을 좁게 지정한다.
- 메인과 서브가 같은 탐색이나 구현을 중복 수행하지 않는다.
- 서브는 변경 파일·검증 결과·미해결 사항 중심으로 간결하게 보고한다.
- 전체 테스트는 통합 후 실행하고, 이후 변경이 없으면 이유 없이 반복하지 않는다.
- 토큰 절약을 위해 필요한 검증을 생략하거나 완료 기준을 낮추지 않는다.
